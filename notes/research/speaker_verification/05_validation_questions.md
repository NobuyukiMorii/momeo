# 仕様を決める前に確認すること

以下は今後の実験案。今回の調査では推論実験・実機ベンチマークを実行していない。

## 最初に知りたいこと

1. momeoの録音条件で、本人と他人の類似度の分布がどの程度分かれるか。
2. 初回登録を増やす効果と、利用者の手間の関係。
3. 実際の会話でVAD一区間に複数話者が混ざる頻度。
4. 常時録音に本人照合を加えたときの実時間処理能力と電池負荷。
5. 自動更新が固定した初回登録よりよくなるか、他人に引っ張られないか。

## 比較するデータ

本人の読み上げ登録、しきい値調整用の音声、最終評価用の音声を分ける。近接する録音の切り出しをそれぞれに配るだけでは、同じ環境に偏りやすい。別の時間・別の日の自然発話を含める。

| 軸 | 比較候補 |
|---|---|
| 登録量 | 有効音声10秒・20秒・30秒など。前提となる発話数も記録 |
| 照合側の長さ | 0.5秒未満、0.5〜1秒、1〜2秒、2〜5秒、5秒以上 |
| 話し方 | 読み上げ、独り言、会話、相づち、小声 |
| 距離・向き | 手持ち、机置き、離れた位置、ポケットなど実際の用途 |
| 入力経路 | 内蔵マイク、普段利用するBluetooth機器 |
| 環境 | 静音、屋外、反響、生活音、テレビ・動画 |
| 話者 | 本人、会話相手、複数人、声が似ている人 |
| 会話構造 | 単独、素早い交代、同時発話、本人がほとんど話さない場面 |

すべてを最初から網羅する必要はない。最初は静かな単独発話で基本性能を確認し、想定する日常利用へ条件を広げる。日本語以外も使う予定なら別条件として加える。

## 見る指標

- 本人の発話を本人以外として落とす割合。
- 他人の発話を本人として通す割合。本人が不在の録音も含める。
- 判断保留率。保留を増やして見かけ上の誤判定だけを減らしていないかを見る。
- 発話数に加えて、誤って通った／落ちた音声時間。
- 混在区間の割合と、その中に残った他人の発話。
- 雑音・テレビ音声からメモが作られる頻度。
- 登録の完了率、やり直し回数、実際にかかった時間。

FAR/FRRやEERは比較に使えるが、EERが最小になるしきい値が製品に最適とは限らない。本人メモの取りこぼしと他人メモの混入、どちらをどの程度許容するかは実験結果を見て検討する。

## 速度・安定性

- 抽出モデルの初期化時間、初回と定常時の抽出時間。
- VAD、特徴抽出、ASRそれぞれの時間と、合計のRTF。
- 発話終了から表示・保存までの遅延。中央値だけでなく遅い側も見る。
- チャンク到着から処理開始までの待ち時間と、待ち行列の増加。
- iOS/Android実機のメモリ、発熱、長時間実行時の消費電力。
- バックグラウンド、着信やマイク経路変更、復帰後の状態。

同じisolateに追加すればUIスレッドを止めずに済むが、音声処理が追いつくかは測定が必要。別isolateに分ける場合も、CPU競合、モデルメモリ、音声の受け渡し量を含めて比較する。

関連研究として、[PVADの実環境評価、2024](https://arxiv.org/abs/2406.09443)もフレーム単位・発話単位・利用者単位の誤りと検出遅延を組み合わせて評価している。今回は要旨を確認した範囲であり、その実験結果をmomeoへ転用するものではない。

## 自動更新は時間順に評価する

固定した初回基準、単純な平均更新、初回基準を保持した限定更新を比較する。過去の発話から更新した基準で、未来の発話を判定する順序を守る。評価対象そのものを先にプロフィールへ混ぜない。

特に、テレビが長く流れる、相手がずっと話す、本人が不在になる、同じ話者を別人に分裂させるケースを含める。本人の受理率だけでなく、他人の受理率が増えていないかを追う。

初回基準との距離、追加されたサンプル数と出所、更新前後の性能を記録する。悪化が検出された場合に初回基準へ戻せるかも確認する。

## 未決定のまま残すもの

- モデル、初回登録の秒数・文章数、判定と更新のしきい値。
- 単独発話中心で十分か、会話中の交代・重複まで扱うか。
- 判定保留の表示・保存、他人が話したときのカードの追記状態。
- 登録音声を保存するか、特徴量だけ保存してモデル変更時に再登録するか。
- 再インストール、機種変更、バックアップ復元時のプロフィールの扱い。
- 自動更新をいつ導入するか。初回は固定基準だけでも価値が出るか。

「sherpa-onnxのAPIがある」という段階から、「この体験が日常の音声で成立する」ことを確認するための問いとして残す。
