# momeoで取れる実装方法

以下はコード調査に基づく設計候補。仕様・実装への着手を決めたものではない。

## 現在の構成

```text
record: 16kHz / mono / PCM16
  → SttListeningPipeline
  → SttAudioWorker（専用isolate）
  → Float32へ変換
  → Silero VAD（無音1.5秒、最短0.25秒、最長30秒）
  → 区間の波形をSenseVoiceへ
  → SttTranscribed（text / durationSec / elapsedMs）
  → ListeningNotifier._onTranscribed
  → 新しいメモ、または同じメモへ追記
```

| ファイル | 確認事項 | 追加時に関係する点 |
|---|---|---|
| `pubspec.yaml`、`pubspec.lock` | sherpa_onnxとiOS/Android各パッケージが1.13.8 | 現在の版にDart APIがある |
| `lib/stt/stt_listening_pipeline.dart` | マイク取得とworkerへの転送。16kHz・1ch | 登録時も同じ録音経路を利用できる |
| `lib/stt/stt_audio_worker.dart` | `_drainAndTranscribe()`で区間の波形にアクセス | 抽出器を常駐させ、文字起こし前後に照合可能 |
| `lib/providers/stt_providers.dart` | モデルを準備し、workerを生成 | 特徴抽出モデルの初期化・状態を追加する候補 |
| `lib/stt/stt_model_provisioner.dart` | iOS同梱、Androidはfast-follow等、SileroはFlutter asset | 新モデルの配布・実パス・整合性の契約が必要 |
| `lib/main.dart` | Splash → Permission → 準備ゲート → メイン | モデル準備後・通常リスニング開始前に登録画面を挟める |
| `lib/providers/listening_providers.dart` | 空でないテキストを新規作成または追記 | 保存前の判定、保留・除外時の状態遷移を追加 |
| `lib/database/app_database.dart` | メモはid・本文・作成日時 | 話者プロフィール、区間別の判定情報は別途保存が必要 |

音声処理は別isolateにあるのでUI停止は避けやすい。ただし `compute()` やASRはそのisolate内では同期処理。処理が長い間にマイクチャンクが到着すると待ち行列が増える。UIが滑らかであることと、常時音声処理が追いついていることは別。

## 比較する実装方式

| 方式 | 処理 | 利点 | 限界・追加負荷 |
|---|---|---|---|
| A. VAD区間単位の本人照合 | 今の区間ごとに特徴抽出・比較 | 変更範囲が小さく、最初の精度検証に向く | 同一区間に二人が入るとまとめて判定してしまう |
| B. 短い窓での照合・話者追跡 | 音声リングバッファを小窓で比較し、時間方向に判定を安定させる | 発話途中や無音の少ない交代を扱える可能性 | 窓長・重なり・切り替え判定・短い発話の品質がトレードオフ |
| C. 一定範囲のダイアライゼーション＋本人との照合 | 匿名話者区間を求め、音声から再抽出して登録者に対応づける | 複数人の交代を扱う公式部品がある | 追加モデル、処理時間、確定待ち、範囲をまたぐ話者IDの管理 |
| D. 本人専用VAD／対象話者抽出モデルの導入 | 登録音声で条件付けした別モデルを利用 | 本人の発話活動や重複音声の処理に近い研究方向 | 今回確認したsherpa APIだけで完結しない。対応モデル・実行経路を別途調査 |

Aを比較の基準にすると、今の録音でどれだけ本人と他人の特徴が分かれるかを少ない変更で確認できる。その結果と混在区間の頻度を見て、B/Cの負荷が必要かを判断する。

Bの例として[第三者実装](https://github.com/qqlzfmn/sherpa-diarize)があるが、公式の完成したオンライン話者分けAPIではない。Cは[公式Dart例](https://k2-fsa.github.io/sherpa/onnx/speaker-diarization/dart.html)がある。Dは現時点の導入候補というより、A〜Cで目的を満たせない場合の追加調査先。

Dのうち「登録した人が話しているかを逐次検出する」という問いに近い研究が [Personal VAD 2.0](https://arxiv.org/abs/2204.03793) で、ストリーミング・端末上の遅延・CPU/メモリ制約を扱う。ただし、この論文を見つけたことは、対応する配布モデルが現在のsherpa-onnxで使えるという意味ではない。またpVADは発話活動の検出であり、重なった声から本人の波形を取り出す対象話者抽出とは別の処理である。

## 初回の声の登録

ユーザーの案である「静かな場所でいくつかの文章を読む」は、そのまま実験用の登録フローにできる。

1. マイク権限と特徴抽出モデルの準備を確認する。
2. 短い文章を複数収録し、使える音声区間から特徴量を抽出する。
3. 登録音声同士の整合性を確認し、基準を保存する。
4. 保存成功後に通常のリスニングへ移る。

「初回インストール済み」という真偽値だけでなく、**有効な本人プロフィールがあるか**を状態として扱う案がよい。登録中の中断、データ消失、モデル変更があるため。通常は初回だけの操作にしつつ、本人が必要時に再登録できる余地を残す。

初回に登録したベクトル群と、その代表ベクトルを残す。プロフィールにはモデルの識別子・版・次元・正規化方法を関連づける。同じ次元でも別のモデルの特徴量を比較しない。

## 「本人／他人／雑音」の判定

次のように段階を分ける案がある。

```text
音声らしいか（VAD）
  ├─ 非音声らしい → 非音声として扱う
  └─ 音声らしい
       → 比較に使える長さ・品質か
            ├─ 不十分／混在の疑い → 判断保留
            └─ 比較できる → 登録した本人との類似度
                              ├─ 高い → 本人らしい
                              ├─ 中間 → 判断保留
                              └─ 低い → 本人以外らしい
```

「雑音」の厳密な種類まで知りたいなら音イベント分類など別機能も検討対象になるが、本人との類似度が低いことを雑音の根拠にはしない。テレビ・ラジオの声はVAD上は音声で、所有者がその場で発話したものではない。本人の録音再生も本人の特徴に似るため、これを除外することは通常の話者照合とは別課題。

長さ・音割れ・無音量などは計算しやすいが、「二人が重なっていない」は単純なVADだけでは確認できない。品質判定が何を確認できて何を確認できないかを明示して評価する。

## 発話量が最多の人を本人にする案

このルールを本人の定義にすると、例えば次の場面で初回登録と矛盾する。

- 自分は聞き役で、相手が長く話している。
- テレビや動画を再生したまま、バックグラウンド録音している。
- 会議や講義で、進行役が長く話している。
- 本人の短い発話が判定保留になり、長い他人の発話ばかり集計される。

ここで必要なのは「最も目立つ話者」の推定と「端末のユーザー」の照合を分けること。案としては、初回登録との一致で本人の対応を保ち、発話量は補助統計・不整合の検知に利用する。長く話す未知話者を本人に自動昇格させない。

割合を求めるなら、発話回数・文字数より、有効な音声時間を候補にする。ただし現状の `durationSec` には区間内の無音が含まれ得る。重なり窓を二重計上せず、未判定区間を分母から除いたかなど、集計の定義が必要。まだ数値ルールは固定しない。

## 手間を増やさず徐々に改善する案

「モデルの学習」と「本人の比較用プロフィールの更新」は分ける。ここで考えるのは、ONNXモデルの重みを端末で再学習することではなく、同じ抽出モデルで得た特徴量を整理・追加する方法である。

### 二つの基準を持つ

- **初回登録の基準:** 本人が明示的に登録したもの。自動更新で上書きしない。
- **利用中に集める基準:** 採用条件を満たした発話だけを、上限を決めて追加する。更新履歴を持ち、戻せるようにする。

追加の条件の候補は、初回基準との十分な一致、発話長と品質、連続区間内の整合性、時間や録音条件をまたいだ再確認。判定に使うしきい値より、プロフィール更新の採用条件を厳しくする案が考えられる。

一回の長い録音が全体を占めないように、区間・セッション単位の追加数や重みを制限する。自動採用した発話が自動採用の根拠を際限なく広げないよう、初回基準への一致も継続的に見る。

ただし厳しい更新条件では、新しいマイクや大きく変化した声に追従できないことがある。初回基準から離れた変化をすべて自動で吸収できるとは約束しない。必要時だけ再登録・訂正できる方法と組み合わせる。

この案は自己強化による誤更新を抑える設計仮説であり、改善の実測結果ではない。固定基準より悪化しないかを時間順の評価で確認する。

## メモ保存と画面への影響

今の `SttSpeechActiveChanged` はVADに反応して先にUIへ送られる。本人照合を発話終了後に加えるだけなら、他人の声でも録音中の表示は動き得る。「保存時に除外」と「表示も本人にだけ反応」は別の仕様になる。

`SttTranscribed` に照合結果を添え、保存前に判断できる。ただし現在は複数の発話を一枚のメモへ追記するので、カード一枚につき一つの話者スコアだけを置くと情報が失われる。再評価や訂正を想定するなら、発話区間単位の情報を持つ案がある。

他人を除外したときにメモの追記先を維持するか終了するか、判断保留を表示・保存するかも未決定。空の文字起こしと、本人以外のため除外した結果を区別できると検証しやすい。

現在、メモDBには音声自体を保存していない。過去メモの本文だけから声の特徴を再計算することはできない。モデル変更時に再抽出する必要があるなら、登録音声を保持するか再登録するかの選択が必要になる。

## 実装を試す場合の最小構成

特徴抽出モデル一つ、登録用の録音モード、プロフィール保存、worker内の抽出、スコア計算、調査用ログを加える。最初は既存のメモ保存を維持して判定を観察する。

その次に、混在区間対策、本人以外の除外、自動更新をそれぞれ独立に比較する。初回から全機能を組み合わせると、良くなった／悪くなった理由が特定しにくい。
