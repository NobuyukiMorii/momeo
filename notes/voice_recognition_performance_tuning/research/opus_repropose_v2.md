# 音声認識の課題に対する再提案 v2

## この文書について

- **目的**: `opus_repropose_v1.md` と `codex_repropose_v1.md` の対立点を自分で検証し、その結果にもとづいて提案を組み直す。
- **調査日**: 2026-09-20
- **検証の方針**: どちらの文書の主張も無条件には採らない。**モデルの語彙・sherpa-onnx の C++ ソース・モデルカードの原文・配布物の実ファイル**にあたって確かめ、確かめられなかったものは「未確認」と書く。
- **前提条件**（指示されたもの）: クラウドは使わない。製品で使う認識モデルは1つ。表示したテキストは書き換えない。電池と発熱が制約。**即時性は譲ってよい**。課題の優先順位は ①日本語精度 → ②日本語中の英語 → ③英語・中国語 → ④自分と他人の識別。

---

## 0. 結論

**いま何が変わるか**: 検証の結果、**どの多言語モデルも「日本語が現行より良い」根拠を持っていない**ことが分かった。したがって v1 で書いた「多言語モデルに替えれば課題2・3 が解け、課題1 も上がるかもしれない」という見通しは**楽観的すぎた**。選び方を変える必要がある。

- **課題2・3 はモデルを替えるしかない**。これは v1 から変わらず、根拠はさらに固まった（後述 1-1）。
- **ただし、どの候補も日本語では現行に届かない可能性が高い**。現行は日本語35,000時間で学習した専用モデルで、公表 CER は JSUT 6.5 / TEDxJP 9.1。多言語モデルがこれを上回る証拠は見つからなかった。
- したがって**選び方は「素の日本語精度が一番良い多言語モデル」ではなく、「日本語の目減りを取り返す道具を持っている多言語モデル」になる**。道具とは用語登録とビームサーチで、**sherpa-onnx の実装では transducer 型にしか経路が無い**ことをソースで確認した。
- **第一候補は Nemotron 3.5 ASR**。理由は素の精度ではなく、**言語の品質区分が優先順位と一致していること**（日本語=最上位・英語=最上位・中国語=二番手）と、**取り返す道具を持つ唯一の多言語候補**であること。
- **SenseVoice は第二候補に下げる**。中国語に強く最も軽いが、**日本語は Whisper-large-v3 より悪いと開発元自身が公表しており**（11.96 対 10.34）、品質の形が優先順位と逆向き。用語登録の経路も無い。
- **Qwen3-ASR は依然として最後**。ただし v1 で書いた「電力10倍」は**異なる端末の数値を転用した無効な比較だった**。構造から計算し直すと、1発話あたりの重み読み出し量は**現行の約23倍**になる。結論は変わらないが、根拠を差し替える。
- **課題1 に対しては、モデル差し替えが効かない可能性を正面から扱う**。効かなかった場合に何を積むか、どこで撤退するかを先に決めておく。

## 1. 争点の検証

### 1-1. 現行モデルは英語を出せるのか

**codex の指摘**: 「語彙に英単語の断片が無いから原理的に英語不可」とは言えない。a〜z があるので文字を並べれば英単語を構成できる。

**検証**: 指摘は理論として正しい。**v1 の「原理的に不可能」という書き方は誤り**。そこで語彙の構成を文字種ごとに数え直した。

| 文字種 | 1文字のトークン | 2文字以上（マージ済み） |
|---|---:|---:|
| ひらがな | 82 | **261** |
| カタカナ | 84 | **44** |
| 漢字 | 2,422 | 55 |
| 数字 | 10 | **8** |
| **ラテン文字** | **26** | **0** |

この語彙は**マージが起きる種類のもの**である（`▁` を持ち、「って」「から」のような複数文字トークンが261個ある）。マージは**頻出する並びに対して形成される**。数字ですら8個のマージが形成されているのに、**ラテン文字だけがゼロ**。

つまり語彙は**学習データの指紋**であり、この形は「学習時の書き起こしにラテン文字がほぼ存在しなかった」ことを示す。文字を並べて綴ること自体は可能でも、**そう出力するように学習していない**。加えて大文字が1つも無いため、`iPhone` や `API` を正しい表記で出すことはどう転んでもできない。

**結論**: 主張は維持するが、根拠を「語彙に無いから不可能」から「**語彙の形が、英語を学習していないことを示している**」に差し替える。**なお、実際にどう出るかは英語混じりの音声を1本通せば分かる。第0段で最初に確かめる。**

### 1-2. 用語登録は CTC で使えるのか

**codex の指摘**: CTC 向けの contextual biasing は研究・実装が存在するので「原理的に不可能」とは言えない。

**検証**: 指摘は正しい。ただし問われているのは momeo が今日使えるかである。sherpa-onnx の C++ 実装を見て、各認識器が hotwords を参照しているかを数えた。

| 実装ファイル | hotwords の出現 | 意味 |
|---|---:|---|
| `offline-recognizer-ctc-impl.h`（**現行モデル**） | **0** | 設定しても読まれない |
| `offline-recognizer-sense-voice-impl.h` | **0** | 同上 |
| `offline-recognizer-transducer-impl.h` | 37 | 完全に対応 |
| `offline-recognizer-qwen3-asr-impl.h` | プロンプトに注入（`BuildSourceIds`） | 別方式で対応 |
| `offline-recognizer-funasr-nano-impl.h` | **0** | 設定項目は登録されているが、実行経路に参照が無い |

**結論**: 「原理的に不可能」は誤り。正しくは「**sherpa-onnx の現行実装では、CTC と SenseVoice に経路が無い**」。Fun-ASR-Nano は Dart にもコマンドラインにも設定項目があるが、**認識の実行経路で参照している箇所が見つからなかった**。効くかどうかは実行して確かめるまで分からない。

### 1-3. Nemotron の40ロケールは同等か

**codex の指摘**: 公式資料には品質区分があり、普通話は誤り率の高い broad-coverage である。

**検証**: モデルカードの原文を確認した。**指摘は正しく、v1 の「40ロケール対応（日中英）」という書き方は雑だった**。

- 3段階の区分がある: **Transcription-ready 19 / Broad-coverage 13 / adaptation-ready 8**
- **日本語（ja-JP）= Transcription-ready**
- **英語（en-US, en-GB）= Transcription-ready**
- **普通話（zh-CN）= Broad-coverage**

公表 CER（チャンク1120ms・言語指定時）: 英語 7.91 / **日本語 11.48** / **普通話 19.28**。

さらに混在対応の記述を読むと、`target_lang=auto` は「**発話ごとに**言語を判定してタグを出す」仕組みであり、**1文の中に英語が混ざる課題2 そのものを保証するものではない**。一方で「大文字・小文字・句読点・アポストロフィに対応」と明記があり、**ラテン文字を正しい表記で出す能力自体は持つ**。

**結論**: 中国語は二番手。ただし**中国語は優先順位の3番目**なので、この弱点は許容できる範囲にある（後述 2）。

### 1-4. Fun-ASR-Nano の252MB版は実在するか

**codex の指摘**: 「SenseVoice 形式・展開252MB」は公式配布と一致しない。Nano の int8 は encoder/adaptor・embedding・LLM で約950MiB。

**検証**: sherpa-onnx の同じリリースに**別物として両方存在する**ことを、リリースの資産一覧とファイル一覧で確認した。

| 配布物 | 圧縮 | 中身 |
|---|---:|---|
| `sherpa-onnx-sense-voice-funasr-nano-int8-2025-12-17` | 178MB | `model.int8.onnx` **251.3MB** ＋ `tokens.txt` 0.9MB（**単一ファイル**） |
| `sherpa-onnx-funasr-nano-int8-2025-12-30` | 802MB | encoder/adaptor・embedding・LLM の構成 |

codex は後者の公式ページだけを見ている。**前者は実在する**。ただし**公式ドキュメントが無く、対応言語も句読点も未確認**という codex の懸念の本質は正しいので、**配布設計の前提にはしない**という扱いは変えない。

### 1-5. 重いモデルの電力は何倍か（v1 の自分の誤り）

**v1 の記述**: Qwen3-ASR は「RTF がおよそ10倍」。

**検証**: これは**無効な比較だった**。0.7 は Apple Silicon の Mac、0.075 は Pixel 8a の debug ビルドで、**端末が違う数値を割り算していた**。取り下げる。

代わりに、ベンチマークを転用せず**構造から**見積もる。モバイルのバッチ1推論は実質メモリ帯域が効くため、**1発話あたりに重みを何バイト読むか**が電力の目安になる。自己回帰する部分は**出力トークンごとに重みを読み直す**点が決定的に効く。

3秒の発話・出力20トークン・int8 と仮定した場合:

| モデル | 1発話の重み読み出し | 現行比 |
|---|---:|---:|
| 現行 NeMo CTC ja | 0.61 GB | 1.0倍 |
| SenseVoice Small | 0.22 GB | 0.4倍 |
| Nemotron 3.5（貪欲探索） | 0.98 GB | 1.6倍 |
| Nemotron 3.5（ビームサーチ4） | 2.15 GB | 3.5倍 |
| **Qwen3-ASR 0.6B** | **14.29 GB** | **23倍** |

Qwen3-ASR が突出するのは、**721MB のデコーダを出力トークンごとに読み直す**ため。20トークンなら14GBを超える。帯域を楽観的に 20GB/s と置いても、**重みを読むだけで0.7秒**かかる計算になる。

前提（int8・バッチ1・重みのみ・活性値とKVキャッシュは除外・帯域は楽観値）を置いた**桁の見積もり**であって予測値ではない。ただし**桁が違うことは、どの前提を動かしても変わらない**。

**重要な副作用**: この構造は「**まとめて長く認識すると Qwen3 はさらに不利になる**」ことを意味する。出力トークンが増えるほど読み直しが増えるためで、後述する「ひと続きの話をまとめて認識する」案と真っ向から相性が悪い。

### 1-6. 公表 CER は候補の比較に使えるか

使えない。**現行モデル自身の公表値が、その決定的な証拠になっている**。

| デコーダ | JSUT basic5000 | MCV 8.0 test | MCV 16.1 dev | MCV 16.1 test | TEDxJP-10k |
|---|---:|---:|---:|---:|---:|
| TDT | 6.4 | 7.1 | 10.1 | 13.2 | 9.0 |
| **CTC（現行が使用）** | **6.5** | **7.2** | **10.2** | **13.3** | **9.1** |

**同じモデルなのに、テストセットを替えるだけで 6.5 から 13.3 まで2倍開く。** したがって「SenseVoice の日本語 11.96」や「Nemotron の日本語 11.48」を現行の何かと比べても、意味のある結論は出ない。

ついでに **codex の「TDT と CTC の差は約0.1ポイント」も正しい**ことが確認できた（6.4 対 6.5、7.1 対 7.2、9.0 対 9.1）。現行の CTC を TDT に替えるだけの案は、やはり主力にならない。

## 2. 検証してわかった、いちばん重要なこと

**どの多言語候補も、日本語で現行を上回る根拠を持っていない。**

- 現行は**日本語35,000時間で学習した専用モデル**。公表 CER は JSUT 6.5 / MCV8.0 7.2 / TEDxJP 9.1。
- **SenseVoice-Small の日本語は 11.96**。開発元自身の論文の表で、**Whisper-large-v3（10.34）より悪い**。しかも sherpa で使えるのは Small だけで、良い方の Large（9.19）は配布されていない。
- **Nemotron の日本語は 11.48**。最上位の区分には入っているが、現行と同じ土俵の数字ではない。
- Qwen3-ASR の日本語の公表値は見つからなかった。

テストセットが違うので**どれも直接比較はできない**。だが少なくとも、「多言語モデルに替えれば日本語も上がる」と期待できる材料は**1つも無い**。v1 の見通しはここが甘かった。

### だから、選び方が変わる

素の精度で選べない以上、**日本語の目減りを取り返す道具を持っているかどうか**で選ぶ。

```text
【 v1 の選び方 】素の日本語精度が最も良い多言語モデルを選ぶ
                 → 比較できる数字が存在しないので、そもそも選べない

【 v2 の選び方 】① 言語の品質区分が優先順位と一致しているか
                 ② 日本語を取り返す道具（用語登録・ビームサーチ）を持つか
                 ③ 電力が現行と同じ桁に収まるか
```

この3つで候補を並べ直すと、順位が入れ替わる。

| 候補 | ① 品質区分の形 | ② 取り返す道具 | ③ 電力（現行比） |
|---|---|---|---:|
| **Nemotron 3.5** | 日=最上位 / 英=最上位 / 中=二番手。**優先順位と同じ形** | **用語登録・ビームサーチとも可** | 1.6〜3.5倍 |
| SenseVoice Small | 中国語が最も得意 / 日本語は Whisper 以下。**優先順位と逆向き** | **どちらも経路が無い** | 0.4倍 |
| Qwen3-ASR | 多言語に広く対応 | 用語登録はプロンプトで可 | **23倍** |
| 現行 NeMo ja | 日本語のみ | どちらも経路が無い | 1.0倍 |

**Nemotron を第一候補にする理由は「日本語が一番良いから」ではなく、「品質の形が優先順位と一致し、かつ目減りを取り返す手段を持つ唯一の多言語候補だから」。** 中国語が二番手であることは、**中国語が3番目の優先事項である以上、受け入れられる**。

逆に SenseVoice は、**最優先の日本語が最も弱く、優先順位の低い中国語が最も強い**という、求めているものと逆の形をしている。軽さは魅力だが、それは①を犠牲にする理由にはならない。

## 3. 提案

### 3-1. 全体の形

```text
録音（変えない）
  ↓
Silero VAD で発話を切り出す（変えない）
  ↓
発話を順番待ちの列に入れる                    ← 追加（遅延を許容するため）
  ↓
単一の認識器が1回だけ認識する                 ← ここを差し替える
  ↓
確定したテキストを一度だけカードにする（書き換えない）
```

モデルは1つ、認識は1回、表示済みテキストは書き換えない。クラウドも使わない。

### 3-2. 第一候補: Nemotron 3.5 ASR streaming 0.6B

- **課題2・3**: 日本語・英語は最上位区分、中国語は二番手。大文字・小文字・句読点に対応するため、**ラテン文字を正しい表記で出す能力そのものは持つ**。
- **課題1**: transducer なので**用語登録とビームサーチの両方が使える**（実装をソースで確認済み）。日本語の目減りをここで取り返す。
- **電力**: 貪欲探索で現行の約1.6倍、ビーム4でも約3.5倍。**現行と同じ桁**に収まる。
- **配布**: 圧縮453MB（展開は未確認。codex の約650MiB は圧縮率から見て妥当）。現行の625MBから増えはしない。
- **言語指定**: 発話ごとに `language` を切り替えられる。`sherpa_onnx` 1.13.3 の `OnlineStream.setOption` が実在することを確認済み。

**最大のリスクは、これが逐次型であること**。先の音を待たずに決める設計なので、発話全体を見てから決める現行より日本語が落ちうる。緩和は、チャンクを最大の1120ms版にすること（公表値も1120msが最良）と、ひと続きの話をまとめて流し込むこと。**それでも現行に届かなければ採らない。**

**確認していない前提が2つある**。① Nemotron で用語登録とビームサーチが実際に効くか（transducer 一般としては使えるが、このモデルでの実証は見ていない）。② 1文に日本語と英語が混ざったときの挙動。**どちらも第2段で最初に確かめる。**

### 3-3. 第二候補: SenseVoice Small（2024-07版）

日本語が現行より明確に落ちた場合、**中国語と軽さを取りに行く選択肢**として残す。句読点が必要なので、`use_itn` で句読点が付く2024-07版を使う（2025-09版は句読点に対応しない）。

`sense-voice-funasr-nano`（251.3MB）は同じ設定で試せる可能性が高いので、**SenseVoice と並べて一緒に測る**。ただしドキュメントが無いため、配布設計の前提にはしない。

### 3-4. 課題1 への積み上げ（差し替えが効かなかった場合も残る）

モデル差し替えで課題1 が上がる保証は無い。**差し替えと独立に効く手を、軽い順に積む。**

1. **収音と区切りの診断**。語頭・語尾の欠け、停止時に捨てられている最大32msの端数（[stt_audio_worker.dart:415](../../../lib/stt/stt_audio_worker.dart:415)）、無音しきい値、小声、遠距離。**モデルを替えても直らない問題をここで潰す。**
2. **表記の置換辞書**。「プッシュ通知 → push通知」のような自分の書き方に寄せる。ニューラルネットを増やさない。`sherpa_onnx` の `HomophoneReplacerConfig` が認識器の設定として渡せる。
3. **用語登録**（Nemotron を選んだ場合のみ）。固有名詞に直接効き、電力はほぼ増えない。
4. **ビームサーチ**（同上）。遅延を譲ったぶんで払える。電力は約2倍だが桁は変わらない。
5. **量子化の見直し**。int8 と fp16 を比べ、**差が実際にあるときだけ**容量を増やす。

### 3-5. 課題4（自分の声の識別）

**codex は今回の範囲外にしているが、残す。** ただし**優先度は最後**で、①〜③の判断がすべて終わってから着手する。

- 使うもの: 声紋モデル1つ（約27MB）と `SpeakerEmbeddingExtractor` / `SpeakerEmbeddingManager`。**ASR を2回走らせる話ではない。**
- 始め方は codex の慎重論に同意する。**最初は判定ではなくラベル付け**（本人・他者・不明）。いきなり他人の声を捨てると、自分の小声・相づち・外国語の発話まで消えて課題1 の体感が悪化する。
- 1区間に複数人が入る場合は声紋だけでは足りない、という指摘も正しい。**最初は対象外**とする。
- 前回書いた「誤り率1〜2%」は特定のベンチマークの値で、momeo の収音条件には転用できない。**取り下げる。**

### 3-6. 遅延をどう使い、どう使わないか

**使う**: ビームサーチを払う。ひと続きの話をまとめて認識して文脈を増やす。認識が詰まったときに録音を止めずに待たせる。

**使わない**: 重いモデルを正当化する理由には**しない**。1-5 で見たとおり、電力は遅延と別軸で、遅延を許しても1ミリも減らない。

**「ひと続きの話をまとめる」には条件がある。** 1-5 のとおり、自己回帰型では**まとめるほど不利**になる。まとめて得をするのは encoder 主体のモデル（現行・Nemotron・SenseVoice）に限られる。**候補ごとに実測して決める**。長くまとめる場合も、長い無音をまたいで無条件に繋げず、最大30秒程度で区切る。

**遅延を入れるなら、同時に直すものが3つある**（いずれも codex の指摘が正しい）。

- **未処理の音声を RAM に溜めない**。短いファイルとして端末内に置き、テキストの保存が終わったら消す。再起動時は未完了の区間から復旧する。
- **カードの時刻を実際の収録時刻にする**。いまは通知が届いた時点の `DateTime.now()` を使っているため、認識が遅れるほど実際の発話時刻からずれる。サンプル数から出す。
- **保存の順序を保証する**。結果がまとまって届いたときに、新規作成と追記が競合しないようにする。

## 4. 電力が成立する条件

codex の定式化が的確なので、そのまま使う。

```text
発話率 d × 持続運転時の RTF r  <  ASR を動かしてよい時間の割合 b
```

- 発話率が10%でRTF が2なら、必要な稼働割合は20%。成立する。
- 発話率が70%でRTF が2なら140%。**常時動かしても追いつかない**。
- **話者を識別しない以上、他人の声もテレビの音も発話率に入る**。静かな部屋での計測だけで合格にしない。

したがって測るべきは、平均のRTFではなく、**発熱で性能が落ちた後のRTF**と、**最長の待ち時間**と、**未処理が増え続けないか**である。

### 発熱の主因は、まだ分かっていない

現行の ASR は RTF 約0.08（過去の実機記録から算出）。**話している時間の8%しか CPU を使っていない**。いま既に熱いなら、熱源は録音を続ける側にある可能性が高い。

| 切り分け対象 | 確認のしかた |
|---|---|
| マイクの常時取得 | ASR と VAD を止め、録音だけを流して測る |
| 前景サービス・スリープ抑止（Android） | サービスのみ起動して測る |
| Silero VAD | 毎秒31回、録音中ずっと動く。VAD のみで測る |
| 変換ループの割り当て | [stt_audio_worker.dart:442](../../../lib/stt/stt_audio_worker.dart:442) は512サンプルごとに `sublist` と `Float32List.fromList` で確保とコピーをしている。環状バッファにすれば消せる |
| 画面の常時更新 | codex 指摘。背景ウィジェットが毎フレーム更新する。表示あり／なしで比較 |
| 監視タイマー | codex 指摘。500ms周期の見張り。release での必要性を確認 |
| Live Activity（iOS） | 表示あり／なしで比較 |

**debug ビルドの観測値を製品の消費電力と見なさない。release 相当で測る。**

## 5. 採らない案

| 案 | 理由 |
|---|---|
| クラウド ASR | 費用と通信量。指示どおり除外 |
| 二段階認識 | 表示済みテキストの書き換え・複雑さ・発熱。指示どおり除外 |
| LLM 整文 | 2つ目のモデルであり電力を食う。加えて**音声から消えた情報はテキストから復元できない**（codex の指摘が正しい） |
| Qwen3-ASR を先に試す | 1発話あたりの重み読み出しが約23倍。第0段で「ASR にまだ余裕がある」と確認できた場合のみ復帰 |
| 現行の頭を TDT に替える | 公表値の差は0.1ポイント。課題2・3 も解けない |
| 逐次表示への変更 | 課題1〜4 のどれも解かず、画面設計の前提を壊す |
| 雑音抑制を常時かける | 録音中ずっと計算が増える。**雑音が主因と診断できた場合に、発話区間だけへ限定して**初めて検討 |
| Whisper 系（kotoba 含む） | 日本語には強いが、固定30秒枠と自己回帰デコードで電力が合わない |

## 6. 進め方

```text
第0段: 電池と収音を切り分ける（モデルを1つも替えない）
        ・待機 / 録音のみ / 録音+VAD / 録音+VAD+現行ASR で release 相当で測る
        ・生PCM と VAD 切り出し後を聴き比べる。32msの端数を確認する
        ・英語混じりの音声を現行モデルに1本通し、1-1 の推論を実地で確かめる
        ↓  「ASR に余裕があるか」と「収音に問題があるか」が決まる
第1段: 評価音声をそろえる
        ・自分の失敗例が中心。日本語のみ / 日本語+英語 / 英語 / 普通話 / 雑音・他人
        ・調整用と最終判定用を分ける。合成音声だけで判断しない
        ↓
第2段: 同じPCMで3つを比べる
        ・現行 NeMo CTC / Nemotron 3.5（1120ms） / SenseVoice Small（2024-07）
        ・Nemotron では用語登録とビームサーチが効くかを最初に確認する
        ・第0段で余裕が確認できた場合のみ Qwen3-ASR を追加
        ↓
第3段: 遅延を精度に変える
        ・用語登録 → 置換辞書 → ビームサーチ → まとめて認識 の順に積む
        ・1つ積むごとに精度と電力の両方を測る
        ↓
第4段: 話者のラベル付けを足す（本人 / 他者 / 不明）
```

第0段と第1段は**モデルを1つも替えずにできる**。ここを飛ばすと、差し替えの結果を判断できない。

## 7. 判断表

| 分かること | 進む方向 |
|---|---|
| 熱源は録音側で、ASR には余裕がある | 録音側を直したうえで Nemotron へ。Qwen3-ASR も候補に戻す |
| ASR にも余裕が無い | ビームサーチを諦め、Nemotron を貪欲探索で使うか、SenseVoice へ |
| Nemotron の日本語が現行と同等以上 | **採用**。課題1・2・3 が同時に前進する |
| Nemotron の日本語が落ちるが、用語登録とビームサーチで現行に並ぶ | **採用**。ただし電力が桁を変えていないことを確認する |
| Nemotron の日本語が道具を足しても届かない | SenseVoice を同じ手順で評価。それも届かなければ次へ |
| どの多言語モデルも日本語で現行に届かない | **差し替えを見送る**。現行を残して第0段・第3段の積み上げだけを進め、**課題2・3 は解けないと明示する** |
| 日本語は同等だが中国語が実用にならない | 採用してよい。**中国語は3番目**なので、英語混在が解ければ前進と見なす |

**課題2・3 のために課題1 を犠牲にしない。** 迷ったらこの線で切る。そして**「どれも届かない」という結果も、正当な結論として受け入れる**。
