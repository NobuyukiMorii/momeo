# momeo 音声認識の再提案 v4 — 検証を終え、本番で採る構成を決める

作成日: 2026-09-21。

本書は `research/` の提案、`plan/` の検証計画、`spike/` の結果を踏まえた採用方針である。追加の公開情報調査・実機実験・再採点は行っていない。Codex の v2 を本書で更新し、v3 は作成しない。

**推奨は、SenseVoice Small int8（2024-07-17）を単一の認識モデルとして採用し、sherpa_onnx を検証済みの 1.13.8 に揃えること。VAD は `threshold = 0.35` の小変更だけを採り、その他の区切り設定は維持する。追加調査を採用判断の前提にしない。**

この判断で改善を狙うのは、現行モデルが日本語の節を落とす実例と、英語・普通話が読める文字にならない問題である。**日本語全般の精度向上、日英混在の英字表記、電池・発熱の改善をすべて達成したとは扱わない。** 残る限界を明示したうえで、実装へ進む提案とする。

## 1. 採るものと、ここで終えるもの

| 対象 | 決定 | 理由 |
|---|---|---|
| ASR | **SenseVoice Small int8・2024-07-17 版に一本化** | 日本語の脱落していた節を出せ、英語・普通話が文字になり、測定上のメモリ負荷も小さい。offline 構成を維持できる |
| 言語・出力 | **自動判定、ITN 有効、ASR 1スレッド** | S6 で動かした条件。日本語固定に日本語側の利得がなく、普通話が崩れた |
| 推論ライブラリ | **sherpa_onnx 1.13.8 に固定** | S4 以降の比較と同じ土台にする。更新そのものを精度改善とは数えない |
| VAD | **`threshold` を 0.5 → 0.35** | 連続音でも取りこぼしが少し減った。SenseVoice との組み合わせの効果は未測定であることを残す |
| 他の VAD 設定 | **無音 1.5秒・最短 0.25秒・`maxSpeechDuration` 30.0秒を維持** | 値を動かす利得より、空結果や過分割などの不利益が見えている |
| 前余白 | **追加しない** | 大きな改善率は二重区切りの影響が大きい。threshold 変更に重ねる根拠がない |
| Qwen3 / Nemotron | **今回の採用候補から外す** | Qwen3 は実機負荷、Nemotron は短い相づちの脱落と移行負担で見送る |
| S9 hotwords / S10 表記辞書 | **実施しない判断を維持** | S9 は Qwen3 不採用に伴い終了。S10 は実用的な規則を支持する材料が不足 |
| S1 段C・追加の長時間比較 | **未実施のまま今回の調査を閉じる** | 追加調査をしない方針を優先する。長時間運用に合格したという主張はしない |
| 話者識別・新候補の探索 | **今回の対象外** | 未検証の機能や候補を追加すると、調査が再開してしまう |

「採用」は本番実装で選ぶ構成の決定を意味する。本書作成時点でアプリを変更・配布したという意味ではない。

## 2. 検証から採用判断へ持ち越す事実

### 2.1 現行 NeMo をそのまま残す損失も分かった

現行の日本語には実用的な出力がある。一方で、誤字だけでなく、**実際に話した節を丸ごと落とす**ことが確認された。

- 「世界史についてはよく知っています」
- 「表現方法が少し違いますと」

SenseVoice と Qwen3 が出したこの2箇所について、本人が話したことを確認している。Nemotron でも同じ箇所が出た。現行出力が自然に読めることは、内容を取りこぼしていない保証にはならない。[S7 の最終追記](../spike/qwen3.md)、[S8 §6.2](../spike/nemotron.md)

英語では 34.65秒の発話が数文字になり、6.11秒の本人の英語が空になる例がある。普通話もカタカナ音写になり、読める中国語として残らなかった。**空結果の件数だけでは、極端な短縮や文中の脱落を捉えられない。** [S3 §4・§6・§8](../spike/current-baseline.md)

したがって、「日本語専用モデルだから日本語は現行が最も安全」とは決めない。SenseVoice への変更には、③の多言語対応だけでなく、①の具体的な欠落への対処という理由もある。ただし、2例の改善から日本語全般の優位までは言えない。

### 2.2 ライブラリ更新だけでは主要な不満は直らなかった

S4 の同じ固定 wav による比較では、丸ごと経路の空結果は **1件 → 1件**で、空になる行が入れ替わった。34.65秒の英語が `そう` → `そうシ` になっても、問題は解決していない。API 追随は不要で、異常終了はなく、処理時間の明確な悪化も確認されなかった。[S4](../spike/lib-update.md)

ここから採るのは **1.13.8 を本番の土台にする判断**である。「桁落ち修正で精度が改善するから、モデル交換は不要」という初期の期待は採らない。

なお、版間の出力差はライブラリ更新に伴う差とは言えるが、複数の更新を含むため、すべてを特定の正規化修正だけに帰属させない。今回の失敗の主因がそのバグだったという証拠は得られていない。

### 2.3 収音全体を作り直す根拠はない

S2 は計画の8条件を実測し、問題が見つかったのは主に語頭だった。相づち、小声、遠距離、生活音、発話間の機器切替、30秒付近の境界では、測定範囲内で取りこぼしが確認されなかった。停止時の16msの端数も、本人が聴いて声が入っていないと判断している。[S2](../spike/capture-audit.md)

このため、ノイズ除去の追加、録音処理の全面変更、停止端数の修正を、今回の精度改善の主力にしない。発話中の機器切替など未測定の条件は残るが、それを理由に追加の収録を求めない。

### 2.4 VAD の効果は小さく、モデル交換の代わりにはならない

S5 の本番に近い連続音の結果は次のとおりである。[S5 §7・§8](../spike/segmentation.md)

| 条件 | 区切り数 | 空結果 | 1.2秒未満の相づち帯 |
|---|---:|---:|---:|
| 既定 `threshold = 0.5` | 32 | 1 | 10件（空1） |
| `threshold = 0.35` | 33 | 0 | 11件（空0） |

`threshold = 0.35` は小さな取りこぼし対策として採る。人の読み比べでは、読みやすさの明確な改善は得られていない。英語・普通話がカタカナになる不満にも届かない。

切り出し済み wav を再び VAD に通したときの **+6.9pt**、前余白の **+6.7pt** は、本番の精度改善率として使わない。この経路では二重区切りによる損失が大きい。連続音では現行設定でも短い相づちは認識できる。[前余白の訂正](../spike/lead-padding.md)

S5 は NeMo で行われており、**SenseVoice ＋ threshold 0.35 の統合結果はない**。VAD が語頭を少し早く拾うという入力側の利得と、観測範囲で重大な副作用がなかったことから、この値を実装方針に選ぶ。効果の加算や、SenseVoice でも同じ件数が改善することは約束しない。

## 3. SenseVoice を選ぶ理由と、その限界

### 3.1 候補比較の結論

以下は Pixel 8a の既存 spike 記録である。時間は凍結コーパス426.05秒の丸ごと認識、PSS はプロセス全体の観測最大値で、モデルファイルの容量ではない。

| 候補 | 記録された最大PSS | 処理時間 | 品質上の判断材料 | 採否 |
|---|---:|---:|---|---|
| 現行 NeMo CTC | 約1,262〜1,393MB（測定回により異なる） | 約46秒 | 日本語は実用的だが節の脱落あり。英語・普通話が崩れる | 置き換える |
| **SenseVoice auto** | **778MB** | **30.9 / 37.5秒** | 脱落した日本語の節が出る。英語・普通話が文字になる。混在英語はカタカナや誤認識が残る | **採用** |
| Qwen3 上限512 | 4,010MB | 1,655秒 | 混在英語の英字表記に最も有望。出力を切らずに処理すると負荷が大きい | 不採用 |
| Nemotron auto | 1,014MB | 106.4 / 119.5秒 | 長い日本語・英語・普通話は有望。`うん`・`はい`の脱落と語頭への弱さがある | 不採用 |

出典: [S6](../spike/sensevoice.md)、[S7](../spike/qwen3.md)、[S8](../spike/nemotron.md)。Nemotron の表中の負荷値は S8 §6.1 の記録であり、末尾無音を1.6秒に直した品質評価と同じ条件の再測定値とみなさない。

SenseVoice の同一測定内では NeMo の PSS 1,393MB に対し778MBで、約44%小さい。ただしサンプリングされた値であり、長時間の常駐量や真のピークの保証ではない。処理時間も同一条件の実行間で幅があるため、一定倍率の高速化・省電力を成果にしない。

**採用理由は、小ささだけではない。日本語の具体的な脱落を改善し、③を大きく前進させつつ、Qwen3 の負荷と Nemotron の短語の弱点を避け、既存の offline 構成で実装できるという組み合わせである。**

### 3.2 日本語で何が言えるか

S6 では、日本語の脱落した節が復元される例と句読点の出力がある。一方で、不自然な空白、数字の誤り、混在英語の誤認識もある。`1600年` が `16002年` になる例は残っており、数字が直ったとは言えない。

さらに、S6 の主比較は凍結コーパス25件であり、**後から作った台本コーパスについて、SenseVoice の最終判定用成績や相づち9件の正答率は記録にない**。凍結コーパスの空結果0件は、その相づち9件の全正解を意味しない。[S6](../spike/sensevoice.md)、[S3 §8](../spike/current-baseline.md)

したがって、本書の判断は「日本語の非劣性が全面的に証明された」ではなく、**確認できた改善と既知の欠点を比べ、現行を残すより SenseVoice を採る価値があると判断する**ことである。追加の精度比較や人の全件レビューを、その判断の条件にはしない。

### 3.3 日英混在は未解決として残す

SenseVoice は `Facebook` を `フェイスブック`、`iPhone` を `アイフォン` と出す一方、`AirDrop` が `エアジョロ` になる例もある。カタカナなら常に正しく読めるわけでもない。

同じ固定 wav を2回流して25/25一致したことは、実行の再現性を示す。しかし、**別の発話でも同じ英単語を同じ表記にできることとは別**である。記録では SenseVoice の `I think` にも複数の表記がある。[S6](../spike/sensevoice.md)、[S7 §10](../spike/qwen3.md)

本人が英語・普通話のカタカナ音写を不満としている点は、S5 の読み比べで明確になった。SenseVoice によって発話全体が英語・普通話の場合は改善するが、**日本語中の英語を望む英字表記で残す要求は満たし切れない**。これを「多言語対応で②③とも解決」とまとめない。

この制約の下では、②を解くためだけに Qwen3 を載せるより、②の限界を残して SenseVoice を採るほうが妥当と判断する。

### 3.4 Qwen3 と Nemotron を再び試さない理由

**Qwen3 は不採用とする材料が揃った。** 上限128では長い出力が切れ、上限512では処理時間が音声長の3.89倍になった。最大PSSは4,010MB。上限128でも2回目が54%遅くなった。常時録音するアプリで、英字表記のためにこの負荷を引き受けない。hotwords やアクセラレーターの追加検証へ広げない。[S7 §9](../spike/qwen3.md)

**Nemotron は RAM・速度では落ちないが、採る必然性がない。** `うん`・`はい`が空になり、語頭の欠けで `昨日` → `脳`、`来週` → `最終` と化ける例がある。混在英語の英字表記も解決していない。そのうえ online API への移行と、末尾無音など固有の扱いが必要になる。[S8 §4・§6](../spike/nemotron.md)

S8 には「相づち9件が全滅」と「`なるほど`は出る」という記述が併存するため、**全相づち0/9という集約は採用根拠にしない**。根拠にするのは、個別に記載された2モーラの `うん`・`はい`の脱落である。全モデルに共通の採点表がない以上、S8 の平均点から SenseVoice との精度順位も作らない。

## 4. VAD と収音で本番に入れる範囲

| 設定・処理 | 本番方針 | 根拠・扱い |
|---|---|---|
| `threshold` | **0.35 を明示** | 小さな取りこぼし対策。0.25では余計な区切りと空結果が出た |
| `minSilenceDuration` | **1.5秒を維持** | 連続音で0.8秒は空結果が増え、2.5秒は相づちが前の発話にまとまった |
| `minSpeechDuration` | **0.25秒を維持** | 短縮して拾う切れ端を増やしても、認識が良くなるとは限らず、S5では逆効果 |
| `maxSpeechDuration` | **30.0秒を維持** | 強制的な上限ではない。超過すると切れやすい設定へ移る仕様 |
| 前余白の持ち越し | **入れない** | 35秒ぶんのバッファと境界管理を増やすほどの本番上の利得が確認できていない |
| 停止時の変換端数 | **今回の変更に含めない** | S2 の16msに声はなく、精度問題の主因とする根拠がない |
| ノイズ除去 | **追加しない** | S2 の生活音条件で問題は出ず、常時処理を増やす理由がない |

出典: [S2](../spike/capture-audit.md)、[S5](../spike/segmentation.md)、[前余白](../spike/lead-padding.md)。

`maxSpeechDuration` のコメントや説明は「上限」「強制区切り」から、**長い発話を切れやすくする設定で、30秒超も返り得る**という内容へ直す。30秒で必ず区切れることを前提に、バッファや処理時間を設計しない。今回、強制分割の新しい処理は足さない。

## 5. 電池・発熱は、解決済みにしない

S1 の同一画面での比較では、発話なしの CPU 9.48% に対し、発話ありは22.19%。非充電で、発話ありは35.6℃ → 37.4℃、発話なしは37.1℃ → 35.8℃だった。**認識を含む発話中の負荷を無視できない**ことは分かった。[S1](../spike/power-triage.md)

ただし次は分けて扱う。

- **RTF は処理時間の比であり、電池の比ではない。** SenseVoice の短時間処理が軽く見えても、「電池が44%改善」「発熱がなくなる」とは言えない。
- **S1 は画面ONで測っている。** 8.9〜11.9%/時という電池値を、画面OFFの本番の持続時間へ換算しない。温度も同じ測定条件の観察として扱う。
- `9.48 + 12.71r` は S1 の CPU 値を発話率で補間した見方であり、実際の1日の発話率や消費電力を測った式ではない。常時稼働側に改善余地はあるが、部品ごとの寄与や節電量は未確定である。
- **SenseVoice の長時間熱特性、画面OFFの電池、iOS の実測結果はない。** Android の少数・短時間の結果を全端末へ一般化しない。

過去の提案は、長時間測定を採用の前提にしていた。**本書では「追加調査はしない」という現在の方針に合わせ、この前提を変更する。** S1 段Cや4〜8時間の比較を再依頼せず、負荷面で最も扱いやすい測定済み候補を選び、長時間の保証を保留したまま実装方針を決める。

録音変換・描画・監視タイマーの最適化、VADとASRのisolate分離、熱による認識休止、永続音声キューは、今回のモデル交換にまとめて入れない。遅い Qwen3 を採らない以上、それを成立させる大きな構成変更まで引き継ぐ必要はない。既存構成の長時間上の弱点が証明済みで消えたという意味でもない。

## 6. 本番実装の形と順序

```text
既存の録音・バックグラウンド処理（16kHz / mono / PCM16）
  → Silero VAD（threshold 0.35、他は現行値）
  → SenseVoice Small int8（自動判定・ITN有効・1スレッド）
  → 確定テキストを既存の保存・カード表示へ渡す
```

**製品のASRは1つ、各区間の認識は1回。** 仮文の表示、後から別モデルで本文を書き換える処理、クラウドへの音声送信は加えない。既存の小型VADは維持する。

実装は以下の3つに分ける。これは新しい候補比較の計画ではなく、決めた構成を本番へ移す作業単位である。

### 6.1 ライブラリの土台を揃える

`sherpa_onnx` と解決済み依存を1.13.8に揃える。S4 の更新内容を参照し、無関係な依存更新は含めない。これだけを先に分離し、後のモデル変更と原因を切り分けられるようにする。

### 6.2 SenseVoice の認識とモデル準備を一緒に移す

認識器の設定だけを替えて、旧モデルのファイルを読ませる変更にしない。既存資料が挙げる変更対象は次のとおりである。

| 対象 | 実装すること |
|---|---|
| `lib/stt/stt_audio_worker.dart` | SenseVoice の offline 設定へ切り替える。S6 と同じ自動言語判定・ITN・スレッド数を使う |
| `lib/stt/stt_model_provisioner.dart` | 配布物の識別子、model/tokens の対応、期待サイズ、検証値、配置先を新モデルへ揃える |
| `lib/providers/stt_providers.dart` と準備処理 | 新モデルが準備できたときだけ認識を開始し、失敗時には既存の準備・再試行経路へ戻す |
| 取得・配置スクリプト、Android / iOS の既存資産設定 | 配布対象を S6 のモデルへ統一する。spike の端末固定パスを本番へ持ち込まない |
| 開発用の説明・カタログ | 現行モデル名や処理方式の説明を実装に合わせる |

対象配布物は **`sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17`**。S6 に記録された `model.int8.onnx` は239,233,841 bytes、`tokens.txt` は315,894 bytesである。アーカイブと個別ファイルのSHA256は [S6 のモデル出典](../spike/sensevoice.md)を正本として引き継ぐ。名前が似た別版や Fun-ASR-Nano に置き換えない。

移行時にはモデルとtokensの取り違えを防ぎ、新モデルの準備完了前に旧資産を消さない。移行後の通常実行で旧・新ASRを二重にロードしない。メモDBや既存テキストはモデル更新のために消さない。

Play Asset Delivery など新しい配布方式や、汎用のモデル選択UIは作らない。spike で省いていた**既存配布経路への接続と準備失敗への対応**は、本番実装の一部として行う。

### 6.3 VAD の小変更を分離して入れる

`threshold = 0.35` を明示し、他の値は変えない。`maxSpeechDuration` の説明も直す。モデル変更とは別の差分にしておけば、統合時に予期しない取りこぼしが出た場合、threshold だけ0.5へ戻せる。

**spike ブランチを丸ごとマージしない。** S4・S6・S5 の必要な実装だけを参照して本番向けに作る。比較用の候補切替、専用main、画面を起こす実験設定、生PCMや評価wavの自動保存、計測ランナーは製品へ入れない。[計画の運用方針](../plan/master.md)

## 7. 実装の完了確認を、追加調査に広げない

この依頼で行うのは提案書の作成までである。将来の本番実装では、変更を壊さず届けるための確認を次に限定する。

| 確認 | 完了の見方 |
|---|---|
| 静的解析・対象プラットフォームのビルド | 変更が解析・ビルドを壊していない。Androidの実測をiOSの動作確認の代用にしない |
| モデルの初回準備・既存環境からの更新・準備失敗 | 正しいモデルとtokensを読む。失敗を検出でき、データを失わず再試行できる |
| 固定音声による実装の回帰確認 | 既存音声と既存出力を使い、設定ミス・モデル取り違え・空結果の異常増加などを検出する。新しい正解作成やモデル順位付けをしない |
| 区切り変更の確認 | 既存の連続セッション音声を使う。切り出し済みwavの二重VADを本番の代用にしない |
| 既存の録音・停止再開・保存の接続 | 終了処理、結果の保存、カードへの追加を変更が壊していない。音声を製品で意図せず保存していない |

S4 で既存の Counter 用 `widget_test` が元の版でも失敗すると分かっている。新しい変更の回帰と区別し、古いテストの失敗を理由にモデル比較を再開しない。一方で、その失敗を新実装が正しい証拠にも使わない。

**新規録音、追加のモデル探索、設定総当たり、人による全件採点、長時間の比較試験は、この完了確認に含めない。** 既存素材で明確な実装回帰が見つかったときは、その不具合を直す。閾値変更に限った問題なら0.5へ戻し、モデル自体を安全に組み込めない問題なら変更を戻す。第二ASRの併用や新しい研究課題で埋め合わせない。

## 8. 記録の食い違いは、この読み方で整理する

資料は追記型なので、冒頭の状態や昔の申し送りが後の結果と一致していない箇所がある。本書では、具体的な実測・本人の確認・後の明示的な訂正を優先した。

| 古い記述・混同しやすい記述 | 本書での扱い |
|---|---|
| 「英語・普通話の正解が未確定」「最終判定用がない」 | S3 の後の追記で解消。ただし凍結コーパスの内容確認と、台本コーパスの逐語採点は区別する |
| 6.11秒の空結果は他者音声・雑音 | 本人の英語と確認済み。S4などに残る古い区分は使わない |
| 「同じ音声でも実行ごとに表記が変わる」 | 固定wavの同条件再実行は一致する。録音時とwav再投入、別発話間の差を区別する |
| 「相づちは0.5秒未満だと構造的に落ちる」 | 二重VADの条件での観察。本番に近い連続音では現行でも拾う |
| 「minSilenceDuration は無効」 | 切り出し済みwavの結果に限る。連続音では区切り数・長さが変わる |
| 「前余白とthresholdでそれぞれ約7pt改善」 | 本番効果として宣伝せず、足し合わせない。併用の効果も未測定 |
| 「Nemotron は相づち9件が全滅」 | 同じ記録で `なるほど` は出る。短い `うん`・`はい`の脱落を根拠にする |
| 台本コーパス30件と32件、相づちの低い集約点 | 記録ごとの入力集合・経路・文への結合単位が異なるため、共通の分母として合算しない |
| S8やS10にある「現行は句読点を出さない」 | 現行にも句読点の実例がある。「モデル交換で句読点の差がすべて消える」とは言わない |
| S10の2規則は、かな→漢字と漢字→かななので矛盾する | 語が違うため、方向だけで規則同士が衝突するとは言えない。不採用理由は材料・利得の小ささと、主要な不満に届かないこと |

SenseVoice の `review.tsv` に残る `pending` を、すべて確認済みとも、すべて未確認とも扱わない。日本語の節の確認、英語・普通話の内容確認など、後の記録で確定した項目だけを採用理由に使う。残る読み味や表記の評価を埋めるため、再び本人に採点を依頼することはしない。

## 9. 今回到達する改善範囲

| 元の課題 | この提案で進めること | 残ること |
|---|---|---|
| ① 日本語精度 | 確認済みの節の脱落に改善例があるモデルへ移す。VADの小さな取りこぼし対策を採る | 一般的な精度向上率、短い相づち全体の非劣性、数字・固有名詞・読み味の全面改善は保証しない |
| ② 日本語中の英語 | 現行の文字混在崩れから、カタカナなどで読める出力になる例を得る | 英字表記の統一、発話間の表記安定、混在語の誤認識は未解決 |
| ③ 英語・中国語 | 自動判定で英語を英字、普通話を漢字として残す | あらゆる発音・環境での品質や、中国語全般の対応を保証しない |
| ④ 本人と他人の識別 | 今回は追加しない | 他人・テレビの声も処理され得る。多言語化しても本人識別にはならない |
| 電池・発熱 | 観測上のメモリ負荷が小さく、短時間処理で実時間を十分下回る候補を選ぶ | 画面OFFの電池持ち、長時間の熱・安定性は未測定 |

本番へ持っていく変更は **1.13.8への統一、SenseVoiceへの移行、threshold 0.35** に絞る。課題②の完全解決や長時間性能の保証を得るために、今回の調査を延長しない。
