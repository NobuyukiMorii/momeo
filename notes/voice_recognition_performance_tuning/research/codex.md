# momeo 音声認識の改善案 — 現行実装と最新技術の再調査

調査日: 2026-09-20  
コード確認対象: `f0c3ffe`。実際の依存解決は `sherpa_onnx 1.13.3`（`pubspec.yaml` の指定は `^1.13.2`）。  
調査範囲: リポジトリ、過去の調査資料、モデル開発元・ライブラリ開発元・API提供元の公式資料。モデル実行、実機計測、音声の外部送信は行っていない。

## 1. 提案の結論

**録音・VAD・バックグラウンド動作・メモUIは活かし、音声認識部分を交換できる形にする。その最初のオンデバイス候補を Qwen3-ASR-0.6B とする。** 日本語を最優先に比較し、改善しなければ多言語対応だけを理由に全面置換しない。

**端末外への送信を許容する場合は、発話区間だけを最新の専用ASR APIへ送る方式が、端末負荷を抑えながら課題①〜③を改善する有力な方向である。** 初回比較は GPT-Transcribe と Gemini 3.5 Transcribe。現段階で一方を「日本語で最も高精度」と断定できる共通のmomeo向け検証結果はない。

今回の重要な発見は、**Qwen3-ASRは別エンジンへの全面移行が必須ではなく、既に導入されているsherpa_onnxのDart APIから扱える**こと。APIの存在はローカルの1.13.3ソースでも確認した。必要なのはモデル配布と認識器設定の変更、処理待ちの管理であり、アプリをゼロから作り直す必要はない。ただし、対象端末でのネイティブ実行成功・速度・メモリ使用量は未確認。

推奨する検討順は次のとおり。

1. **日本語の失敗音声を同一条件で再生できる評価基盤を用意する。** 音の欠落、区切り、モデルの誤認識を分ける。
2. **現行モデルとQwen3-ASR-0.6Bを比較する。** 日本語精度を最優先に、日英混在と英語・中国語も評価。
3. **日本語特化の対抗としてReazonSpeech k2 v2、端末負荷の対抗としてSenseVoice Smallを比較する。** Qwenが重ければWhisper系も含めて絞り直す。
4. **送信を許容するなら専用ASR APIを品質比較に加える。** ローカルで十分なら採用しない。明確な差がある場合に任意の高精度モードを検討。
5. **話者照合は別機能として追加する。** 最初から「自分以外を削除」せず、本人／他者／不明のラベル付けから始める。

過去資料の「オフライン・プライバシー・低コスト」は引き続き有力な製品方針と解釈した。ただし、今回の依頼ではクラウド禁止とは指定されていないため、端末内完結案とクラウド案を両方提示する。クラウド採用自体は本書では決定しない。

## 2. 現在の実装ができること・できないこと

```text
record: 16kHz / mono / PCM16
    ↓
SttListeningPipeline: マイク入力・停止再開・録音監視
    ↓ PCMチャンク
SttAudioWorker: 専用isolate
    ├─ Silero VAD: 発話区間の検出
    └─ NeMo CTC: 各発話の文字起こし
    ↓ SttTranscribed(text, durationSec, elapsedMs)
ListeningNotifier: 新規メモ／追記
    ↓
Drift / SQLite: id・本文・作成日時
```

## 4. 4つの課題を分けて考える

| 優先 | 課題 | 主な対策 | それだけでは足りないもの |
|---|---|---|---|
| ① | 日本語精度 | 収音・区切りの診断、日本語で実測したモデル選択、専門用語のヒント | 新しいモデルという理由だけの置換、句読点の追加 |
| ② | 日本語中の英語 | 同一発話内の言語混在に強い認識器、用語・綴りのヒント | 発話全体を日本語か英語のどちらかへ振り分けるだけ |
| ③ | 英語・中国語 | 対応モデルの導入、自動言語判定と必要時の手動指定 | 日本語モデルのtokens差し替えだけ |
| ④ | 自分と他人の区別 | 本人の声を登録した話者照合、必要に応じて話者区間の分離 | VAD、単なるspeaker A/Bラベル、ASRモデル交換だけ |

②には「英語として発音された英単語」「日本語化した外来語」「サービス名・人名・略語」が混在する。例えば「Flutterでpush通知を実装する」を英字交じりで残したいのか、「フラッターでプッシュ通知を実装する」も正解とするのかを分ける。音響認識と表記の好みを混同すると改善効果を測れない。

③の中国語はまず普通話を対象にし、簡体字／繁体字の表示方針を別に定める。広東語などを含める場合は別の評価枠にする。

## 5. 案A: 現行構成を活かして改善する

### A1. モデル変更前に、収音と発話の境界を診断する

評価用ビルドでのみ、マイクのPCMとVADが切り出した音声を両方保存して同じ認識器に渡す。切り出し前には聞こえる単語が切り出し後に消えていれば、認識モデルだけを交換しても解決しない。

確認項目は、語頭・語尾、0.25秒未満の短い発声、30秒境界、停止時の末尾、Bluetooth等の入力経路、音割れ、小声、遠距離、生活音。現在の停止処理はVADをflushするが、512サンプル未満の変換バッファを別途投入していない。最大約32msの端数が残り得るため検証点とする。これを現状の精度問題の主因とは断定しない。

境界に問題があれば、前後余白やオーバーラップ、無音閾値を調整する。**提案上の探索値**として前後200〜500ms、無音0.8／1.5／2.0秒などを比較する。Sileroが既に保持する前後音声を確認し、重複余白を無条件に足さない。文字列の重複除去も必要になる。

音声強調・ノイズ除去は、雑音例に効果があるときだけ導入する。全音声へ強い処理をかけると、子音や固有名詞の手掛かりまで失う可能性がある。近接マイクや装着マイクも対照条件に含める。

### A2. 第一候補: Qwen3-ASR-0.6Bをsherpa_onnxで動かす

Qwen3-ASRは2026年1月公開の0.6B／1.7Bモデルで、日本語・英語・中国語を含む30言語と中国語方言に対応する。公式実装はTransformers／vLLMを提供する。[開発元リポジトリ](https://github.com/QwenLM/Qwen3-ASR)

sherpa側には0.6Bのint8モデルとVAD連携例があり、モデルはconv frontend・encoder・decoder・tokenizerで構成される。掲載された主要ONNXファイルの合計は約937MiBで、現在の約625MiBより大きい。実行時RAMはこのサイズとは別に計測する。[変換とモデル構成](https://k2-fsa.github.io/sherpa/onnx/qwen3-asr/export.html)、[利用例](https://k2-fsa.github.io/sherpa/onnx/qwen3-asr/pretrained.html)

**推奨理由は本調査の判断:** ①の改善を試しつつ②③も同じ認識器で扱える可能性があり、既存エンジンを再利用できる。小型の日本語専用モデルへ限定するより、今回の優先課題に対する探索範囲が広い。ただし日本語で現行モデルに勝つことも、日英混在の綴りを正しく残せることも未実証。

実装変更の範囲:

- `SttAudioWorker.spawn`の引数を単一model/tokensの前提から、モデル種別ごとの設定へ変更する。
- `_createRecognizer`に`OfflineQwen3AsrModelConfig`を使う分岐を設ける。
- `SttModelProvisioner`、取得スクリプト、iOS同梱、Android配布を複数ファイル構成へ対応させる。
- 出力トークン上限を音声長に合わせて検証する。導入済みDart APIの既定`maxNewTokens=128`をそのまま使うと、長い日本語発話の出力が途中で終わる可能性がある。
- 同APIの`hotwords`を専門用語のヒントとして比較する。従来のtransducer向け`hotwordsFile`とは別の設定で、効果と書式を実行時に検証する。

APIの確認元: ローカル`.pub-cache`内の`sherpa_onnx-1.13.3/lib/src/offline_recognizer.dart`。公開最新版にも同設定がある。[Dart API](https://pub.dev/documentation/sherpa_onnx/latest/sherpa_onnx/OfflineModelConfig-class.html)

最大の採用リスクは、常時録音中の推論待ち・発熱・メモリ。CPU上の他機種の公表速度をiPhone／Androidへ転用しない。Qwenを採用する場合はVADとASRの実行待ちを分離する設計を推奨する。

### A3. 対抗候補: 日本語を優先するReazonSpeech k2 v2

日本語向けZipformerモデルで、開発元は159Mパラメータと日本語ベンチマーク結果を公開している。sherpa-onnxの対応モデルにも含まれる。[Reazon開発元](https://research.reazon.jp/blog/2024-08-01-ReazonSpeech.html)、[sherpa対応モデル](https://github.com/k2-fsa/sherpa-onnx/blob/master/README.md)

①が最優先なので、**多言語ではないことだけで候補から落とさない**。現行より日本語の実用精度と端末負荷が良ければ、日本語モードとして採用する価値がある。一方、②③の全面解決には別の認識器が必要である。

transducerの対応構成では用語の優先認識を検討できる。ただし、現行NeMo CTCに`hotwordsFile`を足すだけで同じ効果が出るとは考えない。sherpaの従来型contextual biasingはtransducerと`modified_beam_search`を前提に説明されている。[hotwords仕様](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)

### A4. 軽量な多言語対抗: SenseVoice Small

日本語・英語・普通話・広東語・韓国語に対応し、sherpa向けint8モデルは掲載例で約228MiB。現行の録音→VAD→OfflineRecognizerという流れを維持しやすい。[モデル配布・利用例](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html)、[開発元](https://github.com/QwenAudio/SenseVoice)

**変更量・負荷を抑えた③の改善候補**として有力。ただし日本語専用の現行モデルより①が良くなる保証はなく、対応5言語という仕様も同一文内のコードスイッチング精度を保証しない。Qwenが遅すぎる場合や、低負荷の外国語モードとして比較する。

### A5. 現行モデルの微調整で見込める範囲

- int8対非量子化版で比較し、量子化による差が実際に大きい場合だけ高精度版を検討する。差のないままモデル容量を増やさない。
- TDTへの変更は日本語比較の一条件としてはよいが、前述の公表差から最優先の改善策にはしない。
- 表記辞書で「プッシュ通知→push通知」などの利用者指定の表記を整えることは可能。ただし元の英語が誤認識・欠落した場合には対応できない。
- スレッド数の変更は主に速度の施策であり、日本語知識や対応言語を増やすものではない。

## 6. 案B: 認識方式・実行場所を変える

### B1. Whisper系へ変更する

日本語優先の比較対象は`kotoba-whisper-v2.0`、日英をまとめて扱う候補は`kotoba-whisper-bilingual-v1.0`、中国語まで含める候補は多言語Whisper large-v3／large-v3-turboとする。

Kotoba bilingualは日英ASRと双方向翻訳向けに学習したモデルで、whisper.cpp向け重みへの導線がある。ただし日英それぞれのASR学習から、日英混在が必ず得意とは言えない。利用時は翻訳ではなく転写タスクを選ぶ。[Kotobaモデルカード](https://huggingface.co/kotoba-tech/kotoba-whisper-bilingual-v1.0)

実行候補は両OSで`whisper.cpp`、iOS最適化を重視する場合はWhisperKit。whisper.cppにはiOS／Android対応や量子化、Core ML等の実装がある。WhisperKitを含むArgmaxのOSS Swift SDKと、Android対応を含むPro SDKは別の提供範囲なので区別する。[whisper.cpp](https://github.com/ggml-org/whisper.cpp)、[Argmax SDK](https://github.com/argmaxinc/argmax-oss-swift)

Whisper導入は録音の全面再実装ではなく、ASRバックエンドの交換でよい。独自のマイク取得機能は使わず、既存recordから得たPCMを渡す。日本語精度が改善する場合に採用し、tiny/baseへ小さくすることを無条件の解決としない。無音時の架空の発話、繰り返し、勝手な翻訳も評価する。

### B2. 専用ASR APIへ発話単位で送る

理論上の利点は、スマートフォンのRAM・発熱に認識モデルの規模を縛られにくく、用語や言語混在に対応したAPIを選べること。欠点は音声送信、ネット接続、費用、障害時の扱いである。

| 候補 | 公式資料で確認した特徴 | momeoでの位置づけ |
|---|---|---|
| **GPT-Transcribe** | 文脈・keywords・複数言語ヒント、コードスイッチング向け機能 | ①②③の最初の比較候補。古いWhisper APIを代表候補に固定しない |
| **Gemini 3.5 Transcribe** | 自動言語認識、混在言語、用語指定、話者ラベル | ①②③の対抗。用語指定と話者分離／単語時刻は併用不可 |
| **MAI-Transcribe-2** | 日英中を含む多言語、用語ヒント、話者分離 | 追加比較候補。Azure Speech経路は調査時点でpublic preview |
| **Scribe v2** | 日英中を含む90以上の言語を掲げる専用ASR | 上位候補が期待に届かない場合の対抗 |
| **Deepgram Nova-3** | 日英を含む多言語モード、中国語単言語対応 | 言語別対応と`multi`対象を分けて確認する |
| **Google Chirp 3** | Speech-to-Text V2の多言語認識、適応機能 | 既存Cloud基盤との統合重視の場合。Gemini転写APIとは別サービス |

出典: [GPTモデル仕様](https://developers.openai.com/api/docs/models/gpt-transcribe)、[GPT転写ガイド](https://developers.openai.com/api/docs/guides/speech-to-text)、[Gemini転写仕様](https://ai.google.dev/gemini-api/docs/transcribe)、[MAI仕様](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/mai-transcribe)、[Scribe仕様](https://elevenlabs.io/docs/overview/capabilities/speech-to-text)、[Deepgram言語一覧](https://developers.deepgram.com/docs/models-languages-overview)、[Chirp 3](https://docs.cloud.google.com/speech-to-text/docs/models/chirp-3)。

**最初はGPT-TranscribeとGeminiの2つに絞る。** 理由は今回必要な用語・言語混在の設定が明示されていることと、発話単位のAPI比較がしやすいこと。公表広告の「最高精度」を根拠に順位を決めたわけではない。比較時は逐語転写を使い、整文・要約で誤りを隠さない。

費用の一例: GPT-Transcribeの掲載価格は音声1分あたりUS$0.0045。これを単純適用すると、送信音声が1日60分なら30日で約US$8.10、1日8時間を全送信すると約US$64.80。これは利用者1人分のASRのみの概算で、通信・中継サーバー・税・重複再試行等を含まない。VADで無音を除いても、周囲の人やTVの音声は送信対象になり得る。[価格の出典](https://developers.openai.com/api/docs/models/gpt-transcribe)

製品へ導入するなら、送信モードを明示して選択可能にする。API鍵はアプリへ埋め込まず中継サーバーで管理する。音声の一時保持期限・再試行回数・削除・提供先でのデータ取扱いを設計する。オフライン時はローカル認識へ切り替えるか、明示された保留状態にする。「失敗したら無断でクラウドへ送る」構成にはしない。

### B3. 自前サーバー／PCで大きい公開モデルを動かす

Qwen3-ASR-1.7B、Fun-ASR-Nano、Cohere Transcribeを比較対象にできる。Fun-ASR-Nanoは日英中に対応する800Mモデルで、sherpa用の配布もある。Cohereは日英中を含む14言語の2Bモデル。スマホ実装の前に、同じ音声に対する認識品質をPC／GPU環境で比較できる。[Fun-ASRモデル](https://huggingface.co/FunAudioLLM/Fun-ASR-Nano-2512)、[sherpa配布](https://k2-fsa.github.io/sherpa/onnx/funasr-nano/pretrained.html)、[Cohere仕様](https://docs.cohere.com/docs/transcribe)

自前運用は音声の提供先を管理できる反面、端末内完結ではなく、サーバー費用・監視・更新が必要になる。個人開発の最初の本番方式には、品質上の明確な利点がない限り推奨しない。

### B4. 最新の追跡候補と、今回の採用を急がない理由

| 候補 | 確認できたこと | 今回の判断 |
|---|---|---|
| Qwen-Audio-3.0-ASR | 2026年9月の技術報告とAPI導線。長い文脈や用語ヒントを扱う新系列 | Qwen3-ASR-0.6Bの公開ONNXと混同しない。API比較の次候補。スマホへのそのままの置換可否は未確認 |
| Nemotron 3.5 ASR Streaming 0.6B | 日本語・英語、中国語にも対応。sherpaに変換・ストリーミング例がある | 低遅延表示が必要になった場合の候補。現在の優先課題①に対する優位は未実測 |

出典: [Qwen新系列](https://qwenaudio.github.io/qwen-audio-3.0-asr/)、[2026年9月の論文](https://arxiv.org/abs/2609.07549)、[Nemotronモデルカード](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b)、[sherpaでの利用](https://k2-fsa.github.io/sherpa/onnx/nemo/nemotron-streaming.html)、[Apple公式解説](https://developer.apple.com/videos/play/wwdc2025/277/)、[SpeechTranscriber対応確認API](https://developer.apple.com/documentation/speech/speechtranscriber)。

最新モデルを追うことと、全候補をアプリへ実装することは分ける。まず少数の候補を同じ評価セットで比較し、良いものだけ端末実装へ進める。

## 7. 課題④: 「自分の声」の判定を追加する

### 3つの技術の違い

- **話者分離（diarization）:** 誰がいつ話したかをspeaker A/Bなどの区間に分ける。Aが端末所有者とは限らない。
- **話者照合（verification）:** 登録した本人の声と、今の発話が同じ話者か比較する。momeoの「自分だけ」に直接必要なのはこちら。
- **音源分離／対象話者抽出:** 同時に重なった声から目的の音声を取り出す。区間ラベルや照合だけでは実現できない。

### 小さく始める実装案

既存のsherpa_onnxには`SpeakerEmbeddingExtractor`と`SpeakerEmbeddingManager`があり、1.13.3のローカルソースでも確認した。別途話者特徴抽出モデルと本人の登録UI・保存処理が必要になる。[sherpa話者識別](https://k2-fsa.github.io/sherpa/onnx/speaker-identification/index.html)

```text
本人の登録音声 → 話者特徴を抽出 → 本人の参照特徴として端末保存

発話音声 → 特徴抽出 → 本人との類似度
                         ├─ 本人らしい
                         ├─ 他者らしい
                         └─ 不明・短すぎる・複数話者が混在
```

初期の登録条件は、例えば静かな環境で合計20〜30秒を複数発話に分けて収録する案から試す。これは本書の実験案で、モデルの保証条件ではない。普段の距離やマイク経路でも評価し、閾値を決める。

**最初はラベルを付けるだけにする。** いきなり本人判定をASRの前段で強制すると、本人の小声・短い相づち・外国語発話が捨てられ、①の体感が悪化する。本人発話を捨てる割合と他人を通す割合を測ってから、自分だけ表示する機能を追加する。「不明」は保持して見直せるようにする。

VADの1区間に複数人が入る場合は、その区間全体のembeddingだけでは足りない。話者区間分割を先に行い、区間ごとに本人照合する必要がある。pyannote Community-1はローカル実行可能な話者分離の比較候補だが、そのままFlutterへ組み込む手軽な置換ではない。[pyannoteモデルカード](https://huggingface.co/pyannote/speaker-diarization-community-1)

クラウドでは`gpt-4o-transcribe-diarize`が参照音声を与えた話者ラベル付けに対応する。通常の高精度転写モデルとは別で、prompt非対応など機能差があるため、④の追加が①②の精度を下げないか別評価する。[OpenAI話者分離仕様](https://developers.openai.com/api/docs/guides/speech-to-text)

重なった会話、TVから流れる本人の録音、極端な小声等まで完全に排除できるものとは扱わない。話者特徴は個人データとして端末内で管理し、登録解除で削除できる形にする。

## 8. 推奨する実装境界

### 共通の音声区間を作り、認識器を交換する

```text
録音 → 軽量VAD処理 → ID・実際の開始終了位置を持つ音声区間 → 上限付きキュー
                                                          ↓
                                  交換可能なASR（ローカル／任意のAPI）
                                                          ↓
                              区間ID付き結果 → 順序整理・保存 → メモ表示
```

現行では音声処理isolateがVADと同期推論を兼ねる。新しい生成型ASRで推論時間が増える場合は、VAD用とASR用のworkerを分ける。キューの最大音声秒数・待ち時間・過負荷時の動作を定義し、無制限にメモリへ溜めない。黙って音声を捨てず、遅延や停止を通知する。

結果には`segmentId`、音声サンプル由来の開始終了時刻、モデルIDを付ける。現行の発話開始時刻は通知受信時の`DateTime.now()`なので、推論待ちが増えるほど実際の発話時刻とずれやすい。

認識結果を保存する処理も順序を保証する。現行`onTranscribed`は非同期DB処理を呼ぶが呼び出し側で完了を待たない。後続結果がまとまって届く構成へ変える際には、新規作成／追記の競合を検証し、区間IDと保存キューで二重保存・追記欠落を防ぐ。

モデルを2つ同時に常駐させる設計は初期案にしない。RAMと発熱が増えるため、モード切替や単一認識器の選択を基本とする。信頼度が低いときだけ再認識する仕組みは、モデル間で比較可能な信頼度の校正と音声の一時保持が必要な後続案である。

## 9. 評価計画と採用条件

以下は実績値ではなく、次の検証で使う提案である。今回の作業では音声収集やモデル実行をしていない。

### 第1段階: ①を軸にした共通の評価音声

最初は合計100〜200発話程度。本人の実際の失敗例を中心に、自然な独り言・言い直し・短文・長文を含める。TTS音声だけで評価しない。

| 区分 | 比重の目安 | 見ること |
|---|---:|---|
| 日本語のみ | 50% | 日常メモ、否定、数字、日時、人名、技術用語 |
| 日本語＋英語 | 25% | 英語の脱落、カタカナ化、綴り、略語、勝手な翻訳 |
| 英語／普通話 | 15% | 言語別の精度、言語自動判定、短い発話 |
| 話者・雑音・無音 | 10% | 他者、TV、重なり、小声、架空の発話 |

調整用と最終判定用の音声を分ける。全モデルに同じPCMを入力する「モデル比較」と、各方式のVAD・録音・送信を含む「アプリ全体比較」を別に行う。

### 第2段階: 比較候補を絞る

最初の組み合わせは、現行NeMo CTC int8、Qwen3-ASR-0.6B、ReazonSpeech k2 v2、SenseVoice Small。端末外処理を許容する評価ではGPT-TranscribeとGemini 3.5 Transcribeを加える。

日本語改善が足りないときだけKotoba／Whisper、Qwen1.7B、Cohere等を追加する。最初から全候補をモバイルへ移植しない。PCでの品質比較に勝った候補を実機へ進める。

### 第3段階: 指標と判定

| 指標 | 判定方法 |
|---|---|
| 日本語・中国語CER | 文字の誤り率。表記正規化の規則を固定する |
| 英語WER | 単語の誤り率。日本語CERと同列の数字として直接順位付けしない |
| 日英混在 | 日本語部分CER＋英語部分WER＋指定用語の完全一致率 |
| 意味の重大誤り | 否定・数値・日付・人名・固有名詞の誤りを別集計 |
| 幻覚・欠落 | 無音に出した文字、言っていない内容、途中で切れた出力 |
| 操作上の速さ | 発話終了から画面確定までのp50/p95。VAD待ちと通信を含める |
| 推論速度 | RTF＝推論時間／音声時間。連続発話では1未満が必要、余裕も必要 |
| 継続性 | 30〜60分で待ち行列が増え続けないか。バックグラウンドでも確認 |
| 資源 | ピークRAM、電池消費、発熱、モデル準備時間・容量 |
| 話者 | 本人を誤って落とす率、他者を本人とする率、不明率 |

初期の採用目安として、**日本語CERの相対20%以上改善、または重要語・重大誤りの明確な改善**を求める。同時に日本語の一部条件で大幅に悪化していないことを確認する。この20%は提案値であり、期待性能の予測ではない。少数音声の差だけで決定せず、未使用の評価音声で再確認する。

②③が改善しても①が悪化するモデルは標準にせず、多言語用の選択肢に留める。④は①〜③と別に合否を出し、話者機能のために完成を遅らせない。

## 10. 最終的な選び方

| 条件 | 選ぶ方向 |
|---|---|
| オフラインを維持し、今の構成で改善したい | **Qwen3-ASR-0.6Bを最初に評価**。日本語対抗にReazonSpeech、軽量対抗にSenseVoice |
| 日本語だけでも確実な改善を優先したい | 日本語評価に勝ったモデルを採用。英中を理由に日本語の退行を許さない |
| 端末負荷が厳しいが外部送信は避けたい | 軽量候補またはOS別最適化。大型モデルへの変更を撤回できる構造にする |
| 通信・費用を許容して品質改善を最大化したい | **ローカル録音＋VAD＋最新専用ASR API**。GPTとGeminiを最初に比較 |
| 自分の声だけをメモにしたい | 選定したASRに、登録式のローカル話者照合を追加 |

**現時点での第一手は、録音基盤の全面刷新でもLLM整文の追加でもなく、同じ音声を使ったQwen3-ASR-0.6Bへの置換評価である。** 日本語精度が十分改善し、端末が継続処理できれば、そのまま既存基盤へ組み込む。満たせなければ、Whisper系・日本語特化・クラウド型へ判断を分岐させる。この順番なら①を最優先に保ちつつ、②③への道も開け、④を独立して追加できる。
