# 音声認識の課題に対する技術方針の提案

## この文書について

- **目的**: 現在感じている音声認識の4つの課題について、「今の実装を基盤とした改善」と「根本からの方式変更」の両面から、理論上もっとも有効と考えられる方向性を提案する。
- **調査日**: 2026-09-20
- **扱う課題**（優先度の高い順）:
  1. 日本語の認識精度に満足できない
  2. 日本語に混ざる英語をテキスト化できない
  3. 外国語（特に英語・中国語）に対応できない
  4. 他人の声と自分の声を識別できない
- **前提**: `notes/on_device_stt/outline.md` の採用経緯と、`notes/research/on_device_stt/vad_whisper_impl_log.md` の実機比較結果を踏まえる。momeo の性格（常時リスニング・オンデバイス・個人開発）は変えない。
- **位置づけ**: 実際に効くかは実機で測らないと分からない。本書は**どの方向に賭けるか**と**何を測れば判断できるか**を示すもので、実装計画ではない。

---

## TL;DR（結論）

**いま何が変わるか**: 課題2と3は「今のモデルでは原理的に解けない」ことが確定した。課題1と4は、モデルを替えなくても積み増せる余地が大きい。

- **課題2（英語が混ざると書けない）は、実装の問題ではなくモデルの語彙の問題**。現行モデルの語彙 3,073 語のうち、ラテン文字を含むのは小文字 a〜z の26個だけで、大文字も英単語の断片も1つも持たない。英語は1文字ずつ綴る以外に出力しようがない。**モデルを替える以外に解決手段はない**。
- **課題3（多言語）も同じ理由**で、モデル差し替えが唯一の道。課題2と3は**同じ1回の差し替えで同時に解ける**。
- **課題4（話者の識別）は、認識モデルと無関係に追加できる**。sherpa-onnx が話者埋め込み（声の特徴ベクトル）の抽出器を持ち、Dart API も揃っている。追加モデルは約27MB で、自分の声を登録して照合するだけ。**4つの中でいちばん確実に解ける**。
- **課題1（日本語の精度）が最も厄介**。モデルを替えれば上がるとは限らない（現行は日本語35,000時間に特化した専用モデルで、多言語モデルに替えると日本語だけは落ちる可能性がある）。効くのは**認識の後ろに補正の層を足すこと**で、これは過去の調査（`speech_recognition_accuracy.md`）で挙げた LLM 後処理そのものである。
- **本命の方向**: **二段階認識**。速いモデルで即座にカードを出し、裏でゆっくり高精度のモデルと LLM にかけ直して本文を静かに差し替える。momeo のメモは既に「後から書き足して更新する」設計なので、**この構造は今のコードにそのまま乗る**。速度と精度のどちらかを捨てる、というこれまでモデル選定を縛ってきた制約そのものを外せる。

## 1. 課題の原因

### 1-1. 課題2・3 は「モデルの語彙」で決まっている（確認済み）

現行モデル `sherpa-onnx-nemo-parakeet-tdt_ctc-0.6b-ja-35000-int8` の `tokens.txt` を直接調べた。

| 項目 | 実際の値 |
|---|---|
| 語彙の総数 | 3,073 |
| ラテン文字を含むトークン | 26（小文字 a〜z のみ） |
| 大文字を含むトークン | 0 |
| 英単語の断片（the, ing など） | 0 |

つまりこのモデルは、**英語を「単語」として出力する手段を持っていない**。運がよくても `deep learning` が `d i p l a n i n g` のような綴りになるだけで、実際には日本語のカタカナか無音として捨てられる。中国語の漢字も、日本語の常用字と重なる範囲しか持たない。

> ここが重要な点で、**プロンプトの工夫や設定変更では絶対に直らない**。モデルが持っていない文字は、どう頼んでも出てこない。

### 1-2. 課題1 は3つの要因に分解できる

日本語の精度は「モデルの地力」だけの話ではない。切り分けると次の3つになり、**それぞれ別の打ち手がある**。

| 要因 | いま起きていること | 打ち手の置き場所 |
|---|---|---|
| 入力の質 | 雑音・遠い声・VAD が発話の頭を削る | 認識の**前** |
| モデルの地力 | int8 量子化・貪欲探索（もっとも確からしい1手だけを選ぶ探索）・文脈は1発話ぶんだけ | 認識**そのもの** |
| 固有名詞と文脈 | 人名・社名・専門用語・同音異義語を外す | 認識の**後** |

現行の実装は、前も後ろも**何も置いていない**。認識器の生出力をそのままメモにしている。逆に言えば、モデルを触らずに積める余地がまだ二層ぶん残っている。

### 1-3. 課題4 は未着手なだけで、難所ではない

声の主を見分ける技術（話者認識）は ASR とは独立した部品として成熟している。momeo は VAD が1発話ずつ音声を切り出しているので、**その1発話ぶんの波形をそのまま話者判定にも渡せる**。切り出しが済んでいることが、そのまま有利に働く。

## 2. 現状の構成（どこを差し替えられるか）

```text
record（マイク）
  ↓ PCM16 / 16kHz / モノラル
音声 isolate
  ├ Silero VAD で発話を切り出す         ← ここは触らない
  └ NeMo CTC で1発話を一括変換           ← ★差し替え対象（1ファイル・1箇所）
  ↓ 確定テキスト
ListeningNotifier → DB → カード表示      ← 更新の仕組みは既にある
```

差し替えに必要な変更は実質2箇所しかない。

| 箇所 | いま | 差し替えで起きること |
|---|---|---|
| [stt_audio_worker.dart:367](../lib/stt/stt_audio_worker.dart:367) `_createRecognizer` | `nemoCtc:` に固定 | 設定クラスを別のものに差し替える |
| [stt_model_provisioner.dart](../lib/stt/stt_model_provisioner.dart) | NeMo 2ファイルの名前とバイト数 | 新しいモデルの名前とバイト数に直す |

Flutter パッケージ `sherpa_onnx` は 1.13.3 が入っており、後述する候補モデルの設定クラス（`senseVoice` / `funasrNano` / `qwen3Asr` / `transducer` / `dolphin` / `canary`）は**すべてこのバージョンで既に使える**。パッケージの乗り換えは不要。

また dev カタログに STT の検証セクション（エンジン・モデル・VAD・転写）が既にあるため、**候補モデルを並べて自分の声で比べる土台も揃っている**。過去に Whisper・Zipformer・Vosk・NeMo を同じ場所で比べた実績がそのまま使える。

## 3. 調査した選択肢

### 3-1. 認識モデル（sherpa-onnx が今すぐ使えるもの）

サイズは sherpa-onnx の配布物（int8 の圧縮済み）。**すべて現行のパイプラインにそのまま載る**。

| モデル | サイズ | 対応言語 | 方式 | 句読点 | 用語指定 | 課題1 | 課題2・3 |
|---|---|---|---|---|---|---|---|
| **現行** NeMo parakeet ja | 466MB | 日本語のみ | CTC | あり | 不可 | 基準 | **不可** |
| **Fun-ASR-Nano**（SenseVoice 形式）2025-12 | **178MB**（展開252MB） | 31言語（東アジア重点） | 非自己回帰 | 要確認 | 不可 | 未知 | 可 |
| SenseVoice 2024-07 | 155MB | 中英日韓粤 | 非自己回帰 | ITN 有効時 | 不可 | 未知 | 可 |
| SenseVoice 2025-09 | 158MB | 中英日韓粤 | 非自己回帰 | **なし** | 不可 | 未知 | 可 |
| **Nemotron 3.5 ASR streaming 0.6B** 2026-06 | 453MB | **40ロケール**（日中英含む） | 逐次型 transducer | あり | **可** | 未知 | 可 |
| **Qwen3-ASR 0.6B** 2026-03 | 837MB | 30言語 | LLM（音声→Qwen3） | あり | **可** | 高い見込み | 可 |
| Dolphin small / base | 182 / 76MB | 東アジア多言語 | CTC | 要確認 | 不可 | 未知 | 可 |
| Moonshine base-ja 2026-02 | 99MB | 日本語のみ | encoder-decoder | 要確認 | 不可 | 未知 | 不可 |
| FireRedASR large | 1,401MB | 中英 | | | | | 端末には重い |
| Cohere Transcribe | 1,621MB | 14言語 | | | | | 端末には重い |

補足として重要な3点。

- **用語指定（hotwords、話しそうな語をあらかじめ渡して認識を寄せる仕組み）は transducer 型と Qwen3-ASR でしか使えない**。現行の CTC 型では原理的に使えない。課題1の「固有名詞を外す」に効く唯一の直接手段であり、**これが使えるモデルに移ることそのものが課題1への打ち手になる**。
- **Nemotron 3.5 は現行と同じ FastConformer 系**。速度の読みが立ちやすく、句読点も内蔵する。ただし逐次型（話しながら出す型）なので、**発話全体を見てから決める現行より日本語が落ちる可能性がある**（過去調査 `speech_recognition_accuracy.md` の「要因A」と同じ理屈）。公称の日本語 CER は 11.48%（1.12秒チャンク時）。
- **Qwen3-ASR は音声エンコーダに Qwen3 の言語モデルを直結した構造**で、文脈で言い直せるぶん精度と多言語混在に強い。反面、デコーダ本体が 721MB あり、Apple Silicon の Mac でも RTF（音声長に対する処理時間の比）が約 0.7。**スマートフォンでは 1 を超える（＝実時間より遅い）可能性が高い**。

> 数値の扱いに注意。各モデルの CER は**それぞれ別のテストセット**で測られたもので、横並びに比較できない。現行モデルの学習元である ReazonSpeech は自前テストで CER 9.3% を出しているが、Nemotron の 11.48% と直接は比べられない。**判断は自分の声・自分の環境での実測でしかできない**。

### 3-2. 話者の識別（課題4）

sherpa-onnx は ASR とは別に、話者の声を特徴ベクトル（声紋）に変換する部品を持つ。Dart API も揃っている。

| 部品 | 使うもの | サイズ |
|---|---|---|
| 声紋の抽出 | `SpeakerEmbeddingExtractor` | 22〜68MB（例: 3D-Speaker CAM++ 中英共用 26.9MB） |
| 登録と照合 | `SpeakerEmbeddingManager`（`add` / `search` / `verify`、しきい値つき） | モデル不要 |
| 何人いるかの自動分離 | `OfflineSpeakerDiarization` ＋ pyannote 分割モデル | 追加 6.6MB |

momeo に必要なのは前2つだけで足りる。

```text
初回設定: 自分の声を数回読み上げて登録   →  声紋を保存
        ↓
通常利用: VAD が切り出した1発話 → 声紋を作る → 登録済みの声紋と照合
        ↓
        しきい値を超えた   → 自分の発話
        超えなかった       → 他人の発話
```

短い発話（2〜3秒）での誤り率は、この系統の新しいモデルで 1〜2% 程度が報告されている。**momeo の1発話は多くが2秒以上**なので、条件は悪くない。

この結果の使い道は3通りあり、どれも同じ仕組みの上で選べる。

- 他人の発話はメモにしない（自分のメモだけを残す。第三者の発話を保存しないので、プライバシー上も筋が通る）
- 他人の発話にも印を付けて残す（会話の記録として使える）
- カードを「自分」「相手」で分けて表示する

### 3-3. 認識の後ろに置く補正（課題1の本命）

過去調査（`speech_recognition_accuracy.md`）で「最大のレバー」と結論づけた層で、**まだ実装していない**。研究では ASR 出力を LLM で直すと文字誤り率が 9〜21% 減ると報告されている。

| 手段 | 実行場所 | 状況 |
|---|---|---|
| iOS 26 Foundation Models（約3B のオンデバイス LLM） | 端末内 | 整文が公式用途。Apple Intelligence 対応端末のみ |
| Android ML Kit GenAI（Gemini Nano） | 端末内 | 校正が公式機能。対応端末が限られる |
| `flutter_gemma`（Gemma 3n ほか） | 端末内 | Flutter から直接。端末を選ばない代わりにモデルを自前で配る |
| 同音異義語の置換（sherpa-onnx `HomophoneReplacer`） | 端末内 | LLM 不要。辞書と置換規則で機械的に直す。**どのモデルにも後付けできる** |

**この層の価値は課題1にとどまらない**。多言語モデルへ差し替えて日本語が少し落ちたとしても、**この層が吸収できる**。つまり差し替えの副作用に対する保険にもなる。

### 3-4. 認識の前に置く処理（全課題に効く）

- **雑音抑制**: sherpa-onnx に DPDFNet 系の雑音抑制モデルがあり、`dpdfnet2 / 4 / 8` は 16kHz の ASR 前段向けと明記されている。遠い声・空調・カフェで効く。
- **マイク設定の見直し**: 現行は `mixWithOthers` と `defaultToSpeaker` を付けている。音を混ぜられる自由度と引き換えに、OS の音声処理が期待どおりに効いていない可能性がある。録音の素性を測る価値はある。
- **VAD の取りこぼし**: Silero VAD のしきい値は既定のままで、発話の頭が削れているかを測っていない。頭が欠けると先頭の単語をまるごと落とすため、**精度の見かけ上の低さがここから来ている可能性**がある。

### 3-5. クラウドを併用する道

オンデバイス一本を崩す選択だが、**選べるようにしておく**価値はある。

| サービス | 料金 | 備考 |
|---|---|---|
| Qwen3-ASR-Flash | 約 $0.126/時 | 端末版と同系統。多言語・用語指定に対応 |
| ElevenLabs Scribe | 約 $0.22/時 | 用語指定は追加料金 |
| Gemini 系の音声入力 | トークン課金 | 1時間あたり数セント規模 |

momeo の「常に聞いている」性格と正面からぶつかるため、既定で使う道はない。**「この1件だけ、もっと正確に読み直す」という明示操作に限る**なら、コストもプライバシーも利用者が握れる。

## 4. 提案A — 今の実装を基盤として変える

今の骨格（録音 → VAD → 一括変換 → カード）をそのまま残し、**部品を差し替える・足す**だけで届く範囲。

### A-1. 多言語1モデルへの差し替え（課題2・3）

差し替え候補は3つ。**どれも1モデルで日本語・英語・中国語をまかなう**ので、課題2と3が同時に消える。

| 候補 | 狙い | 差し替えで得るもの | 引き換えに失うかもしれないもの |
|---|---|---|---|
| **Fun-ASR-Nano**（178MB） | 軽さと多言語の両取り | 端末上で 625MB → **252MB**。配布の作り（Android の後追いダウンロード・準備待ち画面）を畳める見込み | 日本語の地力。専用モデルより落ちる見込み |
| **Nemotron 3.5**（453MB） | 現行の延長線で多言語化 | 用語指定が使えるようになる。句読点内蔵。将来「話しながら出す」表示も選べる | 逐次型ゆえの精度低下。日本語で要実測 |
| **Qwen3-ASR**（837MB） | 精度と文脈理解を最優先 | 文脈で言い直せる。用語指定も可 | 速度。スマートフォンでは実時間より遅い恐れ |

> サイズの副作用が大きい点を見落とさないこと。Android で後追いダウンロード（fast-follow）を選んだのは、625MB では install-time 配信にするとディスクを約1.25GB使うためだった。252MB なら同じ計算で約500MB に収まり、**install-time 配信（アプリと一緒に届く方式）が現実的な選択肢に戻る**。そうなればダウンロード待ちが消え、準備ゲートの待ち画面と fast-follow の橋渡しごと畳める。課題の解決と同時に、いちばん複雑な箇所が軽くなる。

### A-2. 話者識別の追加（課題4）

認識モデルとは独立に足せるため、**A-1 の結論を待たずに着手できる**。必要なのは約27MBの声紋モデル1つと、自分の声を登録する画面1つ。

### A-3. 補正の層を足す（課題1）

- **用語辞書**: A-1 で Nemotron か Qwen3-ASR を選べば、用語指定がそのまま使える。自分がよく話す固有名詞を登録できる画面を持てば、体感の精度はここで大きく変わる。
- **LLM 整文**: 確定テキストを端末内 LLM に通して直す。対応端末が限られるため、非対応端末では素通りさせる前提で組む。
- **同音異義語の置換**: LLM を使わない軽い代替。辞書で機械的に直すだけなので、全端末で効く。

### A-4. 入力の質を上げる（全課題）

雑音抑制の前段追加、マイク設定の見直し、VAD のしきい値調整。**いずれもモデルを替えずに測れる**ので、A-1 の比較を始める前にやっておくと、比較そのものの信頼性が上がる。

## 5. 提案B — 根本から方式を変える

### B-1. 二段階認識（本命）

**いま何が変わるか**: 「速いか、正確か」を選ぶのをやめる。

これまでの全ての判断（Whisper を捨てた・Vosk を捨てた・NeMo を選んだ）は、**1回の認識で速度と精度を同時に満たす必要があった**ことに縛られていた。その制約は、momeo が「メモアプリ」であることを使えば外せる。

```text
① 話し終える
   ↓ 速いモデルで即座に変換（現行と同じ 100〜300ms）
② カードが出る                         ← 体験はいまと同じ
   ↓ 裏で、同じ音声を重いモデル・LLM にかけ直す（数秒かかってよい）
③ カードの本文が静かに差し替わる        ← 精度はいまより上
```

この構造が momeo に合う理由が3つある。

- **メモは後から変わってよい**。通話や字幕と違い、確定した瞬間に完成している必要がない。
- **カードを書き換える仕組みが既にある**。同じカードに次の発話を追記していく機能（`_appendToTarget`）があり、DB も本文の更新に対応済み。**新しい仕組みを足す必要がない**。
- **重い処理を逃がす場所も既にある**。音声 isolate を常駐させる構造が完成しているので、二段目をそこに載せるか、もう1つ isolate を増やすかの選択だけで済む。

二段目に置けるものは段階的に選べる。

| 二段目の中身 | 得られるもの | 重さ |
|---|---|---|
| LLM による整文・誤り訂正のみ | 課題1 | 軽い〜中 |
| Qwen3-ASR で認識し直す | 課題1・2・3 を最高精度で | 重い（数秒） |
| クラウドへ送る（明示操作のみ） | 上限の精度 | 通信とプライバシーの判断が要る |

一段目は現行の NeMo のままでもよいし、A-1 で多言語モデルに替えてもよい。**二段構えにすること自体が、一段目の選択を気楽にする**。一段目は「速くてそこそこ」でよくなるので、Fun-ASR-Nano（178MB）のような軽いモデルを選びやすくなる。

懸念は2つあり、どちらも設計で抑えられる。

- **書き換えが目障りにならないか**: 直前の1件だけ・画面に見えている間だけ・差分が大きいときだけ、など条件を絞れる。
- **電池と発熱**: 二段目を「充電中のみ」「まとめて後で」に寄せる選択ができる。常時リスニングのアプリなので、ここは慎重に測る。

### B-2. LLM型 ASR に一本化する

Qwen3-ASR だけで全部やる。課題1〜3 を1モデルで最もきれいに解ける代わりに、**速度とメモリが最大の賭けになる**。約940MB を常駐させることになり、バックグラウンド録音中に OS から落とされる危険も上がる。**単独では推さないが、B-1 の二段目としてなら価値が高い**。

### B-3. 逐次表示型に乗り換える

Nemotron 3.5 の逐次型を使い、話しながら文字が出る体験にする。Vosk で一度見て「精度が低すぎる」と捨てた道だが、**今回の候補は精度帯がまったく違う**。ただし momeo のアクティブカードは「文字を出さず気配だけ伝える」設計に固めた経緯があり、**採用すると画面設計の前提が変わる**。課題1〜4 のどれも直接は解かないため、優先度は低い。

### B-4. OS の音声認識に戻る

iOS 26 の SpeechAnalyzer は日本語を含む約40ロケールに対応し、英語では Whisper Small を上回るという報告がある。OS の進化に乗れる利点は大きいが、**Flutter から使える成熟したパッケージがまだ無く**、Android 側に同等物も無い。両OSで別々の仕組みを抱えることになり、課題4 も解けない。**いまは見送り、iOS 側の選択肢として覚えておく**のが妥当。

### B-5. 録音を残して後から何度でも読み直す

いまは音声を文字にしたら捨てている。**音声を保持すれば、モデルを乗り換えるたびに過去のメモを作り直せる**。B-1 の二段目も、失敗しても何度でもやり直せるようになる。引き換えに保存容量とプライバシーの設計が要る（16kHz モノラルで1時間あたり約115MB。圧縮すれば1割程度）。**B-1 を選ぶなら、直近ぶんだけ一時的に残す形は検討に値する**。

## 6. 推奨する道筋

優先度（1 → 2 → 3 → 4）と、確実さ・手戻りの少なさを重ねると、次の順になる。

```text
第0段: 比較の土台を作る
        dev カタログに候補モデルを並べ、自分の声・自分の環境で測れるようにする
        （過去に Whisper / Zipformer / Vosk / NeMo を比べた仕組みをそのまま使う）
        ↓
第1段: 話者識別を足す                         → 課題4 が解ける
        認識モデルの結論を待たずに進められる。27MB・独立・確実
        ↓
第2段: 多言語1モデルへ差し替える              → 課題2・3 が解ける
        第0段の実測で Fun-ASR-Nano / Nemotron / Qwen3-ASR から選ぶ
        ↓
第3段: 補正の層を足す                         → 課題1 が上がる
        用語辞書 → 同音異義語の置換 → LLM 整文 の順に軽いものから
        ↓
第4段: 二段階認識にする                       → 課題1 の上限を外す
        一段目は速いまま、二段目で精度を取りに行く
```

**なぜこの順番か**。

- 課題4 を先に置くのは、優先度が低いからではなく、**他のどの判断にも影響されない唯一の課題**だから。ここで1つ確実に前進する。
- 課題2・3 は差し替え1回で同時に解ける。ただし**日本語が落ちないことを確認してからでないと踏めない**ので、第0段の実測が前提になる。
- 課題1 を最後に回すのは、**最優先だが単発の打ち手では上がらない**ため。第2段でモデルが変われば土台も変わるので、補正の層はその上に積むほうが無駄がない。
- 第0段を飛ばさないこと。今回の調査で分かったとおり、**公称の精度数値は横並びに比較できない**。自分の声で測る以外に決め手はない。

**いちばん筋が良いと考える組み合わせ**は次の形。

> 一段目 = 軽い多言語モデル（Fun-ASR-Nano 178MB）で即座に出す
> 二段目 = 端末内 LLM で整文、必要なら Qwen3-ASR で読み直す
> 話者識別 = 声紋27MB を横に足す

この形なら、4つの課題すべてに手が届き、**同時にアプリのサイズが 625MB から大きく減り、Android の後追いダウンロードという最も複雑な部分を畳める可能性**まで付いてくる。

## 7. 未確認のこと（実機で測るまで分からない）

| 項目 | なぜ重要か |
|---|---|
| 多言語モデルの日本語精度 | 課題2・3 を解く代わりに課題1 が悪化しては本末転倒。**最初に測るべき1点** |
| Fun-ASR-Nano の句読点対応 | 句読点の有無は読み返しやすさを大きく変える（Zipformer を退けた理由でもある） |
| Qwen3-ASR のスマートフォンでの速度 | Mac で RTF 0.7。端末で使い物になるかは未知 |
| 日本語と英語が1文に混ざる場合の挙動 | 多くのモデルは「1発話に1言語」を前提にしている。Fun-ASR-Nano は混在対応を明記しているが未確認 |
| 話者識別のしきい値 | 自分の声をどこまで確実に拾い、他人をどこまで弾けるか |
| 二段階認識の電池と発熱 | 常時リスニングのアプリで二重に処理する負荷 |
| 端末内 LLM の対応端末の広さ | 非対応端末での振る舞いを先に決める必要がある |
