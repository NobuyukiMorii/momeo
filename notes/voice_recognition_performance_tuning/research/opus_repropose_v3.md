# 音声認識の課題に対する再提案 v3

## この文書について

- **目的**: `opus_repropose_v2.md`（自分の現行主張）を、`codex_repropose_v2.md` を気づきとして使って組み直す。v2 を守ることが目的ではない。
- **調査日**: 2026-09-20
- **検証の方針**: 主張の出所では判断しない。**momeo が実際に入れている版のソース・配布物の実ファイル・モデルカードの原文**にあたって確かめる。確かめたものには根拠を、確かめられないものには「未確認」を書く。
- **根拠の種別**: 本文では次を区別する。
  - **【コード確認】** 該当バージョンのソース、または momeo のコードで確認した
  - **【一次資料】** 配布物の実ファイル、モデルカード、開発元ドキュメントで確認した
  - **【推論】** 確認した事実から導いた判断。実測が要る
  - **【未確認】** 確かめられていない
- **注意**: `codex_repropose_v2.md` が見ているのは `opus_repropose_v1.md` であり、v2 ではない。よって codex の指摘には「v2 で既に直したもの」が混ざる。本書では3種に分けて扱う。
- **前提条件**（変わらない）: クラウドを使わない。製品で使う認識モデルは1つ。表示したテキストは書き換えない。電池と発熱は採用条件。即時性は譲ってよいが「遅くてよい」は「重くてよい」ではない。優先順位は ①日本語精度 → ②日本語中の英語 → ③英語・中国語 → ④自分と他人の識別。
- **本書は方向性の提案**であり、実装計画ではない。モデル実行・実機計測・音声の外部送信・アプリ変更は行っていない。

## 0. 結論

**v2 から変えること**:

- **v2 の第一候補 Nemotron 3.5 を、第一候補から外す。** v2 がその根拠にした「transducer なので用語登録とビームサーチが使える」は、**momeo が入れている 1.13.3 では成立しない**ことをソースで確認した。この主張は**取り下げる**。
- **v2 の「Nemotron は現行より小さい」も取り下げる。** 圧縮453MB と展開625MB を比べていた。**展開後は約650MB で、現行より大きい**。
- **v2 の「Qwen3 は重み読み出し23倍だから最後」も、根拠として弱すぎた。** 倍率は正しいが、**絶対値を計算していなかった**。計算すると、この差は1日あたり電池の約1.3%相当で、**それ単独では不採用の理由にならない**。Qwen3 の本当の懸念は倍率ではなく**常駐RAMと持続的な発熱**である。
- **代わりに、v2 に無かった最も確度の高い一手が見つかった**（codex の指摘を追って自分で検証した）。**momeo が入れている sherpa_onnx 1.13.3 には、現行モデルが要求する特徴量正規化に float32 の桁落ちバグがある。** モデルを1つも替えずにライブラリを更新するだけで検証でき、**因果の鎖が端から端まで一次情報で確認できている唯一の施策**である。

**そのうえで変わらないこと**:

- 課題2・3 はモデルを替えるしかない（根拠は 3-C-1 のとおり、表現を弱めたうえで維持）。
- **どの多言語候補も、日本語で現行を上回る根拠を持っていない。** これは v2 の中心的な発見で、今回の検証でも覆らなかった。
- したがって**モデル比較の順序は「精度が良さそうな順」ではなく「変更が小さく、外したときの損失が小さい順」で決める**。

## 1. 争点の検証

### 1-A. codex v2 の指摘のうち、v2 で既に直していたもの

codex v2 は `opus_repropose_v1.md` を見ているため、次は**既に反映済み**である。差分の確認のみで、再検討はしない。

| codex v2 の指摘 | v2 での扱い |
|---|---|
| 3.2 CTC でビームサーチ・用語指定が「原理的に不可能」は誤り | v2 §1-2 で訂正済み。「sherpa-onnx の実装に経路が無い」に限定した |
| 3.3 小文字26文字だから英単語を出せない、は証明になっていない | v2 §1-1 で訂正済み。「原理的に不可能」を取り下げ、語彙の形を学習分布の証拠として使う形に変えた |
| 3.4 「RTF 10倍」は端末が違う数値の転用 | v2 §1-5 で自分から取り下げ済み |
| 3.6 252MiB 版の Fun-ASR-Nano は実在する | v2 §1-4 で確認済み。codex も v2 で自分の誤りとして訂正した |
| 公表 CER の横比較は使えない | v2 §1-6 で、現行モデル自身の公表値が JSUT 6.5〜MCV16.1 13.3 と2倍開くことを示した |
| 話者照合の誤り率1〜2%は転用できない | v2 §3-5 で取り下げ済み |

### 1-B. v2 と対立し、検証の結果 codex が正しかったもの

#### 1-B-1. Nemotron で用語登録とビームサーチは「今は」使えない 【コード確認】

**v2 の主張**: transducer 型なので用語登録とビームサーチが使える。これが Nemotron を第一候補にする根拠だった。

**検証**: **v2 は確認するファイルを間違えていた。** v2 が数えたのは `offline-recognizer-transducer-impl.h`（hotwords 37回）だが、**Nemotron 3.5 は逐次型であり、offline ではなく online の実装を通る**。

該当バージョンの実物を読んだ結果:

| バージョン | `online-recognizer-transducer-nemo-impl.h` | hotwords |
|---|---|---|
| **v1.13.3（momeo が使用）** | `greedy_search` 以外は `SHERPA_ONNX_EXIT(-1)` で**プロセス終了** | **0回** |
| v1.13.8（最新リリース） | 同上 | **0回** |
| master（調査時点） | `modified_beam_search` の分岐あり | 49回 |

さらに v1.13.3 の振り分けを読むと、online transducer には**第三の経路** `OnlineRecognizerTransducerNeMoParakeetUnifiedImpl` があり、**こちらも hotwords 0回・greedy のみ**だった。つまり**どちらの NeMo 経路を通っても、リリース版では両方とも使えない**。

**判断**: **v2 の第一候補の根拠は成立しない。取り下げる。** master には実装があるので「永久に不可能」ではないが、**未リリースの実装を採用根拠にはしない**。

> 補足【コード確認】: 言語指定については v2 の主張が残る。v1.13.3 の `online-recognizer-transducer-nemo-impl.h` は `ss[i]->GetOption("language")` を読み `GetLanguagePromptId` に渡している。**発話ごとの言語指定は 1.13.3 で動く経路がある。** （`ParakeetUnified` 側には language の参照が無いため、多言語の Nemotron はこの経路を通ると考えられる。【推論】）

#### 1-B-2. Nemotron は現行より小さくない 【一次資料】

**v2 の主張**: 「容量も 625MB → 453MB と減る」。

**検証**: 圧縮された配布物（453MB）と、現行の**展開後**（625MB）を比べていた。公式ドキュメントに載っている 560ms 版の内訳は **encoder 627M ＋ decoder 14M ＋ joiner 9.1M = 約650MB**。**展開後は現行より大きい。**

**判断**: **取り下げる。** 以後、圧縮サイズ・展開後サイズ・実行時RAMは混ぜない。

#### 1-B-3. 「まとめれば無料で文脈が増える」は言い過ぎ 【推論】

**v2 の主張**: ひと続きの話をまとめて認識すれば文脈が増える（電力は候補次第と留保はしていた）。

**検証**: codex の指摘のほうが正確である。**区間を長くすることと、モデルが実際に見る文脈範囲が広がることは別**。逐次型に30秒を流し込んでも、内部の先読み幅が30秒になるわけではない。

**判断**: 「長くまとめれば精度が上がる」という期待は**設定の探索項目に格下げ**する。採用理由にはしない。

### 1-C. v2 と対立し、検証の結果 v2 を維持するもの

#### 1-C-1. 現行モデルで課題2・3 は解けない 【一次資料・推論】

**codex の立場**: 語彙を数えただけでは「②③が絶対に解けない」と確定できない。文字の並びで `flutter` は構成できる。

**検証と判断**: **論として正しく、v2 は既にこの表現を採っている。**（v2 §1-1 で「原理的に不可能」は取り下げ済み。）維持するのは次の形である。

- 【一次資料】語彙3,073のうち、ひらがな82単独+261マージ／カタカナ84+44／漢字2422+55／数字10+8 に対し、**ラテン文字は26単独+マージ0**。
- 【推論】マージが形成される種類の語彙で、**数字ですらマージが8個できているのにラテンだけゼロ**なのは、学習時の書き起こしにラテン文字がほぼ無かったことを強く示唆する。
- 【一次資料】大文字トークンは0個なので、`iPhone` `API` のような表記は**どう転んでも出ない**。
- 【未確認】実際に英語混じりの音声を通したときの出力。**第0段で最初に確かめる。**

つまり「絶対に解けない」ではなく「**英語を出すよう学習していないと考えるのが妥当で、大文字表記は確実に不可能**」。この強さで維持する。

#### 1-C-2. どの多言語候補も日本語で現行を上回る根拠が無い 【一次資料】

これは v2 の中心的な発見で、今回も覆らなかった。

- 現行の公表 CER（CTC）: JSUT 6.5 / MCV8.0 7.2 / MCV16.1dev 10.2 / MCV16.1test 13.3 / TEDxJP 9.1
- SenseVoice-Small の日本語 11.96 は、**開発元自身の論文で Whisper-large-v3（10.34）より悪い**。sherpa にあるのは Small のみで、良い Large（9.19）は配布されていない
- Nemotron 3.5 の日本語 CER 11.48（最上位区分）
- Qwen3-ASR の日本語の公表値は**見つからなかった**【未確認】

**テストセットが違うので比較はできない。** それでも「多言語に替えれば日本語も上がる」と期待できる材料が**1つも無い**ことは変わらない。

### 1-D. どちらの文書にも無かった新事実（今回の最重要）

#### 1-D-1. momeo が入れている版には、現行モデルが通る経路に桁落ちのバグがある

codex v2 §5 A1 が「sherpa に NeMo の特徴量正規化の数値不安定性を修正した更新がある」と触れている。**指摘としては1行だが、追って検証したところ momeo に直接当たる**ことが分かった。因果の鎖を端から端まで確認できた。

| # | 確認したこと | 種別 |
|---|---|---|
| 1 | 現行モデル `model.int8.onnx` のメタデータに **`normalize_type = per_feature`** が入っている。配布物の実ファイル末尾を HTTP レンジ取得して読んだ（`model_type = EncDecHybridRNNTCTCBPEModel`・`subsampling_factor = 8` も同時に確認） | **【一次資料】** |
| 2 | sherpa の `offline-stream.cc` は `normalize_type == "per_feature"` のとき `NemoNormalizePerFeature` を呼ぶ | **【コード確認】** |
| 3 | **v1.13.3 の `math.cc` はこの分散を `E[x²] − (E[x])²` で計算している**（桁落ちする形） | **【コード確認】** |
| 4 | v1.13.8 では中心化した値から分散を出す形に修正され、コメントで桁落ちの説明が入っている | **【コード確認】** |
| 5 | 修正 PR #3857 の説明: あるメルビンが対数の床（約 −15.94）に貼り付くと、両項が約254.1 になり真の差（約2.5e-5）が float32 の分解能を下回る。**差が0になり `inv_std` が 1e5 になって、そのビンだけ +7515 に飛ぶ**（他は ±17 に収まる） | **【一次資料】** |
| 6 | 同 PR: **int8 エンコーダでは、この外れ値が動的量子化のスケールを壊し、デコーダが全ストリームで空文字を返す** | **【一次資料】** |

**momeo との関係**【推論】:

- momeo は **int8 のモデルを使っている**（条件6に一致）
- momeo は **VAD で切り出した区間**を渡す。区間の前後は無音に近く、**特定の帯域が対数の床に貼り付く条件を作りやすい**（条件5に一致）
- momeo には**空の認識結果を扱う経路が既にある**。[listening_providers.dart](../../../lib/providers/listening_providers.dart) の `emptyResultCount` で、コメントは「咳・物音の誤検知」としている。**その一部がこのバグである可能性がある**

**断定はしない。** 実際に起きているかは未確認である。だが**確かめる費用が極端に低い**。モデルも設定も画面も変えず、依存を 1.13.3 → 1.13.8 に上げて同じ音声を流し直すだけでよい。**今回の調査で、因果が端から端まで一次情報で追えた施策はこれだけである。**

> 注意【未確認】: 1.13.3 → 1.13.8 では onnxruntime も 1.27〜1.28 系へ上がり、Flutter/iOS/Android のネイティブ成果物も入れ替わる。**更新そのものが別の差を生む可能性があるので、更新前後で同じ音声を比較する。**

### 1-E. 双方が言い過ぎだったこと — Qwen3 の電力

**v2 の主張**: 1発話あたりの重み読み出しが現行の約23倍なので、Qwen3 は最後。

**codex の指摘**: RTF と消費電力とエネルギーは別物。sherpa の公式ページには日本語例で RTF 0.119（ja1.wav 5.080秒 → 0.605秒）とあり、0.7 とは違う。「10倍だから試さない」とはしない。

**検証**: **どちらの言い分にも直すべき点がある。**

- codex が正しい点: RTF と電力は別物である。**v2 の23倍は「重みの読み出しバイト数」であって RTF ではない**ので、そもそも RTF 0.119 と矛盾しない。
- **むしろ整合している**【推論】: 5.08秒の日本語なら出力は20トークン前後。v2 の式では 216MB + 721MB×20 ≒ 14.6GB。0.605秒で読むには約24GB/s が要り、**デスクトップの帯域としては妥当**。公式の数値は v2 の構造モデルを**否定せず、裏付ける**。
- **v2 が言い過ぎだった点**: **倍率だけを見て、絶対値を計算していなかった。** 計算するとこうなる。

| モデル | 重み読み出し/発話 | 現行比 | 1発話のエネルギー | 電池の%/日 |
|---|---:|---:|---:|---:|
| 現行 NeMo CTC ja | 0.61 GB | 1.0倍 | 0.05 J | 0.06% |
| SenseVoice Small | 0.22 GB | 0.4倍 | 0.02 J | 0.02% |
| Nemotron 3.5（貪欲） | 1.03 GB | 1.7倍 | 0.09 J | 0.10% |
| **Qwen3-ASR 0.6B** | **14.29 GB** | **23.4倍** | **1.23 J** | **1.36%** |

前提: 1日30分発話（3秒×600回）・int8・重みのみ・DRAM 10pJ/bit・電池15Wh。**桁の見積もりであり予測値ではない。**

**判断**: **23倍は正しいが、それ単独では不採用の理由にならない。** 1.36%/日は小さい。**v2 の「電力が桁違いだから最後」という理由づけを取り下げる。**

**差し替える理由**【推論】: Qwen3 を警戒すべきなのは倍率ではなく次の3つ。

1. **常駐RAM**。約937MB のモデルを、**バックグラウンド録音中ずっと**抱える。OS に落とされる危険が上がる【未確認】
2. **持続的な発熱**。発話率が高い環境（会議・テレビ）では稼働時間が伸び、熱で性能が落ちた後に待ち行列が増える
3. **待ち行列の成立条件**。`発話率 d × 持続RTF r < ASR を動かせる時間割合 b`（codex の定式化）。**話者を識別しない以上、他人の声もテレビも d に入る**

つまり Qwen3 の可否は**電池ではなく、RAM と熱と詰まりで決まる**。これは短時間の試験で判定できる。

## 2. 提案

### 2-1. 全体の形（v2 から変えない）

```text
録音（変えない）
  ↓
Silero VAD で発話を切り出す（変えない）
  ↓
単一の認識器が1回だけ認識する
  ↓
確定したテキストを一度だけカードにする（書き換えない）
```

モデルは1つ、認識は1回、表示済みテキストは書き換えない。クラウドも使わない。

### 2-2. 第一手: モデルを替えず、ライブラリだけ更新して再評価する

**1-D-1 の検証結果にもとづく。** モデル・設定・画面をすべて固定し、`sherpa_onnx` を 1.13.3 → 1.13.8 に上げて、**同じ失敗音声を流し直す**。

- **狙い**: 空の認識結果・崩れた出力のうち、桁落ちバグ由来のぶんを切り分ける
- **費用**: 依存の更新1回。モデルの再配布は不要
- **根拠の強さ**: 本調査で**唯一、因果が端から端まで一次情報で追えている**
- **やらないこと**: 「新しい版があるから上げる」ではない。**更新前後で同じ音声を比較し、差が出たものだけを成果と数える**

**これが効いた場合、課題1 の一部は多言語化の判断と無関係に前進する。** 効かなかった場合も、以後のモデル比較を**バグのない土台**の上で行えるようになる。

### 2-3. 第二手: モデルを比べる（**これは実施順であり、精度の順位ではない**）

**どの候補が日本語で最良かを予測する材料は無い。** したがって順序は「**変更が小さく、外したときの損失が小さい順**」で決める。

| 順 | 候補 | 実装の変更 | 展開後サイズ | 1.13.3 で使える道具 | 外したときの損失 |
|---|---|---|---:|---|---|
| 1 | **SenseVoice Small（2024-07）** | **offline のまま**。設定クラスの差し替えのみ | 228MB | 言語指定・ITN（句読点） | 小さい |
| 2 | **Qwen3-ASR 0.6B** | **offline のまま**。複数ファイル配布への対応が要る | 約937MB | **言語指定・用語登録（プロンプト注入）** | 中（配布が重い） |
| 3 | **Nemotron 3.5（1120ms）** | **online API へ移行**。状態管理・区切り・復旧が変わる | 約650MB | 言語指定のみ（**ビーム・用語登録は不可**） | 大きい |

補足【コード確認】: **1.13.3 で用語登録が実際に動く経路を持つのは Qwen3 だけ**である（`offline-recognizer-qwen3-asr-impl.h` の `BuildSourceIds(hotwords, language, ...)` でプロンプトに注入される）。CTC・SenseVoice・NeMo online のいずれにも経路が無い。**v2 はこれを Nemotron の長所として書いたが、実際には Qwen3 の長所だった。**

各候補の立ち位置:

- **SenseVoice Small**: 最も軽く、最も変更が小さい。ただし**日本語が現行に届く根拠は無く、開発元の公表値はむしろ不利**。**軽さと多言語だけを理由に採用しない。**
- **Qwen3-ASR**: 用語登録が今日使える唯一の候補で、**課題1 に対する唯一の能動的な手段を持つ**。反面、配布が937MB、常駐RAMが最大の懸念。**既定の `maxNewTokens = 128` / `maxTotalLen = 512` を必ず確認する**【コード確認】。長い発話の出力打ち切りを、モデルの認識能力と取り違えない。
- **Nemotron 3.5**: 言語の品質区分（日=最上位・英=最上位・中=二番手）が優先順位と一致する点は**v2 から維持する**【一次資料】。句読点と大文字にも対応する。だが**道具が無く、サイズも現行より大きく、online API への移行という最も大きな変更を伴う**。**先に試す理由が無い。**

### 2-4. 課題1 に対して、モデル差し替えと独立に積めるもの

1. **ライブラリ更新による切り分け**（2-2）
2. **収音と区切りの診断**。語頭・語尾の欠け、停止時に捨てられている最大32msの端数（[stt_audio_worker.dart:415](../../../lib/stt/stt_audio_worker.dart:415)）【コード確認】、無音しきい値、小声、遠距離
3. **表記の置換辞書**。確定表示の直前に決定的な規則として当てる。**消えた英語を取り戻すものではない**ので、期待を分ける
4. **用語登録**（Qwen3 を選んだ場合のみ）。ただし**無関係な語を挿入する方向に働く可能性がある**ので、用語を含まない対照音声でも測る

### 2-5. 課題4（自分の声の識別）

**①〜③の採否が決まるまで着手しない。** v2 では「最後だが残す」と書いたが、実質的に codex の「後回し」と同じ運用になる。差を作らない。

着手するときの形は v2 から変えない: 声紋モデル1つ（約27MB）＋ `SpeakerEmbeddingExtractor` / `SpeakerEmbeddingManager`、**最初は判定ではなくラベル付け**（本人・他者・不明）、1区間に複数話者が入る場合は対象外。誤り率の数値は**転用しない**【未確認】。

## 3. 採らない案

| 案 | 理由 |
|---|---|
| クラウド ASR | 費用と通信量。前提として除外 |
| 二段階認識・別LLMによる整文 | 表示済みテキストの書き換え、2モデル、電力。**加えて、テキストしか見ない処理は音声から消えた情報を復元できない** |
| 言語別に複数の ASR を切り替える | 「モデルは1つ」の前提に反する |
| master の未リリース実装を前提にした設計 | Nemotron の用語登録・ビームサーチは master にしか無い。**リリース版に入ってから別条件として評価する** |
| 「Nemotron は同系統だから省電力」という推定 | サーバGPUの数値や系統の同一性は、スマートフォンの電力の根拠にならない |
| 現行の頭を TDT に替える | 公表値の差は0.1ポイント【一次資料】。課題2・3 も解けない |
| 雑音抑制を常時かける | 録音中ずっと計算が増える。**雑音が主因と診断できた場合に、発話区間だけへ限定して**初めて検討 |
| 充電中にまとめて認識する（録りだめ） | 数時間の遅延は「即時性を譲る」とは別のUXになる。**基本案にしない** |
| 長くまとめれば精度が上がるという前提での設計 | 1-B-3 のとおり。設定の探索項目に留める |

## 4. 進め方と判断表

### 4-1. 進め方

```text
第0段: 現状を測れるようにする（モデルもライブラリも替えない）
        ・待機 / 録音のみ / 録音+VAD / 録音+VAD+ASR を release 相当で比較
        ・生PCM と VAD 切り出し後を聴き比べる。32msの端数を確認
        ・英語混じりの音声を現行モデルに通し、1-C-1 の推論を実地で確かめる
        ・空の認識結果がどの頻度で、どんな音で起きているかを記録する ← 第1段の比較対象
        ↓
第1段: ライブラリだけ更新して同じ音声を流し直す（1.13.3 → 1.13.8）
        ・モデル・設定・画面は固定
        ・空の結果と崩れた出力が減るかを見る
        ↓  ここまでモデルは1つも替えていない
第2段: 評価音声をそろえる
        ・日本語のみ / 日英混在 / 英語 / 普通話 / 雑音・他者・テレビ
        ・調整用と最終判定用を分ける。合成音声だけで判断しない
        ↓
第3段: 同じPCMでモデルを比べる（2-3 の順）
        ・短い予備評価で RAM・異常終了・出力打ち切りを先に落とす
        ・通過した候補だけ長時間試験へ進む
        ↓
第4段: 課題4（本人・他者・不明のラベル付け）
```

**一度に1つだけ変える。** 区間長・辞書・ライブラリ・モデルを同時に動かさない。

### 4-2. 判断表

| 分かること | 進む方向 |
|---|---|
| ライブラリ更新で空の結果・崩れが明確に減る | **課題1 が多言語化と無関係に前進する。** ここを確定させてから第3段へ |
| 更新で変わらない | バグは主因ではなかったと記録し、土台が整った状態で第3段へ |
| 熱源が録音側だった | 録音側を直す。モデルの選択肢は広がる |
| 熱源に ASR も効いている | 重い候補（Qwen3）を先に落とす。SenseVoice の軽さが意味を持つ |
| SenseVoice の日本語が現行と同等以上 | **採用**。課題2・3 が解け、負荷も下がる |
| SenseVoice の日本語が落ちる | 軽さと多言語だけでは採用しない。Qwen3 へ進む |
| Qwen3 の日本語が現行以上で、RAM と熱と詰まりが条件内 | **採用**。用語登録も使える |
| Qwen3 が RAM か熱か詰まりで落ちる | Nemotron へ。ただし online 移行の開発量に見合う改善があるときだけ |
| どの多言語候補も日本語で現行に届かない | **差し替えを見送る。** 現行を残して第0段・第1段・2-4 の積み上げだけを進め、**課題2・3 は解けないと明示する** |
| 日本語は同等だが普通話が実用にならない | 採用してよい。**普通話は3番目**なので、英語混在が解ければ前進と見なす |

**課題2・3 のために課題1 を犠牲にしない。** そして**「どれも届かない」という結果も正当な結論**として受け入れる。
