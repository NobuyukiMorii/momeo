# momeo 音声認識の再提案 v1 — 端末内・単一認識・長時間運用

調査日: 2026-09-20  
対象: 現在の実装、過去の実機記録、[opus.md](opus.md)、前回の[Codex調査](codex.md)、開発元・ライブラリ提供元の公開資料。  
本書は設計と採用候補の提案。モデルの実行、実機での電力測定、音声の外部送信、アプリ実装の変更は行っていない。

## 1. 今回の結論

**現行の録音基盤を活かし、「録音を優先して継続し、単一のオンデバイスASRで各区間を一度だけ認識し、確定した文章だけを表示する」方式を推奨する。** クラウド、二段階認識、別LLMによる整文は採用しない。④の本人識別も今回の必須範囲から外す。

モデルについては、**日本語精度改善の本命候補は引き続きQwen3-ASR-0.6B。ただし、前回のように最初から製品への置換を中心に据えず、長時間運用の電力・発熱条件を通過した場合に限る**。低負荷を狙う比較対象としてSenseVoice Small int8を先に短時間評価し、現行NeMo・SenseVoice・Qwenの3者を同じ音声で比較する。これは開発時の比較であり、製品で3モデルを同梱・併用する提案ではない。

理論上の期待は次のように分かれる。

- **①日本語と②混在認識の改善余地を調べる本命:** Qwen3-ASR-0.6B。音声から直接文字起こしする単一モデルとして使う。用語ヒントも同じ認識処理に渡せる。ただし現行より高精度・低消費電力であることは未証明。
- **長時間運用との両立を狙う有力候補:** SenseVoice Small。非自己回帰型で日本語・英語・中国語を扱え、公式int8配布も比較的小さい。ただし日本語精度が現行に届かなければ採用しない。
- **両者が条件を満たさない場合:** Nemotron 3.5の単一ストリーミング認識を比較する。それでも不十分なら、①を優先して現行モデルの収音・区切り・電力を改善し、②③の全面解決は保留する。

**「遅くてもよい」は、大きなモデルを無条件で採用できるという意味ではない。** 遅延の許容は、録音と推論を分け、発熱時に認識を一時的に待たせ、途中の文字を表示しない自由を与える。一方、長時間平均の計算量や消費電力まで自動的に減らすものではない。

## 2. 守る条件と、今回は解かないこと

| 項目 | 今回の方針 |
|---|---|
| 最重要 | 無意識下で長時間録音を続けられること。認識より録音継続を優先 |
| 課題の順位 | ①日本語 → ②日本語中の英語 → ③英語・中国語 → ④本人識別 |
| クラウド | 使用しない。任意の高精度モード、再認識API、自前サーバーも提案から除外 |
| 認識モデル | 製品で採用するASRは1つ。言語別に複数モデルを切り替える方式も採らない |
| 表示 | 仮の認識文を表示しない。確定した区間を一度だけ追加し、既存文を再認識で書き換えない |
| 遅延 | 許容する。具体的な上限は未指定なので、数秒〜数十秒を初期の評価範囲とし、分単位の待ちも測る |
| 電池・発熱 | 採用条件。短いデモの速度だけで決めない |
| 話者 | 今回は識別しない。他人やテレビの声も処理対象になり得ることを残課題として明示 |

ここで「単一モデル」は**単一の文字起こしモデル**を意味する。現行の小型Silero VADは発話の有無を判定するため残す。VADは一次文字起こしをしないため、二段階認識にはならない。VADまで廃止すると、無音を含めてASRへ渡す構成になりかねず、今回の目的に逆行する。

運用中の音声認識通信量とAPI従量課金はゼロにする。モデルの初回配布・更新には容量が必要なので、1モデルだけを配布し、音声送信や定期的なモデル再取得を行わない設計とする。初回配布まで完全無通信にするならアプリへの同梱が必要であり、その場合もインストール容量自体は消えない。

## 3. 現行実装と過去の判断をどう捉えるか

### 現在は既に、無音中ずっとASRを回す仕組みではない

```text
16kHz / mono / PCM16 録音
  → 専用isolate内のSilero VAD
  → 発話区間ごとにNeMo CTCで同期的に認識
  → 確定テキストをメモへ追加
  → SQLiteへ保存（音声の永続保存はない）
```

モデルは `sherpa-onnx-nemo-parakeet-tdt_ctc-0.6b-ja-35000-int8`。使用するのはCTC側で、ASRは1スレッド、モデルは使い回される。毎回のロード削減やVAD導入は既に済んでいる。VAD設定は無音1.5秒、最短発話0.25秒、最大発話30秒。

したがって、**「VADを入れる」「バッチ化する」「モデルを常駐する」だけでは新しい改善にならない**。現状の主な設計上の弱点は、VADと同期ASRが同じisolateにあり、重い認識に交換すると後続音声のVAD処理も待たされること。現在の速いNeMoでは目立たなくても、遅いモデルでは待ち行列・メモリ・停止処理の問題が出る。

確認箇所: [音声worker](../lib/stt/stt_audio_worker.dart)、[録音pipeline](../lib/stt/stt_listening_pipeline.dart)、[モデル準備](../lib/providers/stt_providers.dart)、[モデル配置](../lib/stt/stt_model_provisioner.dart)、[メモ保存](../lib/providers/listening_providers.dart)。実際の解決済み依存は `sherpa_onnx 1.13.3`。

### 過去の実機比較をやり直しの出発点にする

[VAD・Whisper実装記録](research/on_device_stt/vad_whisper_impl_log.md)には、2026年6月のPixel 8a / Android 16 / debugビルドで次の観察がある。

| 過去の候補 | 記録された結果 | 今回の解釈 |
|---|---|---|
| Whisper small系 | 設定・実装改善後にも秒単位の処理。現行との比較で精度の優位も見られなかった | 遅延を許容しても、省電力になる根拠はない。第一候補へ戻さない |
| ReazonSpeech k2 Zipformer int8 | 発話約0.8〜3.4秒に43〜142ms。句読点なし | 既に試した軽量候補。新発見として扱わない |
| 現行NeMo CTC | 発話約1.4〜3.7秒に108〜276ms。日本語・句読点が良好との評価 | 現行選択には実機上の理由がある。置換候補はこれを越える必要がある |

これは少数音声での定性的な精度評価であり、共通テストセットのCER測定や消費電力測定ではない。古いWhisper wrapperの問題を最新エンジン全体の限界に一般化することもしない。

前回の`codex.md`では、この比較履歴の反映が不足し、Zipformerを新規の有力比較候補のように扱った。またQwenの品質期待と長時間運用の負荷を十分に分けていなかった。この2点を今回修正する。

同意できるのは、日本語向けの現行モデルだけでは②③への対策が不足すること、録音基盤を活かせること、本人識別はASRと別の問題であること。以下の主張はそのまま採用しない。

| 小さいモデルにすれば準備ゲートを畳める | ダウンロード待ちを減らせる可能性はあるが、モデル検証・ロード・失敗復旧は残る。今回確認できない252MBを配布設計の前提にしない |
| 話者照合の誤り率1〜2%なので導入しやすい | 特定ベンチマークの値をmomeoの小声・遠距離・他者との重なりへ転用できない。VADの1区間に複数話者が入る場合もある |
| 軽い一次認識＋高精度二次認識が最終案 | 今回のUX・単純性・電池条件と合わないため採らない。単一ASR＋別LLM整文も同様に除外 |

根拠: [Fun-ASRの公式ONNX構成](https://k2-fsa.github.io/sherpa/onnx/funasr-nano/pretrained.html)、[開発元のNanoモデルカード](https://huggingface.co/FunAudioLLM/Fun-ASR-Nano-2512)、[CTCに対する用語バイアス研究](https://www.isca-archive.org/interspeech_2025/nakagome25_interspeech.html)、[Nemotronのロケール区分](https://k2-fsa.github.io/sherpa/onnx/nemo/nemotron-streaming.html)。Fun-ASR配布説明にはデモの選択肢を「31 languages」とする記述もあるが、それだけで当該checkpointの対応言語を判断しない。

また、圧縮ダウンロード容量・展開後ファイル容量・実行中RAM・消費電力はそれぞれ別の指標。opus.mdと前回資料の数字を比較するときも混ぜない。

## 5. 具体案A: 現行を基盤に単一ASRを交換する（推奨）

### 録音と推論の待ちを分離する

```text
録音 → 軽いVAD処理 → 発話音声を端末内の一時キューへ
                            ↓
                    単一ASR workerが順番に認識
                            ↓
                    確定テキストを一度だけ保存・表示
                            ↓
                    保存済み区間の一時音声を削除
```

ASRの前後で別のASRや整文LLMは動かさない。Qwenが内部に音声encoderとdecoderを持つことも、アプリが2つの認識器を併用することとは異なる。

最初から複雑なスケジューラーは作らず、**録音/VAD担当と1本のASR担当、順番を保つキュー**を基本とする。熱状態に応じた休止は、その必要性が測定で判明した後に加える。ASRを並列実行して待ち時間を縮める設計にはしない。

遅延を許容しても、理由なく毎回数十秒待つ必要はない。まず現行のVAD区間を使い、区間が完成したら処理する。短区間の結合は、固有名詞や文脈の精度改善が実測できる場合だけ加える。初期比較では10〜20秒程度の区間と現行区切りを比べ、最大30秒を出発点とする。これらは探索値であり、全モデルに最適な値ではない。

長い無音をまたいで会話を無条件に結合しない。長く話し続ける場合には最大長で区切る。境界をまたぐ語の欠落は前後余白等で検証するが、重複認識や文字の二重追加にも注意する。長区間化は計算・メモリを増やす場合があり、「まとめれば省電力」とは断定しない。

### UXは「録音中」と「文字起こし待ち」を分ける

録音が続いていることは音声入力側の状態で示す。待ち区間には「文字起こし待ち」などの状態だけを表示し、仮文は出さない。確定結果が来たらその区間を追加する。後続区間の追記は可能だが、表示済み区間を再推論して修正しない。

長い待ちが発生した場合も「録音は継続中／未処理の音声あり」と分かるようにする。録音終了操作は新しい収音の停止を意味し、未処理音声の削除や認識完了とは分ける。

### 遅延を入れるなら、保存・時刻も変更が必要

現在は音声を永続保存しないため、RAMだけに長い待ちを貯める設計は避ける。端末内に**未処理分だけ**短いファイル単位で保存し、区間ID・収録開始/終了時刻・処理状態を持たせる。テキストのDB保存完了後に音声を削除し、再起動時には未完了区間から復旧する。同じ区間IDを二重登録しない。

現在の`ListeningNotifier`には通知到着時の`DateTime.now()`や追記間隔によるカード判定がある。遅れて届いた文章の作成時刻・順序・カード分割は**実際の収録時刻**に基づくようにする。DB書き込みも逐次化し、まとまって届いた結果の競合を防ぐ。

16kHz・mono・PCM16は約1.92MB/分、115.2MB/時。連続8時間なら約922MBになる。VAD後の音声だけなら減るが、テレビや会話が続けば大きくなる。例えば未処理音声30分で約57.6MBという規模を参考に、時間と容量の両方に上限を設ける。30分は設定案であり確定仕様ではない。

容量上限に達したら黙って古い音声を捨てない。可能なら認識を追いつかせ、解消できなければ保存を継続できないことを明示する。**有限の電池・ストレージで無制限の遅延録音は保証できない。** 一時保存は認識の遅さによる消失を減らすための追加機構であり、永久的な録音アーカイブを新設する提案ではない。

SenseVoiceの対象版は、公式説明で`use_itn=1`時の句読点対応が確認できる2024-07版を基準にする。年が新しいという理由だけで別版へ替えない。[SenseVoice開発元](https://github.com/QwenAudio/SenseVoice)、[ONNXモデルと設定](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html)

Qwenの公開ONNXはfrontend・encoder・decoderとtokenizerで構成される。導入済み1.13.3には`OfflineQwen3AsrModelConfig`が存在するため、別ランタイムへ全面移行せず試せる。ただしDart APIの存在だけでiOS/Androidの安定動作を保証しない。既定の`maxNewTokens=128`等は長区間での出力打ち切りも確認する。用語ヒントは短く保ち、不要な語の挿入が増えないかを見る。[Qwen公式ONNX配布・設定](https://k2-fsa.github.io/sherpa/onnx/qwen3-asr/pretrained.html)

**単なる2ファイルの差し替えではない。** 候補に応じた認識器config、複数ファイルの整合性確認、Android/iOSの配布、初期化、停止・復旧を修正する。ただし録音やメモUIを全面的に捨てる必要もない。

①だけに絞る予備候補としてMoonshine v2日本語版もある。公式の配布は言語別であり、日本語版1つで②③まで解決すると見込まない。軽量日本語モデルへ方針を絞る場合に評価する。[Moonshineの言語別モデル一覧](https://k2-fsa.github.io/sherpa/onnx/moonshine/index.html)

## 7. 具体案B: 認識方式・実行基盤を変える場合

### B1. 単一ストリーミングASRで処理し、確定結果だけ表示する

「ストリーミング認識」と「途中の文字を画面へ出すこと」は別。Nemotron等で音声を順次処理しても、仮説は内部に留め、区間確定時に一度だけ表示できる。UX上の書き換えも二段階認識も必要ない。

この方式では処理を細かく進められるため、長い区間を一括decodeする構成との電力・待ち行列の違いを比較できる。ただし、省電力になること自体は未証明。無音時の計算、状態保持、VADと認識器の区切りの整合を測る必要がある。現行のoffline認識器より変更範囲が広いため、案Aの候補で条件を満たせなかった場合に進む。[Nemotronの公式実行方法](https://k2-fsa.github.io/sherpa/onnx/nemo/nemotron-streaming.html)

### B2. 同じ単一モデルを端末のアクセラレーターで実行する

CPU版で日本語精度は良いが電力だけが不合格だった場合、Core ML等の端末別実行経路を検討する。モデルを増やさず負荷を改善する方向である。

ただし、`provider`の文字列を替えれば全体がNPUで動くとは限らない。演算対応、量子化形式、動的shape、ネイティブライブラリのビルド対応を確認する。CPUとアクセラレーター間で多数の分割が生じると性能が悪化する場合もある。iOS/Androidで保守経路が増えるため、最初から採らず、品質が確認できたモデルだけを対象にする。[ONNX Runtimeのモバイル適合性確認](https://onnxruntime.ai/docs/tutorials/mobile/helpers/model-usability-checker.html)

端末別のOS音声認識へ全面依存する案や自前学習は、今回の「単純な仕組み」と両OSでの挙動統一に対して変更が大きい。上記の既存モデル・ローカル実行案より優先しない。

## 8. 遅延と電力についての重要な限界

認識時間を音声の長さで割った値をRTFとする。単一workerの待ちが長期的に増え続けないための粗い条件は、次のように考えられる。

```text
発話率 d × 持続運転時のRTF r < ASRを動かせる時間割合 b
```

例えばRTF=2でも発話率10%なら必要な稼働割合は約20%になる。一方、発話率70%なら約140%となり、常時動かしても追いつかない。発熱対策でASRを動かせる時間を制限すれば、さらに厳しくなる。これは概算であり、I/Oや区切りの費用・発話の集中を別途見込む必要がある。

前回の「RTFが1を下回るか」という判定だけでは不十分だった。**発話の少ない生活と、会議やテレビのある環境では成立条件が違う。** 本人識別をしない今回は、他者の声も発話率に含まれる。平均RTFだけでなく、熱で性能が落ちた後の値と最長待ち時間を測る。

また、同じ計算を後回しにしても総エネルギーは残る。熱のピークを抑える効果と、電池の減りを抑える効果を混同しない。ASRが休んでいる間もマイク・VAD・録音の基礎負荷は続く。充電中にまとめて処理する方式は候補にはなるが、「一定の遅延許容」を「翌日まで文字が出なくてよい」と読み替え、基本仕様にはしない。

## 9. モデル交換と並行して調べる現在の発熱要因

現時点では、発熱の主因がASRだと実測で確定していない。モデル交換だけに原因を求めない。

| 切り分け対象 | コード上の観察と確認内容 |
|---|---|
| 画面描画 | [ListeningBackdrop](../lib/widgets/listening_backdrop.dart)はTickerで毎フレーム更新する。画面表示時の描画負荷と非表示時の停止を確認。バックグラウンドでも描画が続くと断定しているわけではない |
| 定期処理 | [MainThreadWatchdog](../lib/diagnostics/main_thread_watchdog.dart)は500ms周期。releaseでの必要性と実際の寄与を確認 |
| PCM処理 | worker内の変換・配列操作・音量通知の頻度を計測。コピー削減やUI通知間引きで効果があるかを見る |
| 録音継続機構 | Androidのforeground service・wake lockは録音維持との関係がある。電池対策として無条件に外さない |
| ASR | 無音時・発話時の差、スレッド数、CPU実行時間、熱で遅くなった後の挙動を測る |

isolateを増やすこと自体に省電力効果はない。録音を推論待ちから守るために分離し、データコピーの増加も測る。スレッドを1本に減らす施策も現行では既に1本であり、新規の省電力策として数えない。

バックグラウンド録音にはOSによる制約があり、OSによる終了や権限変更まで防げるわけではない。既存の再開・監視を保ち、ASR worker異常時にも録音と未処理区間を守る設計にする。

## 10. 最小限の検証順と採用判断

### 第1段階: 現状を測れる形にする

同じ失敗音声をモデル間で比較できるローカル評価セットを作る。日本語を中心に、日英混在、英語、普通話を分ける。小声・早口・固有名詞・遠距離・雑音・短い発話・長い発話・無音・テレビ音声を含める。

録音直後とVAD切り出し後を比較し、語頭・語尾の消失を確認する。現行の停止時に512サンプル未満の端数が残る可能性も確認する。ただし最大約32msの端数だけを精度問題全体の原因とはしない。

同時に、画面オン/オフを揃えた「待機」「録音のみ」「録音＋VAD」「録音＋VAD＋現行ASR」を測り、どこで電力が増えるか分離する。debugの観察値を製品の消費電力と見なさず、release相当で測る。[Android公式のプロファイリング方針](https://developer.android.com/studio/profile)

### 第2段階: 3モデルを別々に評価する

現行・SenseVoice・Qwenをそれぞれ単独で実行する。まず短い評価で精度・RAM・異常終了・出力打ち切りを確認し、明らかに条件外の候補を落とす。通過候補は30分程度の予備運転後、4〜8時間など実利用に近い長時間で測る。これは提案する試験時間であり、既に実施したという意味ではない。

| 観点 | 指標と採用基準 |
|---|---|
| ①日本語 | CERと人による意味確認。否定・数値・人名・固有名詞・脱落を別集計。現行に対する改善を最優先 |
| ②混在 | 英単語の脱落率・正しい綴り・周囲の日本語の悪化。外来語のカナ表記と英字表記の好みは分ける |
| ③外国語 | 英語WER、普通話CER。言語別に測り、日本語との平均だけで判断しない |
| 安定性 | 録音欠落、未処理秒数の増加、最長待ち、復帰後の重複・消失、最大RAM |
| 電力 | 同条件の電池消費/時、可能ならエネルギー/音声分、熱状態と性能低下。現行の悪化を容認して置換しない |
| 利用環境 | 発話率0%・10%・50%・ほぼ連続を比較。低発話率だけで合格にしない |

最低対象AndroidとiPhoneの両方で確認する。電池消費の絶対的な製品目標は未指定なので、現行との相対値に加え、必要連続時間から許容予算を決める。「現行より良いが、長時間運用にはなお不十分」という結果も区別する。

### 第3段階: 結果に応じて一つに決める

1. **Qwenが①②を改善し、長時間運用も通過:** 単一ASRとして採用。今回の品質改善方針として最も望ましい結果。
2. **Qwenは負荷が大きく、SenseVoiceが①を改善し②③も有用:** SenseVoiceを採用。小さいことだけで日本語の悪化を正当化しない。
3. **SenseVoiceは日本語が不十分、Qwenは運用条件を満たさない:** Nemotronを次に比較。Qwenの品質差が特に大きければアクセラレーター対応も検討。
4. **いずれも不合格:** 現行を維持し、収音・VAD境界・UI負荷を改善する。①の改善が限定的であることを明示し、②③を無理に約束しない。必要なら日本語専用の軽量候補へ評価範囲を絞る。

採用前に選んだcheckpointと配布物のライセンス・再配布条件を確認し、モデル一式を固定する。世代名だけで性能や条件を引き継がない。

## 11. ④本人識別を後回しにする理由

VADは声の有無を判定するだけで、本人の声かどうかは分からない。話者A/Bを分けることと、登録した本人を特定することも別である。音量や距離だけで本人と決める方法は採らない。

実用的な本人照合には、登録音声・話者特徴抽出・照合閾値・複数話者区間への対処が必要になる。今回の単純性と追加負荷への懸念を踏まえ、ここは明確に未解決のまま残す。将来、他人の声を処理する電力が大きな問題だと判明した場合に、小型照合器の追加負荷とASR削減量を比較して別途判断する。

**今回まず進めるべきなのは、現行の発熱要因を切り分けながら、SenseVoiceとQwenを単独比較すること。その先の製品構成は、端末内の単一ASR・確定表示のみ・録音優先に統一する。** 即時性を緩めることを、モデル二重化や無制限の処理待ちの理由にしない。
