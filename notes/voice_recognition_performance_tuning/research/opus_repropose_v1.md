## この文書について

- **調査日**: 2026-09-20
- **突き合わせた資料**: 自分の調査（`notes/opus.md`）と、別エージェントの調査（`notes/codex.md`）。両者の食い違いはコードと一次情報で確認した。

## 0. 結論

**いま何が変わるか**: 前回の本命だった二段階認識を取り下げ、**1モデル・1パスのまま、譲ってよくなった「遅延」を「精度」に変換する**形に組み直した。

- **即時性を譲れることは、いちばん大きな追い風**。ただし**「遅くてよい」は「重くてよい」ではない**。電池と発熱は遅延ではなく **RTF（音声長に対する処理時間の比）に比例する**ため、遅延を譲っても電力の余裕は1ミリも増えない。ここを取り違えると、発熱が悪化するモデルを「遅くてもいいから」という理由で選んでしまう。
- 遅延を譲ることで**電力を増やさずに手に入るもの**が3つある。**ビームサーチ**（複数の候補を並行して残す探索）、**用語登録**（話しそうな語を事前に渡す）、**長い文脈**（1発話ではなく、ひと続きの話をまとめて認識する）。**この3つはいずれも課題1に直接効く**。
- ただし前の2つは **transducer 型のモデルでしか使えない**。現行の CTC 型では原理的に使えない。**つまり「課題1に効く道具を手に入れる」こと自体が、モデルを替える理由になる**。
- **本命は Nemotron 3.5 ASR（453MB）への1モデル差し替え**。日本語・英語・中国語を含む40ロケールに対応し（課題2・3）、transducer なので用語登録とビームサーチが使え（課題1）、句読点も内蔵する。現行と同じ FastConformer 系なので電力の見当も付けやすい。
- **Qwen3-ASR を第一候補にはしない**。codex.md はこれを第一候補に置いているが、**RTF がおよそ10倍になる**ため、既に発熱が出ている状況では最もリスクが高い。除外はしないが、**電池の内訳を測ってからでなければ触らない**。
- **発熱は、先に切り分ける**。現行の ASR は RTF 約0.075、つまり**話している時間の7.5%しか CPU を使っていない**。いま既に熱いなら、主因は ASR ではなく録音の常時稼働側にある可能性が高い。**そこを測らずに重いモデルへ動くのは、いちばんやってはいけない手**。

## 3. いちばん大事な一点 — 「遅くてよい」は「重くてよい」ではない

即時性を譲れることは大きな追い風だが、**そこから「だから重いモデルを積める」と進むと、発熱の問題を悪化させる**。理由は、電池と発熱が遅延ではなく**処理量**で決まるからである。

```text
【 遅延 】 話し終えてから文字が出るまでの待ち時間
          → ここは譲れる。3秒でも5秒でも構わない

【 電力 】 RTF × 話した時間ぶんの計算量
          → ここは譲れない。遅延を許しても1ミリも減らない
```

同じ「1発話に3秒かかる」でも中身はまったく違う。

- 軽いモデルが 0.3秒で終えて 2.7秒待たせている → **電力は小さい**
- 重いモデルが 3秒ずっと計算している → **電力は10倍**

**momeo が守りたいのは「無意識下で長時間録音し続けられること」**であり、それを壊すのは遅延ではなく電池と発熱である。したがって、**RTF は遅延と切り離して、独立した採用条件として扱う**。

### では、遅延を譲ると何が手に入るのか

電力をほとんど増やさずに、課題1 に効く道具が3つ手に入る。

| 手に入るもの | 中身 | 課題1 への効き方 | 追加の電力 |
|---|---|---|---|
| **ビームサーチ** | 候補を1本だけでなく複数残して最後に選ぶ探索 | 後の音を聞いてから前を言い直せる | 小（transducer なら主に後段のみ） |
| **用語登録** | 話しそうな固有名詞を事前に渡して認識を寄せる | 人名・社名・専門用語の取りこぼしに直接効く | ほぼゼロ |
| **長い文脈** | 1発話ずつではなく、ひと続きの話をまとめて認識する | 前後の言葉で同音異義語を決められる | 小〜中（モデル次第。要実測） |

**ビームサーチと用語登録は transducer 型でしか使えない**。現行の CTC 型ではどちらも使えず、**現行モデルに留まる限り、遅延を譲っても課題1 は1ミリも前進しない**。ここが今回の判断の中心になる。

## 4. 先に測る — 発熱の主因は ASR ではない可能性が高い

いま既に発熱が出ているという事実は、モデル選びより先に扱うべき情報である。

現行の ASR は RTF 約0.075。**話している時間の7.5%しか CPU を使っていない**。1日に30分話しても、ASR の計算時間は合計2分強にすぎない。**この規模で端末が熱くなるとは考えにくい**。

つまり熱源は、ずっと動き続けている側にある可能性が高い。

| 熱源の候補 | 稼働のしかた | 確認方法 |
|---|---|---|
| マイクの常時取得と音声経路 | 録音中ずっと | ASR を止めた状態で録音だけ流して測る |
| 前景サービス・スリープ抑止 | 録音中ずっと（Android） | サービスのみ起動して測る |
| Silero VAD | 32msごと、毎秒31回、録音中ずっと | VAD のみ動かして測る |
| 変換ループの割り当て | 毎窓で確保とコピーが走る（下記） | プロファイラで確認 |
| Live Activity の更新 | 表示中（iOS） | 表示あり／なしで比較 |
| 画面とアニメーション | 前景表示中 | 画面消灯時と比較 |

### コードで見つけた具体的な2点

どちらも**現行の発熱の主因だと断定はできない**が、長時間動かすアプリとして確認する価値がある。

- **変換ループが毎窓で確保とコピーをしている**。[stt_audio_worker.dart:442](../lib/stt/stt_audio_worker.dart:442) の `acceptAudio` は、512サンプルごとに `sublist` で新しいリストを作り、`removeRange` で前詰めし、さらに `Float32List.fromList` でもう一度確保している。これが毎秒31回、録音中ずっと続く。固定長の環状バッファにすれば確保もコピーも消せる。
- **停止時に最大32msが捨てられている**（codex.md の指摘。検証済み）。`stopListening` は VAD を flush するが、変換バッファに残った512サンプル未満を投入していない。末尾の一語が欠ける可能性がある。

**第0段でこれらを測るまで、重いモデルには動かない。** ここで「ASR にはまだ余裕がある」と分かれば選べる候補が広がり、「録音側で既に一杯」と分かれば、**モデルは軽い方向にしか動かせない**ことが確定する。どちらに転んでも、その後の判断がはっきりする。

## 5. 本命の提案 — 1モデル差し替えと、認識の単位の変更

### 5-1. 何を変えるか

```text
【 いま 】
  VAD が1発話を切り出す → 認識器を作る → 1発話だけ変換 → 破棄 → カード
  ・文脈は1発話ぶんだけ。前の発話は一切参照しない
  ・日本語しか出力できない
  ・貪欲探索のみ。用語登録は使えない

【 提案 】
  VAD が1発話を切り出す → ひと続きの話がまとまるまで溜める → まとめて変換 → カード
  ・文脈はひと続きの話ぜんぶ
  ・日本語・英語・中国語を1モデルで出力できる
  ・ビームサーチと用語登録が使える
```

変えるのは**認識器と、認識を呼ぶ単位**の2つだけ。録音・VAD・バックグラウンド動作・保存・画面はそのまま。**モデルは1つ、認識は1回、テキストの書き換えは発生しない。**

「ひと続きの話」の区切りは、無音が長めに続いたとき（例: 5秒）か、溜まった音声が上限に達したとき（例: 30秒）のどちらか早い方とする。**これは今のカードの作り方とほぼ同じ考え方**で、既に「最後の追記から1分」で次のカードに移る仕組みがある。認識の単位をカードの単位へ寄せる形になる。

副次的に、**認識の呼び出し回数が減る**（発話ごと → ひと続きごと）。1回あたりの固定費が減るぶん、電力にも有利に働く可能性があるが、**注意点がある**。自己注意を使うモデルは入力が長くなるほど計算量が増えるため、**長くまとめた方が重くなる場合がある**。ここは候補ごとに実測して決める。

### 5-2. モデル候補

**電力を第一級の軸に置いて**絞ると、現実的な候補は3つになる。

| 候補 | 容量 | 言語 | 型 | 用語登録 | 句読点 | 電力の見込み |
|---|---|---|---|---|---|---|
| **Nemotron 3.5 ASR 0.6B** | 453MB | 40ロケール（日中英） | transducer | **可** | あり | 現行と同系統。近いと見込む |
| **SenseVoice Small** | 228MB | 中英日韓粤 | 非自己回帰 | 不可 | ITN 有効時 | **最も軽い**（公表 RTF 0.099 / Cortex-A76） |
| 現行 NeMo CTC ja | 625MB | 日本語のみ | CTC | 不可 | あり | 基準 |

参考として外した候補とその理由。

| 候補 | 外した理由 |
|---|---|
| Qwen3-ASR 0.6B | RTF が約10倍。第0段で余裕が確認できた場合のみ復帰 |
| Fun-ASR-Nano（948MB 版） | 容量と RTF（公表 0.144〜0.191、PC 級）で上と同様 |
| sense-voice-funasr-nano（252MB） | SenseVoice の新しい版として有望だが、対応言語と句読点が未確認。SenseVoice の比較対象として一緒に測る |
| Whisper 系（kotoba 含む） | 過去の実機比較で速度が桁違いに不利。中国語を含めると更に大きくなる |
| ReazonSpeech k2 v2 | 日本語のみで課題2・3 を解けない。**ただし日本語の退路として残す** |
| 逐次表示（話しながら文字を出す） | 課題1〜4 のどれも解かず、画面設計の前提を壊す |

### 5-3. なぜ Nemotron 3.5 を第一候補にするか

- **課題2・3 を一度に解く**。日本語・英語・中国語を含む40ロケールに対応し、言語は発話ごとに指定できる（`ja` 固定でも `auto` でも可）。`sherpa_onnx` 1.13.3 の Dart API に `OnlineStream.setOption` があることを実物で確認したので、**Flutter から言語を切り替えられる**。
- **課題1 に効く道具が付いてくる**。transducer なので、ビームサーチと用語登録が両方使える。**これは現行の CTC では手に入らない**。
- **電力の見当が付く**。現行と同じ FastConformer 系で、CTC を transducer にしたものに近い。**未知の領域に飛ばずに済む**のが、発熱を気にする状況では大きい。
- **句読点を内蔵する**。過去に Zipformer を退けた理由（句読点が付かない）を踏まない。
- 容量も 625MB → 453MB と減る。

**主なリスクは、これが逐次型であること**。話しながら出すために先の音を待たずに決める設計なので、**発話全体を見てから決める現行より日本語が落ちる可能性がある**。緩和策は、チャンクを最大の 1120ms 版にすること（大きいほど精度が高いと明記されている）と、ひと続きの話をまとめて流し込むこと。**それでも落ちるなら採らない。**

### 5-4. 課題1 への打ち手（軽い順）

課題1 は単発の施策では上がらない。**電力の追加がほぼゼロのものから順に積む。**

1. **収音と区切りの診断**（第0段）。語頭・語尾の欠け、32msの端数、無音しきい値、小声、遠距離。**モデルを替えても直らない問題をここで潰す。**
2. **用語登録**。自分がよく話す固有名詞を登録できるようにする。効き方が最も直接的で、電力はほぼゼロ。
3. **表記の置換辞書**。「プッシュ通知 → push通知」のような自分の書き方に寄せる。ニューラルネットを増やさない。`sherpa_onnx` に `HomophoneReplacerConfig` があり、認識器の設定として渡せる。
4. **ビームサーチ**。遅延を譲ったぶんで払える。
5. **長い文脈**。認識の単位を変える（5-1）。
6. **量子化の見直し**。int8 と fp16 を比べ、**差が実際にあるときだけ**容量を増やす。

### 5-5. 課題4（自分の声の識別）

**1モデルの原則には反しない**。ASR を2回走らせる話ではなく、**別軸の小さな部品を1つ足す**だけである。

- 使うもの: 声紋を作るモデル1つ（約27MB）と、登録・照合の API（`SpeakerEmbeddingExtractor` / `SpeakerEmbeddingManager`）。
- 電力: 1発話あたりの計算量は ASR よりはるかに小さい。**それでも「ほぼゼロ」と決めつけず、第0段と同じ物差しで測る**。
- 始め方: codex.md の指摘どおり、**最初は判定ではなくラベル付けから**。いきなり他人の声を捨てると、自分の小声・相づち・外国語の発話まで消えて課題1 の体感が悪化する。本人・他者・不明の3つに分け、取りこぼし率を測ってから「自分だけ表示」に進む。
- 限界: VAD の1区間に複数人が入っている場合、その区間の声紋だけでは足りない。ここまで追うなら話者区間の分割が別途必要になる（追加6.6MB）。**最初は対象外とする。**

### 5-6. 触らないもの

録音（`record`）、VAD（Silero）、バックグラウンド録音の仕組み、保存、カードの見せ方、準備ゲート。**今回の課題はどれもここに原因がない。**

## 6. 対抗案 — 認識を後回しにする（録りだめ方式）

第0段の計測で「録音を続けるだけで既に電力が一杯」と出た場合、**本命の差し替えだけでは足りない**。そのときの選択肢を1つ挙げておく。

```text
【 本命 】録音しながら、ひと続きの話ごとに認識する
          → 録音中ずっと、断続的に計算が走る

【 対抗 】録音中は録音と VAD だけ。切り出した音声を溜めておく
          → 前景に戻ったとき、または充電中にまとめて認識する
```

- **良くなること**: 長時間の録音中に**持続的な発熱がなくなる**。「無意識下で長時間録音し続ける」という momeo の芯をいちばん素直に守れる。また、認識をまとめて走らせる前提なら**重いモデルも選択肢に戻る**（充電中に回せばよい）。
- **代償**: 切り出した音声を一時的に保存する必要がある（発話ぶんだけなら 16kHz モノラルで毎秒32KB。30分の発話で約57MB。圧縮すればさらに減る）。未処理の溜まりが増えたときの扱いと、保存した音声の削除・保護を設計する必要がある。画面を開いた直後にまだ文字になっていないカードが並ぶ、という見え方にもなる。
- **条件は満たす**: モデルは1つ、認識は1回、**表示済みのテキストは書き換わらない**。クラウドも使わない。

本命より複雑なので**最初から採らない**。第0段の結果しだいで開く扉として置いておく。

## 7. 採らない案と、その理由

| 案 | 採らない理由 |
|---|---|
| クラウド ASR | 費用と通信量が運用の前提に合わない。常時録音との相性も悪い |
| 二段階認識 | 表示済みテキストの書き換え・複雑さ・発熱。指摘のとおり |
| LLM 整文 | 2つ目のモデルであり電力を食う。加えて、**音声から消えた情報は復元できない** |
| Qwen3-ASR を最初に試す | RTF が約10倍。発熱が既に出ている状況では最もリスクが高い。第0段しだいで復帰 |
| 逐次表示への変更 | 課題1〜4 のどれも解かず、画面設計の前提を壊す |
| 現行モデルの頭を TDT に替える | 元モデルの公表値で CTC との差は各セット約0.1ポイント。課題2・3 も解けない |
| 雑音抑制を常時かける | 録音中ずっと計算が増える。**雑音が主因だと診断できた場合に、発話区間だけへ限定して**初めて検討する |

## 8. 進め方

```text
第0段: 電池と収音を切り分ける
        ・録音のみ / VAD まで / ASR まで で電力と発熱を測る
        ・生の PCM と VAD 切り出し後の音声を両方残して聴き比べる
        ・32ms の端数と、変換ループの確保・コピーを確認する
        ↓  ここで「ASR に余裕があるか」が決まる
第1段: 評価用の音声をそろえる
        ・自分の失敗例が中心。日本語のみ / 日本語＋英語 / 英語・中国語 / 雑音・他人
        ・合成音声だけで判断しない。調整用と最終判定用を分ける
        ↓
第2段: モデルを比べる（同じ PCM を全候補に入れる）
        ・現行 NeMo CTC / Nemotron 3.5（1120ms） / SenseVoice Small
        ・第0段で余裕が確認できた場合のみ Qwen3-ASR を追加
        ・日本語が落ちた場合の退路として ReazonSpeech k2 v2
        ↓
第3段: 遅延を精度に変える
        ・用語登録 → 置換辞書 → ビームサーチ → 認識の単位 の順に積む
        ・1つ積むごとに、精度と電力の両方を測る
        ↓
第4段: 話者のラベル付けを足す
        ・本人 / 他者 / 不明 の3分類まで。捨てる機能はその後
```

第0段と第1段は**モデルを1つも変えずにできる**。ここを飛ばすと、差し替えの結果が良かったのか悪かったのか判断できない。

---

## 9. 判断の分かれ目

| 第0段・第2段で分かること | 進む方向 |
|---|---|
| ASR に電力の余裕がある／熱源は録音側だった | 録音側を直したうえで、Nemotron 3.5 を本命に進める。Qwen3-ASR も候補に戻す |
| 余裕がない／ASR も無視できない | **SenseVoice Small（228MB）**へ。用語登録は諦め、置換辞書と診断で課題1 を拾う |
| Nemotron の日本語が現行より明確に良い | そのまま採用。課題1・2・3 が同時に前進する |
| Nemotron の日本語が現行と同等 | 採用してよい。課題2・3 が解け、用語登録とビームサーチの余地が残る |
| どの多言語モデルも日本語が明確に落ちる | **課題1 を優先し、現行を残す**。課題2・3 は「外国語モード」として手動切替で分離する。同じ端末に2モデルを常駐させず、切り替え式にする |
| 日本語の劣化が英語・中国語の獲得に見合わない | 差し替えを見送り、第0段・第3段の積み上げだけを進める |

**課題2・3 のために課題1 を犠牲にしない**。これは優先順位としてすでに示されているので、判断に迷ったらこの線で切る。

## 10. 未確認のこと

| 項目 | なぜ重要か |
|---|---|
| 発熱の実際の内訳 | すべての判断の前提。**最初に測る1点** |
| Nemotron 3.5 の日本語精度（現行比） | 本命の成否そのもの。公表 CER は横並び比較に使えない |
| Nemotron 3.5 で用語登録とビームサーチが実際に効くか | 逐次型 transducer としては使えるはずだが、このモデルでの実証は未確認 |
| Nemotron 3.5 を Flutter から言語指定できるか（実行時） | API の存在は確認済み。実機での動作は未確認 |
| 日本語と英語が1文に混ざるときの挙動 | 多くのモデルは「1発話に1言語」を前提にしている |
| 認識の単位を長くしたときの電力 | 自己注意を使うモデルでは逆効果になりうる |
| 話者照合のしきい値と取りこぼし率 | 自分の小声・相づちを落とすと課題1 の体感が悪化する |
| sense-voice-funasr-nano（252MB）の対応言語と句読点 | 有望だが公式ドキュメントに記載が無い |
