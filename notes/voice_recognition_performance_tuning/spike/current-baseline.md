## 2. 作った足場

音声は別アプリで録らず、**このアプリ自身で録る**。別アプリの圧縮やノイズ抑制がかかった音は、momeo が `record` 越しに受け取る音と別物になるため、足場として使えない。
録り込みも実行も端末内で完結し、転送も形式の変換も要らない。

### 録り込みの経路

音声は別アプリで録らず、**いつも通り momeo を使うだけで溜まる**。

- 本番のリスニングが使う `SttListeningPipeline` に録り込み先を渡す。渡すのは **debug ビルドのときだけ**で、release では何も残らない（`listening_providers.dart` の `_spikeCaptureDirPath()`）
- 録音用の画面は作らない。本番のリスニング画面は `PageView` の中で動き続けるため、別画面で録ると**マイクの取り合い・認識器（625MB）の二重読み込み・本番メモの汚染**が起きる
- VAD が区切った1発話ぶんを `files/spike_audio/<時刻>.wav` として残す。`SpeechSegment.samples` を `sherpa_onnx` の `writeWave()` で書き出しており、wav を組み立てるコードは自作していない
- ファイル名を時刻にすることで、通し番号を持たなくても録った順に並ぶ。16kHz・モノラルで出るため変換が要らない
- 音声と対になる認識結果を `files/spike_audio/captured.tsv` へ1行ずつ追記する（列: `file` / `recognized` / `durationSec` / `elapsedMs`）

### 区分と正解テキストを付ける画面

dev カタログ「STT → 録り込み」（`lib/pages/dev/catalog/sections/stt/stt_capture_section.dart`）。**録音操作は持たない。**

- `captured.tsv` を読み、人が付けたラベルを重ねて表示する
- 既定は「日本語・調整用・認識結果のまま」。**そこから外れるものだけ人が触る**
  - 区分: `ja` / `ja_en` / `en` / `zh` / `noise`
  - 用途: 調整用 / 最終判定用
- 結果は `files/spike_audio/answers.tsv` へ自動で書き出す（打つたびではなく少し待ってからまとめて書く）
  - 列: `file` / `category` / `purpose` / `answer` / `recognized` / `durationSec` / `elapsedMs`
  - `answer` と `recognized` の両方を残すため、**どれが認識ミスだったかは2列の差分で分かる**。確認済みフラグは持たない

### 固定 wav を流す経路

dev カタログ「STT → 固定 wav」（`lib/pages/dev/catalog/sections/stt/stt_fixed_audio_section.dart`）。

- 録り込みが溜めた `files/spike_audio/` をそのまま読む（音声の受け渡しは無い）
- 2つの経路で流す
  - **丸ごと** … wav 全体を1発話として認識器へ渡す（モデル同士の比較用）
  - **VAD 経由** … wav をマイク入力と同じ 0.1 秒刻みで VAD に流し、区切られた分だけ認識する（本番に近い挙動）
- wav の読み込みは `sherpa_onnx` の `readWave(path)`。解析コードは自作していない
- 認識器は現行と同じ `SttAudioWorker`。モデルのパスは `SttModelProvisioner().provision()` から取る
- 結果は画面表示に加え、`files/spike_results/<経路>_<日時>.tsv` へ書き出す
  - 列: `file` / `seg` / `text` / `durationSec` / `elapsedMs`
  - 認識テキストが空の場合は `(空)`。先頭の注記行に総件数と空の件数が入る
  - 流せなかった wav（16kHz でない・読めない）と、VAD が1件も区切らなかった wav は `!! 理由` の行として残る

### `SttAudioWorker` / `SttListeningPipeline` への追加

| 追加 | 内容 |
|---|---|
| `startListening(captureDirPath:)` | 渡されたときだけ、区切った発話を wav として保存し、認識結果を `captured.tsv` へ追記する |
| `SttTranscribed.capturedFileName` | 保存した wav のファイル名。保存していなければ null |
| `_spikeCaptureDirPath()`（`listening_providers.dart`） | debug ビルドでだけ録り込み先を返す。release では null |
| `transcribeWhole(samples)` | VAD を通さず丸ごと1発話として文字化する。返事に中身を乗せるため `_Reply` に `result` を足し、`_request` の戻り値を `Future<Object?>` にした |
| `SttListeningPipeline(captureDirPath:)` | 録り込み先を worker へ橋渡しする。録音の作り直し時も同じ先を渡す |

本番のリスニングには、録り込み先を渡す一手だけを足した。release では null になるため挙動は変わらない。**この仕掛けは spike ブランチ限定で、main には入れない。**

## 5. 英語混じりの扱い（課題②の前提を確かめる）

仮説（`research/opus_repropose_v3.md` §1-C-1）: 現行モデルは**英語をまともに出せない**。語彙にラテン文字のマージが1つも無く、大文字トークンが0個であることからの推論で、実際に通してはいなかった。

**この仮説は外れている。** 足場を作る途中に実機で得た出力を、加工せず写す。

### `I think` が8通りになる

`I think` は、**同じセッション内で8通りの表記に散った**。

| 他者音声（動画） | `ieteink` / `itin` / `アイス` / `アイtイン` / `アイスインe` / `アイスティe` |

### 語ごとの扱い

### 読み取れること

- **ラテン文字は出る。** 「出せない」ではなく「**小文字でしか出ない**」が実態。大文字トークンが0個という語彙の観察とは矛盾しない

**課題②の動機は変わる。** 「英語が出ない」ではなく「**英語の表記が定まらない**」問題として立て直す。
さらに §6.1 から、この揺れは**モデルの判断が境界上にある**ことによると分かった。ホットワードや語彙の固定で境界を動かせるかは S6 以降で確かめる。

## 6. 空の認識結果

録り込み25件のうち **2件（8.0%）** が空。

**この2件は当初「他者音声」と記録していたが、誤りだった。** 6.11 秒は**本人の英語**である（2026-09-21 に本人が聴いて確認。S2 で判明）。

| # | ファイル | 音声長 | 出力 |
|---|---|---|---|
| 1 | `…19-41-52-750851.wav` | 0.61 秒 | `(空)` |
| 2 | `…19-44-54-203960.wav` | **6.11 秒** | `(空)` ／ 実際は `For example, if I speak like this in English suddenly, can you understand.` |

**`listening_providers.dart` の `emptyResultCount` のコメントは「咳・物音の誤検知」としているが、これでは説明が付かない。**
6.11 秒は咳や物音の長さではない。VAD が6秒間を「発話」と判断して切り出したのに、認識器が1文字も返していない。
**中身は普通の英語の一文だった。** 空になったのは音が無かったからではなく、**現行モデルが英語を1文字も返さなかったから**である。
短い側（0.61 秒）は、同じ長さで `あっ` が出た例（`…19-43-30-875706.wav`）と対になる。**長さだけでは空になる条件を説明できない。**

`research/opus_repropose_v3.md` が挙げている sherpa 1.13.3 の NeMo 正規化の桁落ちバグ（空文字の原因になりうる・1.13.8 で修正）と突き合わせる価値がある。**S4 `lib-update` の比較対象はこの2件。**

### 空より悪い結果がある

英語のみ 34.7 秒の発話が `そうニ` の2文字になった（§4）。
**空なら「空だった」と分かるが、これは何かが出てしまうため気付けない。** 空の件数だけを指標にすると、この壊れ方を見落とす。

## 6.1 足場の再現性（S4 へ渡す前提）

同じ wav を「丸ごと」で**2回流して 25/25 完全一致**。**認識器は決定的**で、固定 wav の足場はライブラリ比較に使える。

ただし**録音時の結果と、その wav を流し直した結果は 25件中16件で食い違う**。

原因は非決定性ではない。認識器が決定的である以上、変わったのは入力しかない。
**wav 保存時に Float32 → int16 の丸めが入る**ため、読み直したサンプルは録音時のものと完全同一にならない。

食い違いの例（左が録音時、右が wav 流し直し）。

| 録音時 | 流し直し |
|---|---|
| `ハワイですよ` | `ハワイです` |
| `ieteink` | `ipetin` |
| `iphene` | `iphone` |
| `フacebook` | `フaceブok` |
| `(空)` | `ピ` |
| `オーr` | `オnw` |

**この揺れ幅の小ささが重要である。** 振幅にして 1/32768 程度の差でここまで出力が変わる。
**モデルの判断が境界上にある**ことを意味し、§5 の表記ゆれと同じ現象の別の見え方である。

**S4 への申し送り。** ライブラリを比べるときは、**旧ライブラリの「丸ごと」対 新ライブラリの「丸ごと」**で比べる。
どちらも同じ丸めを通るので比較は成立する。**録音時の結果を基準にしてはいけない。**

## 6.2 ついでに見えたこと（この spike では追わない）

**区切りが `maxSpeechDuration` を超えている。** `stt_audio_worker.dart` の `_kMaxSpeechDuration` は 30.0 秒だが、実際には 33.56 秒・35.48 秒・37.17 秒の区切りが出た。上限として効いていない。

**同じ音声を VAD に流し直すと、さらに細かく割れる。** 録り込み24件を「VAD 経由」で流すと31区切りになった（日本語5件→8区切りなど）。一度区切った音の端に無音が残るためと考えられる。

どちらも S5 `segmentation` へ申し送る。**この spike では設定を変えない。**

## 6.3 文字化が発話時間のどれだけを使っているか（S1 への申し送り）

`captured.tsv` の `durationSec` と `elapsedMs` を割るだけで、**文字化の稼働率が計測なしで出る**。

| 指標 | 値 |
|---|---|
| 発話合計 | 426.1 秒（25件） |
| 変換合計 | 42.4 秒 |
| 全体の比 | **10.0%** |
| 1件ごとの比 | 平均 9.9%（最小 8.1% / 最大 16.9%） |

**S1 の仮説「現行 ASR は発話時間の一部しか CPU を使っていない」は、この数字と整合する。**
録音・VAD は常時動いているのに対し、文字化は発話時間の1割しか回らない。1日を通した稼働率は、**話していない時間があるぶんさらに小さくなる**。

**ただし、これは消費電力ではない。** 次の2点で慎重に扱う。

- **1コアの実時間である。** 認識は音声 isolate 1つで動くため CPU 時間としても同じ桁だが、**短時間に強く回すぶんクロックは高い**。「10% だから電力も10%」とは言えない
- **debug ビルドの値である。** 録り込みは debug 限定のため、release では速くなる可能性がある

したがって **S1 で実測すべきは温度**であり、電池の絶対値は後回しにできる。
