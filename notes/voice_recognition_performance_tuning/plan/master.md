# 音声認識の改善 — 検証計画

## 1. この文書について

- **目的**: 調査でまとめた案を、**効くかどうかを切り分けられる大きさの実験（spike）に分解する**こと。採用する施策を決める文書ではない。
- **いまの状態**: `research/` に調査が揃っているが、**実機で効いたことはまだ一つもない**。自分の現行の結論は `research/opus_repropose_v3.md`、相手側の最終案は `research/codex_repropose_v2.md`。どちらも机上の提案である。
- **したがって**: 本書では v3 の「第一手」「実施順」も**採用の決定ではなく、検証の順序についての仮説**として扱う。どの案が効くかは、spike が終わるまで決めない。
- **仮説の正本**: `research/opus_repropose_v3.md`。本書は v3 の未確認項目を実験に落としたものである。

### git の運用

- spike ごとにブランチを切る。名前は `spike/voice_recognition_performance_tuning/<短い英語名>`
- ブランチはいくつ作ってもよい。**`main` には一切マージしない**
- 分かったことは `notes/voice_recognition_performance_tuning/spike/<同じ短い英語名>.md` に書く
- spike が一段落したら **`main` に戻り**、結果を見たうえで、どの方向で本番実装するかを改めて検討する
- 本書を書いた時点では、**コードもブランチも spike 記録も作らない**

#### `notes/` は `main` が正本（**2026-09-21 に追加**）

**コードと記録を逆向きに扱う。** spike ブランチは**実験コードを置く場所**であり、**計画書と記録を置く場所ではない**。

| 何 | どこが正本 | `main` に入れるか |
|---|---|---|
| `lib/` `scripts/` `pubspec.yaml` の実験コード | spike ブランチ | **入れない**（使い捨て。レビューもしない） |
| `notes/.../plan/` の計画書 | **`main`** | もともと `main` にある |
| `notes/.../spike/` の記録 | **`main`** | **spike が終わったら写す** |

- **spike を始めるとき、計画書は `main` から読む。** 枝の中のコピーを読まない。枝を切ったあとに `main` 側で計画書が改訂されることがあり、**枝のコピーは古い**
- **spike が終わったら、記録ファイルだけを `main` に写す。** `git checkout <branch> -- notes/.../spike/<名前>.md` のように**ファイルを1つずつ指定**する。ブランチごとマージしない。そうすれば `lib/` が混ざる余地がない
- **計画書を枝の中で書き換えない。** 書き換えるなら `main` 側で行う。枝の計画書を `main` に上書きすると、`main` 側の改訂が消える

**この節を足した理由**: S2・S4・S5 のブランチは、計画書が全面改訂される21分前の S3（`96cf384`）から枝分かれしていた。そのため**古い計画書のコピーを持ったまま走り**、書いた記録も枝の中に取り残された。S1・S2・S4 の記録が `main` に無い状態が2日続き、**`main` を見ても何が分かったのか読めなかった**。取り残した6件は 2026-09-21 に `main` へ集約済み。

### 設計の原則

- **一度に変えるものは1つ**。ライブラリ更新・モデル差し替え・区間長変更を同じブランチに入れない
- **測定系と介入系を混ぜない**。まず現状を測り、そのあとで1つずつ変える
- 「動かす」ことが目的ではない。「**その仮説が棄却できるか、残るか**」が目的
- 配布の作り込み・UI・永続キュー・エラー復旧・リファクタは、検証に必要でなければ入れない
- **コードを書かずに測れるものは、コードを書かない**
- 「うまくいった」は採用を意味しない。採用判断は全 spike のあと

### 人の手数についての原則（S3 の反省から）

S3 の最初の計画は、人に「別アプリで録る → 変換する → 渡す → 全件書き起こす → 全件ラベルを申告する」をさせる作りだった。**手間が大きすぎて実行されない計画は、計画として失敗している。** 次の5つを全 spike に適用する。

- **人には判断だけを頼み、作業は頼まない。** 録る・転送する・変換する・書き写す・数値を読み取る・表に転記するは、すべて作業である
- **既定値は機械が埋め、人は差分だけ触る。** 全件記入させない。機械の出力を初期値にし、違うものだけ直してもらう
- **材料はアプリ自身が副産物として生む。** 評価用のデータを別経路で用意して渡す作りにしない
- **受け渡しを作らない。** 端末内で完結させる。手元との転送は、消えたときの復旧用にだけ用意する
- **人の回答はファイルに構造化して残す。** チャットで返させない。後続の spike が読み直せる形（TSV など）で端末内に置く

**この原則は「コードを書かずに測れるものは、コードを書かない」より優先する。** 人が繰り返す操作は、機械側に寄せてよい。設定を振るために再ビルドを繰り返させるくらいなら、dev 画面に設定の入口を作るほうが正しい。ただし**寄せるのは手数の削減に必要な最小限**であり、配布の作り込み・本番 UI・自動採点は依然として作らない。

### 共通の足場（S3 で作り、以後すべてが使い回す）

モデルを比べるには**同じ音声を同じ入口から流す**必要がある。現行の dev カタログのセクションはすべてマイク入力で、固定音声を読む経路が無い。

**S3 で作り終えている。** コードはブランチ `spike/voice_recognition_performance_tuning/current-baseline`（コミット `96cf384`）にある。**後続の spike は、このブランチから枝を切って使う。同じやり方で作り直さない。**

足場は次の3つでできている。**これ以上は作らない**（自動採点・グラフ表示・本番 UI の作り込みはしない）。

| 何 | 中身 |
|---|---|
| **録り込み**（本番のリスニングに debug 限定で同居） | いつも通り喋るだけで、VAD が区切った1発話ぶんが `files/spike_audio/<時刻>.wav` に溜まる。認識結果と対にして `captured.tsv` に追記される（列: `file` / `recognized` / `durationSec` / `elapsedMs`）。release では何も残らない |
| **ラベル付け**（dev カタログ「STT → 録り込み」） | 区分（`ja` / `ja_en` / `en` / `zh` / `noise`）・用途（調整用 / 最終判定用）・正解テキストを `answers.tsv` に書き出す（列: `file` / `category` / `purpose` / `answer` / `recognized` / `durationSec` / `elapsedMs`）。**既定は「日本語・調整用・認識結果のまま」で、人は違うものだけ触る** |
| **固定 wav の流し込み**（dev カタログ「STT → 固定 wav」） | 溜まった wav を「丸ごと」（1発話として認識器へ）と「VAD 経由」（0.1秒刻みで VAD に流す）の2経路で流し、`files/spike_results/<経路>_<日時>.tsv` に書き出す（列: `file` / `seg` / `text` / `durationSec` / `elapsedMs`）。空は `(空)`、流せなかったものは `!! 理由` |

- **音声と結果の正本は端末内**（`getApplicationSupportDirectory()` 配下）。`.dev_models/spike_audio/` と `.dev_models/spike_results/` は**バックアップ**である（`scripts/pull_android_spike_audio.sh` で回収、`scripts/place_android_spike_audio.sh` で復元）
- **正解テキストは `answers.tsv` の `answer` 列にある。** 突き合わせは `file` 列をキーに機械的に結合し、**差分が出た行だけを人に見せる**
- **全 spike を Android で行う。** iOS はバンドルリソース同梱しか配置の経路が無く、「新しい配布経路は作らない」に触れる

#### 足場を使うときの注意（S3 で判明）

- **認識器は決定的。** 同じ wav を「丸ごと」で2回流して 25/25 一致した。ライブラリやモデルの比較に使える
- **ただし録音時の結果と、その wav を流し直した結果は食い違う**（25件中16件）。wav 保存時に Float32 → int16 の丸めが入るため。**比較は必ず流し直し同士で行い、録音時の結果を基準にしない**
- **`_kMaxSpeechDuration`（30.0 秒）が上限として効いていない**（37.17 秒の区切りが出た）。S5 の対象
- **同じ音声を「VAD 経由」で流すとさらに細かく割れる**（24件 → 31区切り）。S5 の対象
- **土台の `sherpa_onnx` は 1.13.8 に揃える**（S4 で決定）。1.13.3 との差は小さいが、版が混ざった比較をしないため
- **数文字の揺れは、版を1つ上げるだけで常時発生する**（S4 で丸ごと25件中15件が変化）。**設定やモデルを振ったときに、数文字の差を「効果あり」と読んではいけない**
- **正解が確定している行は3件しかない**（`ja_en`）。**これが全 spike の比較の解像度を決めている**。英語・普通話の正解確定と `最終判定用` の収録は S3 の残タスク

### 実施順（ID の順ではない）

**S1（段 A・B のみ）→ S3 → S2 → S4 → S5 →（S6・S7・S8）→ S1 の段 C → S9 → S10。**

## 4. 各 spike

### S1 `power-triage` — 電池と発熱の内訳を切り分ける

- **仮説**: 現行 ASR は発話時間の一部しか CPU を使っていないため、いま出ている発熱の主因は ASR ではなく、録音・VAD・画面など**常時動いている側**にある。**S3 のデータと整合している**（文字化は発話時間の 10.0%。`spike/current-baseline.md` §6.3）。残る実測は**温度**。
- **やること（最小）**: 段階を「待機」「録音のみ」「録音＋VAD」「録音＋VAD＋現行 ASR」に分け、**CPU → 温度 → 電池の順**に測る。**dev カタログの既存セクション（record / VAD / 転写）をそれぞれ単独で動かせば、新しいコードはほぼ要らない。** 値は `adb` で取り、**人に読み取らせない**（人がやるのはケーブルを抜き差しすることだけ）。
  - **切り分けの答えは CPU で出る。** CPU 使用率は充電中でも変わらないので、**ケーブルをつないだまま数分で4段階を一巡できる**
  - 温度はケーブルを外す必要があるが、飽和が早いので**1段階20分ほど**で足りる。満充電に戻さなくてよい
  - **電池残量の実測（段 C）はこの spike ではやらない。** 全条件でやると、粒度が1%刻みで充電待ちも入るため**暦で2〜3日かかる**。**S6・S7 のあとに、現行と採用候補を1本ずつ**測る
- **やらないこと**: 最適化の実施。環状バッファ化や描画の見直しは、ここでは**候補として記録するだけ**にする。**全条件で電池の減り方を測ること。段階ごとに満充電へ戻すこと。**
- **観察の目安**: 数値の合格線は置かない（現行の実測値が無いため）。記録するのは、段階ごとの**CPU の取り分・温度・時間経過後の速度低下**と、**発話率をいくつか変えたときの差**、それに電池の絶対値を1本。release 相当で測り、debug の値を製品の消費電力と見なさない。
- **記録先**: `spike/power-triage.md`
- **次へ**: ASR の寄与が小さいと出れば、重い候補（S7）を残したまま進む。ASR も無視できないと出れば、**S7 を後回しにし、軽い候補（S6）を先に見る**。**段 C（電池の実測）は S6・S7 のあとに戻ってきて行う。**

### S2 `capture-audit` — 収音と発話境界を診断する

- **仮説**: 語頭・語尾の欠けなど、**モデルを替えても直らない取りこぼし**が収音か区切りの側にある。
- **やること（最小）**: **S3 のブランチから枝を切り、録り込みに生の PCM の保存を足す。** 切り出し後の wav は録り込みがすでに保存しているので、足すのは生 PCM 側だけ。**生 PCM のどの区間が切り出しに対応するかを機械が記録し、その区間を切り出した wav を並べて人に渡す**（長い音源の中から人に探させない）。確認するのは語頭・語尾、短い相づち、30秒境界、停止時の末尾、小声、遠距離、雑音、入力機器の切り替え。停止時に投入されない最大32msの端数（[stt_audio_worker.dart:415](../../../lib/stt/stt_audio_worker.dart:415)）が実際に語尾を削っているかも見る。
- **やらないこと**: しきい値の変更。**ここでは直さない**（直すのは S5）。
- **観察の目安**: 「切り出し前には聞こえる語が、切り出し後に消えているか」を事例として残す。件数と条件を書く。**32msの端数を精度問題全体の原因と決めつけない。**
- **記録先**: `spike/capture-audit.md`
- **次へ**: 境界の問題が見つかれば S5 を実施する。見つからなければ S5 は後回しにしてよい。

### S3 `current-baseline` — 現行モデルの素の出力を固定音声で記録する（**実施済み**）

- **仮説**: 現行モデルは**英語をまともに出せない**（v3 §1-C-1 の推論）。また**空の認識結果が一定の頻度で出ている**。
- **やったこと**: 評価音声が**いつも通りアプリを使うだけで溜まる**録り込み経路と、**溜まった wav を丸ごと／VAD 経由で流す** dev 経路を作り、現行モデルの出力を記録した。詳細は §1「共通の足場」。
- **分かったこと**
  - **英語の仮説は外れた。** 「出せない」ではなく「**表記が定まらない**」。`I think` が8通りに散り、実行ごとに変わる。**課題②は表記の安定性の問題として立て直す**
  - **英語のみ・普通話は崩壊する。** 34.7 秒が `そうニ` の2文字、普通話は漢字が出ずカタカナの音写。表記ゆれとは別問題
  - **空は25件中2件（8.3%）で、2件とも他者音声。** 6.11 秒の空があり、「咳・物音の誤検知」では説明が付かない
  - **空より悪い壊れ方がある。** 空なら空と分かるが、`そうニ` は気付けない。**空の件数だけを指標にしない**
  - 足場は決定的（25/25 一致）だが、**録音時の結果と流し直しの結果は食い違う**（int16 丸め）。**比較は流し直し同士で行う**
- **記録先**: `spike/current-baseline.md`（やり残しは同ファイルと `plan/spike/current-baseline.md` §10）
- **次へ**: **S4 へ進む。** 比較対象は空の2件と、崩れた出力。

### S4 `lib-update` — ライブラリだけ更新して同じ音声を流し直す

- **仮説**: `sherpa_onnx` 1.13.3 に残っている特徴量正規化の桁落ちが、**空結果や崩れた出力の一部を作っている**（v3 §1-D-1。因果は一次情報で追えているが実機では未検証）。
- **やること（最小）**: **モデル・設定・画面をすべて固定**し、依存を 1.13.3 → 1.13.8 に上げるだけ。S3 と同じ音声を同じ経路で流し直す。
- **やらないこと**: モデルの差し替え、区間設定の変更、他の改善の同時投入。**更新ついでの整理もしない。**
- **観察の目安**: S3 で記録した**空結果と崩れた出力が減るか**を、同じ音声で1件ずつ突き合わせる。突き合わせは結果 TSV を `file` 列で結合し、**差分が出た行だけを人に見せる**。1.13.3 → 1.13.8 では onnxruntime も上がりネイティブ成果物も入れ替わるため、**更新そのものが別の差を生む可能性を前提に、良くなった点と悪くなった点の両方を記録する**。
- **S3 からの申し送り**: 比較対象は**空の2件**（0.61 秒と 6.11 秒）。比較は**「丸ごと」同士**で行い、**録音時の結果を基準にしない**（int16 丸めで別物になる）。**空の件数だけを見ない**（34.7 秒 → `そうニ` のような、空より悪い壊れ方を見落とす）。
- **分かったこと（実施済み）**
  - **仮説は外れた。** 1.13.8 で出力は確かに動く（丸ごと25件中15件が変化）が、**予測されていた帰結である空文字が減っていない**（1件 → 1件。埋まった行と新たに空になった行が入れ替わっただけ）
  - **空より悪い壊れ方も手つかず。** 34.65 秒の英語は `そう` → `そうシ` で、2文字が3文字になっただけ
  - **差はライブラリに帰属すると言い切れる。** 1.13.8 で丸ごとを2回流して 25/25 一致（1.13.3 も S3 で確認済み）。**両版とも決定的**
  - 変化の中身は**ほぼすべてが数文字の揺れ**で、文が立て直された行も崩壊した行も無い
  - **追随コストはゼロ。** API の変更なし、コード修正なし、処理時間も有意差なし
  - **35秒の英語が潰れる現象はライブラリ由来ではない。** モデルか VAD の側にある（S5〜S8 の担当）
- **記録先**: `spike/lib-update.md`（実施済み）
- **次へ**: 仮説は外れたが、**以後の spike はすべて 1.13.8 の上で行う**（土台を揃えるため。追随コストがゼロだったことも根拠）。**課題①の空文字・崩壊は前進していない。原因の候補はモデルと VAD に絞られた。**

### S5 `segmentation` — 区切り設定だけを振る

- **仮説**: 無音しきい値や前後の余白を変えると、**モデルを替えずに**日本語の取りこぼしが減る。
- **やること（最小）**: 現行モデルのまま、S2 で見つかった事例に効きそうな設定を振って、S3 の音声で比べる。振るのは無音しきい値・最短発話・前後余白など。**設定は dev 画面から変えられるようにし、1回のインストールで全条件を回す**（定数を書き換えて再ビルドを繰り返させない）。
- **S3 からの申し送り**: **`_kMaxSpeechDuration`（30.0 秒）が上限として効いていない**（37.17 秒の区切りが出た）。**一度区切った音を VAD に流し直すとさらに割れる**（24件 → 31区切り）。**`最終判定用` の音声が未収録**なので、設定を振り始める前に録り足す。
- **S4 からの申し送り**: **土台は 1.13.8。** 1.13.8 でも**区切りの数は変わらない**（32 → 32）ので、S3 で見えた割れすぎはそのまま残っている。**数文字の差を「効果あり」と読まない**（版を1つ上げるだけで15件が数文字動く）。**正解が確定している行は3件しかなく、これが判定の上限**なので、S3 の残タスクを先に片付ける。
- **やらないこと**: モデルの差し替え。**「長くまとめれば文脈が増えて精度が上がる」という前提での設計**（v3 §1-B-3 のとおり、区間を長くすることとモデルが見る文脈が広がることは別）。ここでは探索項目として1つずつ振るだけにする。
- **観察の目安**: 設定ごとに、取りこぼしが減ったか・逆に区切りが粗くなって読みにくくなったかを事例で残す。**重複認識や文字の二重追加が起きていないかも見る。**
- **記録先**: `spike/segmentation.md`
- **次へ**: 効く設定が見つかれば、それを**以後のモデル比較でも同じ設定として固定する**。

### S6 `sensevoice` — SenseVoice Small に差し替えて比べる

- **仮説**: 日英中を1モデルで扱え（課題②③）、日本語も現行に並ぶ（課題①）。**日本語について並ぶ根拠は無く、開発元の公表値はむしろ不利**なので、これは棄却されうる仮説として置く。
- **やること（最小）**: モデルをローカルの固定パスに置き、認識器の設定を差し替える。S3 と同じ音声を流す。句読点の扱い（ITN の設定）と版（2024-07）を記録する。**取得と配置はスクリプトにし、人は1コマンド叩くだけにする**（既存の `scripts/download_nemo_model.sh` と `scripts/lib/spike_device.sh` の流儀に合わせる）。
- **やらないこと**: Play Asset Delivery、配布設計、画面の作り込み、準備ゲートの変更。**端末に固定パスで置いて読むだけでよい。**
- **観察の目安**: 日本語・日英混在・英語・普通話を**別々に**記録する。日本語と普通話は文字の誤り、英語は語の誤りで見るが、**平均して1つの順位にしない**。加えて常駐RAM・異常終了・出力打ち切り・1発話あたりの処理時間を記録する。**日英混在は「表記が定まるか」で見る**（現行は同じ語が実行ごとに変わる。S3 §5）。**同じ音声を2回流し、候補自身の出力が安定しているかも確かめる。**
- **記録先**: `spike/sensevoice.md`
- **次へ**: 日本語が現行に並べば有力候補として残す。落ちれば「軽さと多言語だけでは採らない」と記録し、S7 へ進む。

### S7 `qwen3` — Qwen3-ASR 0.6B に差し替えて比べる

- **仮説**: 多言語を1モデルで扱え、**1.13.3 で用語登録が動く唯一の候補**（v3 §2-3）なので、課題①に対する能動的な手段を持つ。ただし**常駐RAM・持続的な発熱・待ち行列の詰まり**で落ちる可能性がある。
- **やること（最小）**: 複数ファイル構成のモデルをローカル固定パスに置き、認識器の設定を差し替える。S3 と同じ音声を流す。**既定の `maxNewTokens = 128` / `maxTotalLen = 512` を必ず確認し、長い発話が途中で切れていないかを見る。** 取得と配置は S6 と同じスクリプトの流儀にする。
- **やらないこと**: 配布設計、用語登録の評価（それは S9）、最適化（アクセラレーター対応など）。
- **観察の目安**: S6 と同じ項目に加えて、**常駐RAM の最大値**と、**発話率を上げたときに未処理が増え続けないか**を記録する。**RAM は `adb shell dumpsys meminfo` で機械が取り、人に読み取らせない。** 出力が途中で切れた事例を、モデルの認識能力の不足と**区別して**記録する。
- **記録先**: `spike/qwen3.md`
- **次へ**: RAM・熱・詰まりのいずれかで落ちれば、そこで打ち切って S9 も飛ばす。残れば S9 へ。

### S8 `nemotron` — Nemotron 3.5 に差し替えて比べる

- **仮説**: 言語の品質区分が優先順位と一致し（日＝最上位・英＝最上位・中＝二番手）、句読点と大文字にも対応する。ただし**用語登録とビームサーチはリリース版では使えず**（v3 §1-B-1）、**展開後は現行より大きく**（約650MB・v3 §1-B-2）、**online API への移行**という最も大きな変更を伴う。
- **やること（最小）**: online の認識器で、1120ms 版を読んで S3 と同じ音声を流す。言語指定が Flutter から実際に効くかを確認する。取得と配置は S6 と同じスクリプトの流儀にする。
- **やらないこと**: **master の未リリース実装を取り込まない。** 用語登録とビームサーチの実験は、対応がリリース版に入ってから別条件として行う。状態管理・復旧・配布の作り込みもしない。
- **観察の目安**: S6・S7 と同じ項目。加えて、**online 移行に伴う実装量**を所感として残す（採用判断の材料になる）。
- **記録先**: `spike/nemotron.md`
- **飛ばす条件**: **S6・S7 の両方で日本語が明確に落ちた場合は実施しない。** 2つの多言語モデルが揃って落ちたなら、「多言語モデルが専用日本語モデルに並ぶ」という仮説自体が弱く、最も変更の大きい候補を試す理由が無い。

### S9 `hotwords` — 用語登録が効くかを見る（S7 が残った場合のみ）

- **仮説**: 固有名詞・専門用語を事前に渡すと、その語の誤りが減る。
- **やること（最小）**: S7 のブランチ上で、用語を渡した場合と渡さない場合を同じ音声で比べる。
- **やらないこと**: 用語を登録する画面の実装。
- **観察の目安**: 渡した語が正しく出るようになったかに加えて、**無関係な語が挿入される方向に偏っていないか**を、用語を含まない対照音声でも見る。**追加計算を「ほぼ無料」と決めつけず、処理時間の差も記録する。**
- **記録先**: `spike/hotwords.md`
- **飛ばす条件**: S7 が落ちた場合は実施しない。

### S10 `notation-dict` — 表記の置換辞書（低優先）

- **仮説**: 確定表示の直前に決定的な置換を当てると、読み返しやすさが上がる。
- **やること（最小）**: 少数の規則で、自分の書き方に寄せる置換を当てて比べる。**置換したい語の候補は `answers.tsv` の `answer` と `recognized` の差分から機械が出し、人は選ぶだけにする。**
- **やらないこと**: 意味を変える同音語の一括置換。**消えた英語を取り戻す用途に使わない**（テキストからは復元できない）。
- **S3 からの申し送り**: **英語の表記ゆれを置換で直そうとしない。** 同じ語が実行ごとに違う綴りになるため（`iphene` / `iphone`、`airドrップ` / `airdrop`）、**置換のキーが安定しない**。この spike で扱えるのは、表記が安定している日本語側だけである。
- **観察の目安**: 読み返しやすさは数値にしにくいので、**変わった事例と、意図せず壊れた事例の両方**を残す。
- **記録先**: `spike/notation-dict.md`
- **着手条件**: 課題①②の他の spike が片付いてから。

## 5. spike のあとに戻って決めること

**全 spike が一段落したら `main` に戻り、記録を見たうえで初めて次を検討する。本書の時点では決めない。**

- **課題①**: ライブラリ更新・区切り設定・モデル差し替えのうち、どれが実際に効いたか。効いたものだけを本番の検討対象にする
- **課題②③**: 多言語モデルへ移る価値があったか。**日本語を落とさずに移れる候補があったか**
- **どの候補も日本語で現行に届かなかった場合**: 差し替えを見送り、**課題②③は解けないと明示する**という結論も正当なものとして扱う
- **課題④**: ①〜③の結論が出てから、着手するかどうかを判断する
- **本番計画の要否**: 採用する方向が決まった場合に限り、そこで初めて本番の分割計画（`notes/on_device_stt/outline.md` のような形）を作るかどうかを考える

**「うまくいった」は採用を意味しない。** 長時間の録音を続けられること、RAM、発熱、待ち行列の詰まりを満たさない候補は、精度が良くても採らない。

## 6. 対象外

| 案 | 今回 spike を切らない理由 |
|---|---|
| クラウド ASR | 費用と通信量。前提として除外 |
| 二段階認識 | 表示済みテキストの書き換え・複雑さ・発熱。前提として除外 |
| 別 LLM による整文 | 2つ目のモデルであり電力を食う。加えて音声から消えた情報は復元できない |
| 言語別に複数 ASR を切り替える | 「モデルは1つ」の前提に反する |
| master の未リリース実装の取り込み | Nemotron の用語登録・ビームサーチは master にしかない。リリース版に入ってから別条件で評価する |
| アクセラレーター対応（Core ML / NNAPI など） | 品質が合格した候補が出てから考える。全候補に先回りしてやらない |
| 雑音抑制の常時適用 | 録音中ずっと計算が増える。雑音が主因と診断できた場合に、発話区間だけへ限定して初めて検討 |
| 充電中にまとめて認識する（録りだめ） | 数時間の遅延は「即時性を譲る」とは別のUXになる |
| 課題④（話者識別） | ①〜③の検証が終わるまで spike を切らない |
| 配布方式の変更（Play Asset Delivery など） | モデル差し替えの spike では、端末に手で置いて読めば足りる |
