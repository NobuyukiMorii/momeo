# S3 `current-baseline` — 現行モデルの素の出力を固定音声で記録する

## 1. このセッションへの指示

- このセッションでやるのは **S3 だけ**。モデルもライブラリも**替えない**。
- この spike は、**後続すべてが使い回す共通の足場を1つだけ作る**。それは「**決まった wav を読んで認識器に流し、結果をファイルに出す**」最小の dev 経路である。
- **これ以上は作らない。** UI の作り込み、自動採点、バッチ実行、グラフ表示は作らない。
- 評価用の音声をここで揃える。以後の spike はこの音声を使う。
- 途中で人が音声を録る必要がある。**そこで止まり、人に頼み、返ってきた音声で続きを進める。**
- 結果は `notes/voice_recognition_performance_tuning/spike/current-baseline.md` に書く。**`main` にはマージしない。**

## 2. 背景

### 仮説

- 現行モデルは**英語をまともに出せない**（`research/opus_repropose_v3.md` §1-C-1。語彙にラテン文字のマージが1つも無く、大文字トークンが0個であることから推論したが、**実際に通したことはない**）
- **空の認識結果**が一定の頻度で出ている（`lib/providers/listening_providers.dart` の `emptyResultCount`。コメントでは「咳・物音の誤検知」としている）

### 答える問い

- 英語混じりを通すと、実際に何が出るか（カタカナ化 / 欠落 / 小文字の綴り / 無音扱い）
- 空の認識結果はどのくらいの頻度で、どんな音で起きているか
- 日本語・英語・普通話それぞれで、素の出力はどうなっているか

### なぜ固定音声が要るか

現行の dev カタログのセクションは**すべてマイク入力**で、同じ音声を流し直せない。モデルを比べるには同じ音声を同じ入口から入れる必要がある。ここで1回だけ作る。

## 3. 開始条件と依存

- ブランチ: `main` から `spike/voice_recognition_performance_tuning/current-baseline` を切る
- 依存する spike: **なし**
- 前提: 実機にモデルが置いてあること（Android は `scripts/place_android_device_models.sh`、iOS は `scripts/place_ios_models.sh`）

## 4. 作業の分担

| 誰が | 何を |
|---|---|
| エージェント | ブランチ作成、固定 wav を流す dev 経路の作成、音声の配置手順の用意、実行と結果の書き出し、記録の下書き |
| **人** | 評価用の音声を録る（自分の声で・実際の失敗例を含めて）、端末への配置の承認と実行、実機の操作 |
| 止まる条件 | 固定 wav を流す経路ができたところ。ここでエージェントは待ち、人が録った音声で続きを進める |

## 5. エージェントが行う手順

1. ブランチを切る。
2. **固定 wav を流す dev 経路を1つ作る。** 置き場所は `lib/pages/dev/catalog/sections/stt/` の下。`catalog_page.dart` の `_Section(title: 'STT', ...)` に1項目だけ足す。
   - wav の読み込みは `sherpa_onnx` の `readWave(path)` を使う。戻り値 `WaveData` は `samples`（`[-1,1]` の `Float32List`）と `sampleRate` を持つ。**wav を解析するコードを自作しない。**
   - 認識器は現行と同じものを使う。`lib/stt/stt_audio_worker.dart` の `SttAudioWorker.spawn({modelPath, tokensPath})` を使うのがいちばん近い。モデルのパスは `lib/stt/stt_model_provisioner.dart` の `SttModelProvisioner().provision()` から取る（`nemoModel.path` / `nemoTokens.path`）。
   - **VAD を通すかどうかは、両方できるようにする。** 「wav を丸ごと1発話として認識器へ渡す」経路と、「wav を VAD に流して区切ってから認識する」経路の2つ。前者はモデル比較用、後者は本番に近い挙動の確認用。
   - 出力は**画面だけにしない**。1件ごとに次をテキストファイルへ書き出す: 入力ファイル名 / 認識テキスト / 音声長 / 処理時間。空文字の場合も**空だったと分かる形で**書く。
3. **音声の置き場所を決めて手順を書く。** 評価音声は容量が大きいので git に入れない。`.dev_models/` は `.gitignore` で丸ごと無視されているので、**その下に `spike_audio/` を作って使う**（`.gitignore` を変更しなくて済む）。端末へは既存の手置きと同じ考え方で置く（Android は `/data/local/tmp` 経由で `run-as jp.momeo` のアプリ領域へ。`scripts/place_android_device_models.sh` の流儀に合わせる。**新しい配布経路は作らない**）。
4. **ここで止まる。** 人に §6 を依頼する。
5. 音声が揃ったら、全件を2つの経路（丸ごと / VAD 経由）で流し、出力ファイルを回収する。
6. 結果を §7 の枠に整理する。**英語混じりの出力は、加工せず原文のまま残す。**

## 6. 人が行う手順

### 録ってほしい音声

**自分の声で、実際にメモを取るときと同じ距離・同じ環境で**録る。合成音声だけにしない。

| 区分 | 目安 | 入れてほしいもの |
|---|---|---|
| 日本語のみ | 多め | 日常の独り言、言い直し、否定、数字、日時、人名、専門用語 |
| 日本語＋英語 | 中くらい | 英語として発音する単語、カタカナで言う外来語、略語、製品名やサービス名 |
| 英語のみ | 少し | 短い文 |
| 普通話 | 少し | 短い文（話せる人がいなければ「未収録」と書いて飛ばしてよい） |
| 雑音・他者・テレビ | 少し | 自分が話していない音。空の認識結果を見るため |

**「うまく認識できなかった実際の例」を必ず入れる。** これが今回いちばん重要な材料になる。

### 分け方

- **調整用**と**最終判定用**に分ける。後の spike で設定を振るときは調整用だけを見て、最後に最終判定用で確かめる
- 1ファイル1発話でも、まとまった録音でもよい。**どちらにしたかを書く**

### 返してほしいもの

| もの | 形 |
|---|---|
| wav ファイル | 16kHz・モノラルが望ましい。難しければそのままでよい（エージェントが変換する） |
| 各ファイルが何を言っているか | テキストで。**正解として使う** |
| 区分 | 上の表のどれか |
| 調整用 / 最終判定用の別 | どちらか |

## 8. やらないこと

- モデルの差し替え、ライブラリの更新、区切り設定の変更
- 自動採点、文字誤り率の自動計算、UI の作り込み
- 本番の画面・保存・配布への変更
- 固定 wav を流す経路以外の新しい仕組み

## 9. 完了条件と、次へ渡すもの

**完了条件**: 次の3つが揃っていること。

1. **固定 wav を流して結果をファイルに出せる経路**が、このブランチにある
2. **評価用の音声**が `.dev_models/spike_audio/` に揃い、正解テキストと区分が付いている
3. **現行モデルの素の出力**が記録に残り、空の結果の件数と割合が書かれている

**次へ渡すもの**: `spike/current-baseline.md` と、`.dev_models/spike_audio/` の音声（git には入れない）。**コードはマージしない。** 後続の spike は、このブランチの dev 経路を**同じやり方で作り直す**か、このブランチから枝を切って使う。どちらにしたかを記録に書く。

**必ず S4 `lib-update` へ進む。** ただし、ここで英語が意外にも実用になっていた場合は、課題②の前提が変わるので**その旨を記録に明記する**（S6 以降の動機が課題③中心に変わる）。
