# S7 `qwen3` — Qwen3-ASR 0.6B に差し替えて比べる

## 1. このセッションへの指示

- このセッションでやるのは **S7 だけ**。用語登録の評価はしない（それは S9 `hotwords`）。
- 変えるのは**認識モデルだけ**。ライブラリは 1.13.8 のまま、区切り設定は S5 で決まった値のままにする。
- **配布の作り込みをしない。** モデルを端末の固定パスに置いて読むだけでよい。
- この候補は**常駐RAM・発熱・待ち行列の詰まりで落ちる可能性が高い**。**精度より先に、そこを見て早く打ち切る。**
- **既定の出力長上限（`maxNewTokens` = 128 / `maxTotalLen` = 512）を必ず確認する。** 長い発話が途中で切れたとき、それをモデルの認識能力の不足と取り違えない。**S3 の録り込みには 30 秒を超える発話が複数ある**（最長 37.17 秒）ので、上限に当たりやすい。
- **人の手数を増やす作りにしない**（`master.md` §1 の原則）。とくに次をさせない。
  - **約1GB のダウンロードと配置を人の作業にしない。** スクリプト1本にし、人は1コマンド叩くだけにする
  - **常駐RAM を人に読み取らせない。** `adb shell dumpsys meminfo` で機械が取る
  - **`maxNewTokens` を変えるたびに再インストールさせない。** 画面から変えられるようにする
  - **全件の出力を読ませない。** 差分が出た行だけを見せる
- 結果は `notes/voice_recognition_performance_tuning/spike/qwen3.md` に書く。**`main` にはマージしない。**

## 2. 背景

### 仮説

多言語を1モデルで扱え（課題②③）、**sherpa_onnx の現行版で用語登録が動く唯一の候補**なので、課題①に対する能動的な手段を持つ（`research/opus_repropose_v3.md` §2-3）。ただし**RAM・発熱・詰まり**で落ちうる。

### 答える問い

- 日本語・日英混在・英語・普通話はどうか
- **常駐RAM はどこまで増えるか。バックグラウンド録音中に OS に落とされないか**
- 発話率を上げたとき、未処理が増え続けないか
- 出力が途中で切れる事例はあるか

### 注意（`research/opus_repropose_v3.md` §1-E）

「重み読み出しが現行の約23倍」という見積もりはあるが、**絶対値に直すと1日あたり電池の1%台**で、それ単独では不採用の理由にならない。**電池の倍率を理由にここで打ち切らないこと。** 見るべきは RAM と熱と詰まりである。

## 5. エージェントが行う手順

1. S4 のブランチから枝を切る（`sherpa_onnx` は 1.13.8 のまま）。
2. S3・S4 の記録と、端末内の音声・`answers.tsv` があることを確認する。**無ければ止める。**
3. 足場（固定 wav を流す dev 経路）はブランチに入っている。**作り直さない。**
4. **モデルの取得と配置をスクリプト1本にする。** 対象は `sherpa-onnx-qwen3-asr-0.6B-int8-2026-03-25`。
   - **複数ファイル構成**である。frontend・encoder・decoder の3つの onnx と、tokenizer のディレクトリ。現行モデル（単一ファイル）とは形が違う
   - 展開後の合計は約1GB。**端末の空き容量の確認もスクリプトの中で行う**（人に確認させない）。現行モデル 625MB が同居していることを勘定に入れる
   - 取得・配置は S6 と同じ流儀（`scripts/download_nemo_model.sh` と `scripts/lib/spike_device.sh`。`/data/local/tmp` 経由 → `run-as jp.momeo` コピー）。**新しい配布経路は作らない**
   - **`SttModelProvisioner` 本体は変更しない**
5. **認識器の設定を差し替える。** 使う設定クラスは `OfflineQwen3AsrModelConfig`。`OfflineModelConfig` の `qwen3Asr` に渡す。
   - フィールドは `convFrontend` / `encoder` / `decoder` / `tokenizer` / `maxTotalLen` / `maxNewTokens` / `hotwords` ほか
   - **`maxNewTokens` の既定は 128、`maxTotalLen` の既定は 512。** 長い発話で足りるかを最初に確かめ、足りなければ上げて、**上げたことを記録する**。**画面から変えられるようにし、再インストールを繰り返させない**
   - `hotwords` はこの spike では**空のまま**にする（評価は S9）
   - `OfflineModelConfig` の `tokens` に何を渡すかは、**着手時に `~/.pub-cache/hosted/pub.dev/sherpa_onnx-1.13.8/lib/src/offline_recognizer.dart` を開いて確認する**。想像で書かない
6. **人に §6 を依頼する。ここで止まる。**
7. モデルが置かれたら、**まず短い予備確認を行う。** 起動するか、RAM がどこまで増えるか、異常終了しないか、出力が途中で切れないか。**ここで明らかに条件外なら、精度の評価に進まずに打ち切る。**
   - **長い発話を最初に通す。** S3 の録り込みには 30 秒超が複数あり、最長 37.17 秒。出力長上限に当たるならここで分かる
   - RAM は `adb shell dumpsys meminfo` を一定間隔で取り、最大値を機械が出す
8. 通過したら、S3 と同じ音声を流し、区分ごとに出力をファイルへ書き出す。区分は `answers.tsv` の `category` 列から取る。
9. **同じ音声を2回流す。** 出力が実行ごとに変わるかを見る（現行は変わる。S3 §6.1）。
10. 現行の出力（S4 の「丸ごと」経路の結果）と1件ずつ突き合わせ、**差分が出た行だけを人に見せる**。

## 6. 人が行う手順

1. **スクリプトを1つ実行する**（約1GB のダウンロードから端末への配置まで自動。時間と通信量がかかるので、実行のタイミングだけ決めてほしい）
2. 実機への再インストールの承認と操作
3. **長時間の連続動作を試す。** 充電ケーブルを外し、録音を続けたまま放置する。**数値は S1 のスクリプトで機械が取る**ので、返してほしいのは体感だけ
   - 端末が熱くなったか
   - アプリが落ちていないか
   - 話してから文字が出るまでの待ちが、時間とともに伸びていないか
4. **差分が出た行だけ**を渡されるので、それを読んで次を返す

| 返してほしいもの | 形 |
|---|---|
| 日本語の読み返しやすさ | 現行と比べて。**実際の出力を引用して** |
| 英語混じりの見え方 | 英字で出たか、カタカナか、消えたか。**同じ語で表記が揺れていないか** |
| 長時間動かしたときの様子 | 発熱・落ちた・待ちが伸びた、など。**数値は要らない** |
| 途中で切れた出力 | あれば、その文 |
