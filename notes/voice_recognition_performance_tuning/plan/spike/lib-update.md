# S4 `lib-update` — ライブラリだけ更新して同じ音声を流し直す

## 1. このセッションへの指示

- このセッションでやるのは **S4 だけ**。モデル・設定・画面は**すべて固定**する。
- 変えるのは **`sherpa_onnx` の版だけ**（1.13.3 → 1.13.8）。**更新ついでの整理もしない。**
- S3 `current-baseline` の記録と音声が**必須**。無ければ**進まずに止まる**（想像で進めない）。
- 良くなった点だけでなく、**悪くなった点も同じ重さで記録する**。
- **比較は「丸ごと」経路同士で行う。録音時の結果を基準にしない。** S3 で、録音時の結果と同じ wav を流し直した結果が 25件中16件で食い違うと分かっている（wav 保存時の Float32 → int16 丸め）。旧ライブラリで流し直した結果と、新ライブラリで流し直した結果を比べる。
- **空の件数だけを指標にしない。** S3 で、34.7 秒の発話が `そうニ` の2文字になる例が出ている。**空なら空と分かるが、これは気付けない。** 空より悪い壊れ方を必ず併せて見る。
- **人の手数を増やす作りにしない**（`master.md` §1 の原則）。突き合わせは機械が行い、**差分が出た行だけを人に見せる**。全件を人に読ませない。
- 結果は `notes/voice_recognition_performance_tuning/spike/lib-update.md` に書く。**`main` にはマージしない。**

## 2. 背景

### 仮説

`sherpa_onnx` 1.13.3 に残っている特徴量正規化の桁落ちが、**空の認識結果や崩れた出力の一部を作っている**。

### 根拠（`research/opus_repropose_v3.md` §1-D-1 の要約）

- 現行モデルのメタデータに `normalize_type = per_feature` が入っている（配布ファイルを直接読んで確認済み）
- sherpa はこの値のとき `NemoNormalizePerFeature` を呼ぶ
- **1.13.3 はこの分散を `E[x²] − (E[x])²` で計算していて、float32 で桁落ちする**。1.13.8 で中心化した形に修正済み
- 修正 PR の説明によれば、桁落ちすると外れ値が出て、**int8 エンコーダの動的量子化が壊れ、デコーダが空文字を返す**
- momeo は int8 を使い、VAD で切り出した（前後が無音に近い）区間を渡しており、条件に合致する

**ただし、momeo で実際に起きているかは未確認。** それを確かめるのがこの spike である。

### 答える問い

- S3 で記録した空の結果・崩れた出力は、更新後に減るか
- 更新そのものが別の差（良い方向・悪い方向）を生んでいないか

## 3. 開始条件と依存

- ブランチ: **`spike/voice_recognition_performance_tuning/current-baseline`（`96cf384`）から枝を切る。** 名前は `spike/voice_recognition_performance_tuning/lib-update`。**足場を作り直さない**（`master.md` §1）
- **依存: S3 `current-baseline` が完了していること**
  - `notes/voice_recognition_performance_tuning/spike/current-baseline.md` があること
  - **端末内に音声と `answers.tsv` があること**（正本は端末。`.dev_models/spike_audio/` はバックアップで、消えていれば `scripts/place_android_spike_audio.sh` で戻す）
  - **どちらか欠けていたら、このセッションはここで止める。** S3 を先に実施してもらう
- 前提: **Android 実機**（`master.md` §1）
- **S3 の「丸ごと」経路の出力（`.dev_models/spike_results/whole_*.tsv`）を、比較の基準として先に手元に置く**

## 4. 作業の分担

| 誰が | 何を |
|---|---|
| エージェント | ブランチ作成、`pubspec.yaml` の版の変更、ビルドの確認、固定音声の流し直し、S3 との突き合わせ、記録の下書き |
| **人** | 実機への再インストール（署名・USB・承認が要る場合）、実機の操作 |
| 止まる条件 | 実機ビルドを入れる直前。それ以外はエージェントが進める |

## 5. エージェントが行う手順

1. S3 のブランチから枝を切る。
2. S3 の記録と、端末内の音声・`answers.tsv` があることを確認する。**無ければここで止める。**
3. `pubspec.yaml` の `sherpa_onnx` の版を 1.13.8 に上げる（現在は `^1.13.2`、解決済みは `pubspec.lock` で 1.13.3）。**他の依存は触らない。**
4. `flutter pub get` を実行し、`pubspec.lock` で 1.13.8 に解決されたことを確認する。
5. **ビルドが通るか確認する。** 通らない場合、原因が API の変更なら、**最小の追随だけ**を行い、何を直したかを記録する。大きな追随が必要なら、そこで止めて記録し、人に相談する。
6. **本番コードの意味は変えない。** `lib/stt/stt_audio_worker.dart` の `_createRecognizer` は `nemoCtc` のまま、VAD の定数もそのままにする。
7. 実機に入れ、S3 と**同じ音声を同じ経路で**流す（丸ごと経路と VAD 経由の両方）。出力をファイルに書き出す。
8. S3 の出力と**1件ずつ突き合わせる**。**突き合わせは機械が行う。** 結果 TSV を `file` 列（VAD 経由は `file` + `seg`）で結合し、`answers.tsv` の `answer` 列を正解として並べる。
   - 空だったものが埋まったか（**S3 の空2件が主対象**: 0.61 秒と 6.11 秒）
   - 崩れていたものが直ったか（**英語のみ 34.7 秒 → `そうニ` が代表例**）
   - **直っていたものが崩れていないか**
   - **比較は「丸ごと」対「丸ごと」。** 録音時の `captured.tsv` と比べてはいけない
9. 差が出たものだけでなく、**差が出なかったことも**記録する。**人に見せるのは差分が出た行だけ**にする。

## 6. 人が行う手順

- 実機への再インストールが必要な場面で、署名・USB デバッグ・インストールの承認を行う
- **差分が出た行だけ**を渡されるので、判断に迷うものがあれば**元の音声を聴いてどちらが正しいか**を返す（全件を読む必要はない）
- **`最終判定用` の音声は未収録**（S3 の残タスク）。この spike は調整用だけで進めてよい

## 8. やらないこと

- モデルの差し替え（S6〜S8 の担当）
- 区切り設定の変更（S5 の担当）
- 「せっかく更新したから」という理由での他の改善の同時投入
- リファクタ、警告の一括修正、不要コードの整理
- `sherpa_onnx` を 1.13.8 より先（master など）に上げること
- **録音時の結果（`captured.tsv`）を比較の基準にすること**
- **全件の出力を人に読ませること**（差分だけ見せる）

## 9. 完了条件と、次へ渡すもの

**完了条件**: S3 と同じ音声で、更新前後の出力の差（または差が無いこと）が記録に残っていること。

**次へ渡すもの**: `spike/lib-update.md` のみ。**コードはマージしない。**

**差が出ても出なくても、以後の spike（S5〜S10）はすべて 1.13.8 の上で行う。** 土台を揃えるためであり、更新が効いたかどうかとは別の理由である。この方針を記録に明記しておく。
