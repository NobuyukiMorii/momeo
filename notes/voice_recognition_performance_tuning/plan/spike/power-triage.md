# S1 `power-triage` — 電池と発熱の内訳を切り分ける

## 1. このセッションへの指示

- このセッションでやるのは **S1 だけ**。他の spike（S2 以降）には進まない。
- **アプリの本番挙動を変えない。** これは測定だけの spike である。
- 新しい仕組みを作らない。**既にある dev カタログのセクションを単独で動かして測る。**
- 最適化はしない。「ここが重そう」と思っても、このセッションでは**候補として記録するだけ**にする。
- **このセッションで行うのは段 A（CPU）と段 B（温度）まで。合わせて2時間ほどで終わる。**
  - **段 C（電池残量の実測）はこのセッションではやらない。** 数時間の放置が要るうえ、切り分けの判断には使わない。**候補が絞れたあと（S6・S7 のあと）に、現行と候補を1本ずつ測る**
  - 詳しくは §2「測り方の順序」
- **電池残量の減り方を全条件で測らない。** これがこの spike をいちばん長引かせる。
  - **切り分けの答えは CPU 時間で出る。** これは有線をつないだまま数分で測れる
  - **温度**はケーブルを外す必要があるが、飽和が早いので1段階20分ほどで足りる
- **S3 でもう半分は分かっている。** `captured.tsv` から、**文字化は発話時間の 10.0% しか使っていない**と出ている（`spike/current-baseline.md` §6.3）。仮説と整合するので、**この spike の主目的は「温度で裏づけを取ること」に絞ってよい。**
- **人の手数を増やす作りにしない**（`master.md` §1 の原則）。とくに次をさせない。
  - **電池残量と温度を人に読み取らせない。** `adb` で取れる値を人が目で見て転記する必要はない
  - **数値を人に表へ転記させない。** 取得したログをそのまま記録に落とす
  - **何時間も喋り続けさせない。** 発話率は音源を流して作る
  - **満充電のやり直しを何度もさせない。** 充電待ちが測定時間より長くなる
- 結果は `notes/voice_recognition_performance_tuning/spike/power-triage.md` に書く。**`main` にはマージしない。**

## 2. 背景

### 仮説

現行の文字化は、発話している時間のうち一部しか CPU を使っていない。したがって、いま出ている発熱の主因は文字化ではなく、**録音・VAD・画面など常時動いている側**にある。

### 答える問い

- 「待機」「録音のみ」「録音＋VAD」「録音＋VAD＋文字化」で、**CPU をどれだけ使っているか**
- 同じ4段階で、温度はどう変わるか
- 発話率（話している時間の割合）を変えると、その差はどう動くか
- 熱で処理速度が落ちる現象は起きるか

### S3 から分かっていること（この spike の出発点）

S3 の録り込みは、1発話ごとに**発話長と変換時間**を `captured.tsv` に残している。割るだけで文字化の稼働率が出る。

| 指標 | 値 |
|---|---|
| 発話合計 | 426.1 秒（25件） |
| 変換合計 | 42.4 秒 |
| 全体の比 | **10.0%**（1件ごとの平均 9.9%・最大 16.9%） |

**仮説と整合している。** 録音・VAD は常時動くのに対し、文字化は発話時間の1割しか回らない。話していない時間があるぶん、1日を通した稼働率はさらに小さい。

**ただしこれは消費電力ではない。** 1コアの実時間であり（isolate は1つなので CPU 時間としても同じ桁だが、短時間に強く回すぶんクロックは高い）、しかも**debug ビルドの値**である。だから**温度の実測には意味がある**。詳しくは `spike/current-baseline.md` §6.3。

### 測り方の順序（**この spike の要**）

素朴に「各段階で電池の減り方を測る」とやると、**数日かかるうえに差が見えない**。理由は2つある。

- **電池残量の粒度が粗い。** `level` は1%刻みで、待機状態の消耗は30分で1〜2%しか動かない。「待機」と「録音のみ」の差はこの中に埋もれる。差を見るには1段階あたり1〜2時間が要る
- **段階ごとに充電待ちが入る。** 同じ残量から始めようとすると、測定時間より充電時間のほうが長くなる。4段階 × 2発話条件 = 8回で、暦にして2〜3日になる

**そこで測る順序を変える。** この spike の問いは「ASR か、常時動いている側か」という**切り分け**であって、消費電力の絶対値ではない。切り分けは CPU 時間で答えが出る。

| 段 | 何を測るか | ケーブル | 1段階あたり | いつやるか | 何が分かるか |
|---|---|---|---|---|---|
| **A** | **CPU 使用率・CPU 時間** | **つないだまま** | 数分 | **この spike** | **切り分けの答え。** 常時動いている側が回し続けている量と、文字化が発話のときだけ使う量 |
| **B** | 温度 | 外す | 20分ほど | **この spike** | 実際に熱くなるのはどの段階か。温度は飽和が早い。**S7 の熱を評価するための基準値になる** |
| **C** | 電池残量 | 外す | 数時間 | **後回し（S6・S7 のあと）** | 絶対値（1日あたり何%か） |

**この spike は A と B で終える。合わせて2時間ほど。**

**C を今やらない理由。** 切り分けの判断に使わないうえ、**候補が絞れたあとにやるほうが同じ放置時間で意味が増す**。現行と採用候補を1本ずつ測れば、「乗り換えて電池がどうなるか」という実際に知りたい比較になる。いま4段階 × 2条件で測っても、比べる相手がいない数字が並ぶだけである。

**C を全条件でやらない。** やると他の spike に進めない。

### なぜ先にこれをやるか

重いモデルに動く前に「ASR に余力があるのか」が分からないと、モデル比較の結果を解釈できない。根拠は `research/opus_repropose_v3.md` の §1-E と §4-1。

- 依存する spike: **なし**（最初に実施してよい）

## 4. 作業の分担

| 誰が | 何を |
|---|---|
| エージェント | ブランチ作成、**CPU・温度・電池を自動で取るスクリプトの用意**、測定の実行（段 A は人の手を借りずに回せる）、ログからの表の作成、結果メモの下書き |

## 5. エージェントが行う手順

### 準備

1. ブランチを切る。
2. **測定に使う画面が長時間動き続けるかを最初に確かめる。** ここが準備でいちばん引っかかりやすい。**新規に作らない。** `lib/pages/dev/catalog/catalog_page.dart` の `_Section` に次が登録済みである。
   - `Packages` → `record`（`PackagesRecordSection`）… マイク取得のみ
   - `STT` → `VAD 区切り`（`SttVadSection`）… 録音＋VAD
   - `STT` → `文字化`（`SttTranscriptionSection`）… 録音＋VAD＋文字化
   - 「待機」はカタログの一覧を開いたまま何もしない状態とする

   画面が消える・スリープで止まる・すぐ終了するなら、**そのセクションを動かし続けられるようにする最小の変更だけ**を加える（画面を消えないようにする等）。本番コードは触らない。**ここで大きな変更が要ると分かったら、その事実を記録して人に相談する。**
3. 実機で release 相当のビルドを作る。`Makefile` に `make run d=<デバイスID> mode=release` がある。**debug の観測値を製品の消費電力と見なさないこと。**
4. **発話率の作り方を決める。** 人に何時間も喋らせない。
   - 「よく話す」は、**動画やラジオを流しっぱなしにして作る**。S3 で動画の音から録り込みが成立しているので、この方法は実証済み
   - 「ほとんど話さない」は静かな場所に置く
   - **ここで測るのは電力であって精度ではない**ため、他者音声でかまわない。その旨を記録に書く

### 段 A — CPU で切り分ける（ケーブルをつないだまま・数分）

5. **プロセス単位の CPU 使用率を一定間隔で取る。** 充電中でも値は変わらないので、**ケーブルをつないだまま測れる。放置も充電待ちも要らない。**
   - `adb shell dumpsys cpuinfo` は shell から常に取れ、プロセスごとの負荷が出る。**これを主軸にする**
   - **スレッド単位まで見られるかは端末による。** `adb shell top -H -p <pid>` や `/proc/<pid>/task/*/stat` は、release ビルド（`run-as` が使えない）だと見えない場合がある。**着手時に実際に叩いて確かめ、使えた／使えなかったを記録に書く。想像で書かない**
   - 4段階 × 2発話条件を**続けて一巡する**。1段階あたり数分でよい。**ここまでで30分程度**
6. **累積の CPU 時間も取る。** 使用率のサンプリングだけでは、文字化のように「短く強く使う」処理を取りこぼす。
   - `adb shell dumpsys batterystats --reset` で計測を始め、区間の終わりに `adb shell dumpsys batterystats --charged jp.momeo` で uid ごとの CPU 時間を出す
   - **この経路は充電状態の影響を受ける。** 使えるかどうかは着手時に確かめ、使えなければ段 B の放置中に併せて取る
7. **ここで仮説を一度判定する。** 常時動いている側と文字化の取り分が見えたら、§7 に書く。S3 の 10.0% と突き合わせ、**食い違うならその食い違いを記録する**（debug と release の差、クロックの差が出ている可能性がある）。

### 段 B — 温度を見る（ケーブルを外す・1段階20分ほど）

8. 人に §6 を依頼する。**段階ごとに20分ほどケーブルを外して放置してもらう。** 温度は飽和が早いので、これで十分。
   - 無線デバッグ（Android 11 以降）が使えるなら、**外したまま一定間隔で温度を取る**。使えるかどうかを最初に確かめ、記録に書く
   - 使えないなら、つなぎ直した直後に `adb shell dumpsys battery`（`temperature`）と、対応していれば `adb shell dumpsys thermalservice` を取る。**つなぎ直しで少し下がることを前提に、条件を揃えて比べる**
   - **満充電に戻さなくてよい。** 温度は残量に大きく左右されない。残量が近い範囲（例: 80〜100%）で揃えれば足りる

### まとめ

9. 取得は1つのスクリプトにまとめ、**出力はそのまま記録に貼れる形**（TSV）にする。置き先は `.dev_models/spike_power/`（`.gitignore` 済み）。**このスクリプトは段 C と S7 で使い回す。**
10. 表を埋め、**どの段階で増えたか**を文章でまとめる。あわせて、測定中に気づいた重そうな箇所を「最適化の候補」として列挙する（実施はしない）。
11. **段 C の段取りだけ書き残して、このセッションは終える。** どの段階を測るべきか（段 A・B で差が最大だったもの）を指定しておく。

> **見込みの時間**: 準備 1〜2時間、段 A 30分、段 B 1〜2時間。**ここまでで終える。**

### 段 C — 電池の絶対値（**この spike ではやらない。S6・S7 のあと**）

**候補が絞れてから行う。** 現行と採用候補を同じ条件で1本ずつ測れば、「乗り換えて電池がどうなるか」という実際に知りたい比較になる。

- 満充電からケーブルを外して数時間放置する。段階は**段 A・B で差が最大だったもの**
- 放置中は取りに行けないので、つなぎ直したあとに **`adb shell dumpsys batterystats --history` で電池推移を時系列で吸い出す**。OS 側が履歴を持っているので事後に取れる
- **取るのは現行1本＋候補1本まで。** それ以上は取らない

## 6. 人が行う手順

**段 A では何もしなくてよい。** ケーブルをつないだまま測れるので、画面を開いておくだけでよい。

### 段 B（温度）

1. 対象の画面を開く
2. **充電ケーブルを外し、20分ほどそのまま放置する**
3. つなぎ直す。エージェントが値を取りに行く
4. これを段階ごとに繰り返す。**満充電に戻さなくてよい**（残量が近い範囲であればよい）

### 段 C（電池）は、この spike では依頼しない

候補が絞れたあと（S6・S7 のあと）に、現行と候補を1本ずつ測る。そのときに改めて依頼する。

**数値を読んで返す必要はない。** 電池の推移も温度も CPU も、機械が取る。
発話条件（よく話す／ほとんど話さない）の音源も、エージェントが用意した手順に従って流すだけでよい。

気づいたことがあれば、それだけ返してほしい。

| 返してほしいもの | 形 |
|---|---|
| 体感 | 熱くなった時間帯、動作が重くなったか。**気づかなければ「特になし」でよい** |

## 9. 完了条件と、次へ渡すもの

**完了条件**: 「発熱の主因は ASR か、録音の常時稼働側か」について、**どちらかに寄せて話せる材料が記録に残っていること**。**段 A と段 B が埋まっていれば完了。段 C は待たない。** 決着しなくてもよいが、「分からなかった」で終わらせず、何が分からなかったかを書く。

**次へ渡すもの**: `spike/power-triage.md` と、CPU・温度・電池を取るスクリプト（**S7 の長時間確認と、段 C で再利用する**）。**本番コードはマージしない。**

**段 C は S6・S7 のあとに行う。** どの段階を測るかを記録に書き残しておくこと。

この結果は後続の判断に使う。

- ASR の寄与が小さい → 重い候補（S7 `qwen3`）を残したまま進める
- ASR も無視できない → **S7 を後回しにし、軽い候補（S6 `sensevoice`）を先に見る**
