# S1 `power-triage` — 電池と発熱の内訳を切り分ける

## 1. このセッションへの指示

- このセッションでやるのは **S1 だけ**。他の spike（S2 以降）には進まない。
- **アプリの本番挙動を変えない。** これは測定だけの spike である。
- 新しい仕組みを作らない。**既にある dev カタログのセクションを単独で動かして測る。**
- 最適化はしない。「ここが重そう」と思っても、このセッションでは**候補として記録するだけ**にする。
- **人の手数を増やす作りにしない**（`master.md` §1 の原則）。とくに次をさせない。
  - **電池残量と温度を人に読み取らせない。** `adb` で取れる値を人が目で見て転記する必要はない
  - **数値を人に表へ転記させない。** 取得したログをそのまま記録に落とす
  - **何時間も喋り続けさせない。** 発話率は音源を流して作る
- 人がやるのは「**充電ケーブルを外して放置する**」という物理的なことだけ。**そこで止まり、人に頼み、返ってきたログで続きを書く。**
- 結果は `notes/voice_recognition_performance_tuning/spike/power-triage.md` に書く。**`main` にはマージしない。**

## 2. 背景

### 仮説

現行の文字化は、発話している時間のうち一部しか CPU を使っていない。したがって、いま出ている発熱の主因は文字化ではなく、**録音・VAD・画面など常時動いている側**にある。

### 答える問い

- 「待機」「録音のみ」「録音＋VAD」「録音＋VAD＋文字化」で、電池の減り方と温度はどう変わるか
- 発話率（話している時間の割合）を変えると、その差はどう動くか
- 熱で処理速度が落ちる現象は起きるか

### なぜ先にこれをやるか

重いモデルに動く前に「ASR に余力があるのか」が分からないと、モデル比較の結果を解釈できない。根拠は `research/opus_repropose_v3.md` の §1-E と §4-1。

## 3. 開始条件と依存

- ブランチ: `main` から `spike/voice_recognition_performance_tuning/power-triage` を切る
- 依存する spike: **なし**（最初に実施してよい）
- 前提: **Android 実機**に release 相当のビルドを入れられること（`master.md` §1 のとおり、全 spike を Android で行う）

## 4. 作業の分担

| 誰が | 何を |
|---|---|
| エージェント | ブランチ作成、測定手順の確定、ビルド、**電池と温度を自動で取るスクリプトの用意**、ログからの表の作成、結果メモの下書き |
| **人** | 実機の接続、対象の画面を開く、**充電ケーブルを外して放置する**、放置後にケーブルをつなぎ直す |
| 止まる条件 | 長時間放置の測定に入る直前。ここでエージェントは待ち、人が放置を終えたらログを取りに行く |

## 5. エージェントが行う手順

1. ブランチを切る。
2. 測定に使う画面を確認する。**新規に作らない。** `lib/pages/dev/catalog/catalog_page.dart` の `_Section` に次が登録済みである。
   - `Packages` → `record`（`PackagesRecordSection`）… マイク取得のみ
   - `STT` → `VAD 区切り`（`SttVadSection`）… 録音＋VAD
   - `STT` → `文字化`（`SttTranscriptionSection`）… 録音＋VAD＋文字化
   この3つが、そのまま3段階の測定に対応する。「待機」はカタログの一覧を開いたまま何もしない状態とする。
3. 各セクションを開いて**単独で動き続けるか**を確認する。動かない・すぐ止まる場合は、その事実を記録し、**そのセクションを長時間動かせるようにする最小の変更だけ**を加える（画面が消えないようにする等）。本番コードは触らない。
4. 実機で release 相当のビルドを作る手順を用意する。`Makefile` に `make run d=<デバイスID> mode=release` がある。**debug の観測値を製品の消費電力と見なさないこと。**
5. **電池と温度を機械が取る段取りを用意する。** 人が数値を読む場面を作らない。
   - **放置中は取りに行けない**（ケーブルを外すため）。放置が終わってつなぎ直したあと、**`adb shell dumpsys batterystats --history` で放置中の電池推移を時系列で吸い出す**。OS 側が履歴を持っているので、事後に取れる
   - 温度と残量のスナップショットは `adb shell dumpsys battery`（`level` と `temperature`）、端末が対応していれば `adb shell dumpsys thermalservice` も取る
   - **無線デバッグ（Android 11 以降）が使えるなら、ケーブルを外したまま一定間隔で取る。** そのほうが時系列が細かい。使えるかどうかを最初に確かめ、**使えた／使えなかったを記録に書く**
   - 取得は1つのスクリプトにまとめ、**出力はそのまま記録に貼れる形**（TSV）にする。置き先は `.dev_models/spike_power/`（`.gitignore` 済み）
6. **発話率の作り方を決める。** 人に何時間も喋らせない。
   - 「よく話す」は、**動画やラジオを流しっぱなしにして作る**。S3 で動画の音から録り込みが成立しているので、この方法は実証済み
   - 「ほとんど話さない」は無音の部屋に置く
   - **ここで測るのは電力であって精度ではない**ため、他者音声でかまわない。その旨を記録に書く
7. 記録の受け皿を作る。`notes/voice_recognition_performance_tuning/spike/power-triage.md` に §7 の表を先に置く。
8. **ここで止まる。** 人に §6 を依頼する。
9. 放置が終わったらログを吸い出し、表を埋め、**どの段階で増えたか**を文章でまとめる。あわせて、測定中に気づいた重そうな箇所を「最適化の候補」として列挙する（実施はしない）。

> **測定の回数を最初から増やさない。** 4段階 × 2発話条件を最初から長時間やると、それだけで何日もかかる。**まず短時間（30分程度）で4段階を一巡し、差が見える段階が分かってから、その段階だけ長時間で確かめる。**

## 6. 人が行う手順

各段階について、**同じ端末・同じ画面の明るさ・同じ室温**で行う。

1. 端末を満充電にする
2. 対象の画面を開く
3. **充電ケーブルを外し**、決めた時間そのまま放置する（まず30分。差が見えた段階だけ数時間）
4. 時間が来たら**ケーブルをつなぎ直す**。エージェントがログを取りに行く

**数値を読んで返す必要はない。** 電池の推移も温度も、つなぎ直したあとに機械が吸い出す。
発話条件（よく話す／ほとんど話さない）の音源も、エージェントが用意した手順に従って流すだけでよい。

気づいたことがあれば、それだけ返してほしい。

| 返してほしいもの | 形 |
|---|---|
| 体感 | 熱くなった時間帯、動作が重くなったか。**気づかなければ「特になし」でよい** |

## 7. 観察・記録の枠

`notes/voice_recognition_performance_tuning/spike/power-triage.md` に写す表。**数値はスクリプトの出力から転記する。**

| 段階 | 発話条件 | 経過 | 電池 開始→終了 | 温度（最大） | 備考 |
|---|---|---|---|---|---|
| 待機 | | | | | |
| 録音のみ | | | | | |
| 録音＋VAD | | | | | |
| 録音＋VAD＋文字化 | | | | | |

あわせて次を文章で残す。

- **どの段階で増えたか**（増分がいちばん大きい段階）
- 発話条件を変えたときの差
- 時間が経ってから処理が遅くなる現象があったか
- 無線デバッグが使えたかどうか（次の spike の測定のしかたに影響する）
- 最適化の候補（実施はしない。場所と理由だけ）

## 8. やらないこと

- 最適化の実施（変換ループの作り直し、描画の見直し、監視タイマーの削除など）
- モデルの差し替え、ライブラリの更新、区切り設定の変更
- 本番の画面・保存・配布への変更
- 数値の合格線を新たに決めること（現行の実測値が無いため、ここでは**記録するだけ**）
- **人に数値を読み取らせること**

## 9. 完了条件と、次へ渡すもの

**完了条件**: 「発熱の主因は ASR か、録音の常時稼働側か」について、**どちらかに寄せて話せる材料が記録に残っていること**。決着しなくてもよいが、「分からなかった」で終わらせず、何が分からなかったかを書く。

**次へ渡すもの**: `spike/power-triage.md` と、電池・温度を取るスクリプト（S7 の長時間確認で再利用する）。**本番コードはマージしない。**

この結果は後続の判断に使う。

- ASR の寄与が小さい → 重い候補（S7 `qwen3`）を残したまま進める
- ASR も無視できない → **S7 を後回しにし、軽い候補（S6 `sensevoice`）を先に見る**
