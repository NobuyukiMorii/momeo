# S1 `power-triage` — 電池と発熱の内訳を切り分ける

## 1. このセッションへの指示

- このセッションでやるのは **S1 だけ**。他の spike（S2 以降）には進まない。
- **アプリの本番挙動を変えない。** これは測定だけの spike である。
- 新しい仕組みを作らない。**既にある dev カタログのセクションを単独で動かして測る。**
- 最適化はしない。「ここが重そう」と思っても、このセッションでは**候補として記録するだけ**にする。
- 途中で人の操作（実機の充電を外して放置する等）が必要になる。**そこで止まり、人に頼み、返ってきた数値で続きを書く。**
- 結果は `notes/voice_recognition_performance_tuning/spike/power-triage.md` に書く。**`main` にはマージしない。**

## 2. 背景

### 仮説

現行の文字化は、発話している時間のうち一部しか CPU を使っていない。したがって、いま出ている発熱の主因は文字化ではなく、**録音・VAD・画面など常時動いている側**にある。

### 答える問い

- 「待機」「録音のみ」「録音＋VAD」「録音＋VAD＋文字化」で、電池の減り方と温度はどう変わるか
- 発話率（話している時間の割合）を変えると、その差はどう動くか
- 熱で処理速度が落ちる現象は起きるか

### なぜ先にこれをやるか

重いモデルに動く前に「ASR に余力があるのか」が分からないと、モデル比較の結果を解釈できない。根拠は `research/opus_repropose_v3.md` の §1-E と §4-1。

## 3. 開始条件と依存

- ブランチ: `main` から `spike/voice_recognition_performance_tuning/power-triage` を切る
- 依存する spike: **なし**（最初に実施してよい）
- 前提: Android 実機と iPhone 実機のうち、少なくとも1台で release 相当のビルドを実機に入れられること

## 4. 作業の分担

| 誰が | 何を |
|---|---|
| エージェント | ブランチ作成、測定手順の確定、ビルド、ログ取得の準備、結果メモの下書き |
| **人** | 実機の接続と操作、充電ケーブルを外しての長時間放置、電池残量と温度の読み取り、マイクへの発話 |
| 止まる条件 | 長時間放置の測定に入る直前。ここでエージェントは待ち、人が返す数値で続きを書く |

## 5. エージェントが行う手順

1. ブランチを切る。
2. 測定に使う画面を確認する。**新規に作らない。** `lib/pages/dev/catalog/catalog_page.dart` の `_Section` に次が登録済みである。
   - `Packages` → `record`（`PackagesRecordSection`）… マイク取得のみ
   - `STT` → `VAD 区切り`（`SttVadSection`）… 録音＋VAD
   - `STT` → `文字化`（`SttTranscriptionSection`）… 録音＋VAD＋文字化
   この3つが、そのまま3段階の測定に対応する。「待機」はカタログの一覧を開いたまま何もしない状態とする。
3. 各セクションを開いて**単独で動き続けるか**を確認する。動かない・すぐ止まる場合は、その事実を記録し、**そのセクションを長時間動かせるようにする最小の変更だけ**を加える（画面が消えないようにする等）。本番コードは触らない。
4. 実機で release 相当のビルドを作る手順を用意する。`Makefile` に `make run d=<デバイスID> mode=release` がある。**debug の観測値を製品の消費電力と見なさないこと。**
5. 記録の受け皿を作る。`notes/voice_recognition_performance_tuning/spike/power-triage.md` に §7 の表を先に置く。
6. **ここで止まる。** 人に §6 を依頼する。
7. 人から数値が返ったら、表を埋め、**どの段階で増えたか**を文章でまとめる。あわせて、測定中に気づいた重そうな箇所を「最適化の候補」として列挙する（実施はしない）。

## 6. 人が行う手順

各段階について、**同じ端末・同じ画面の明るさ・同じ室温・同じ充電状態（ケーブルを外す）**で行う。

1. 端末を満充電にしてからケーブルを外す
2. 対象の画面を開いたまま、決めた時間（例: 30分と、可能なら数時間）放置する
3. 発話条件を変えて繰り返す。少なくとも「ほとんど話さない」と「よく話す」の2通り
4. 次を記録して返す

| 返してほしいもの | 形 |
|---|---|
| 段階の名前 | 待機 / 録音のみ / 録音＋VAD / 録音＋VAD＋文字化 |
| 経過時間 | 分 |
| 電池残量の変化 | 開始% → 終了% |
| 端末の温度（分かれば） | 触った感じでもよい。数値が取れるなら数値 |
| 発話条件 | ほとんど話さない / よく話す |
| 気づいたこと | 熱くなった時間帯、動作が重くなったか |

> 数値が取りにくい場合は、**同じ時間放置したときの電池の減り方の差**だけでも判断材料になる。

あわせて次を文章で残す。

- 時間が経ってから処理が遅くなる現象があったか
- 最適化の候補（実施はしない。場所と理由だけ）

## 8. やらないこと

- 最適化の実施（変換ループの作り直し、描画の見直し、監視タイマーの削除など）
- モデルの差し替え、ライブラリの更新、区切り設定の変更
- 本番の画面・保存・配布への変更
- 数値の合格線を新たに決めること（現行の実測値が無いため、ここでは**記録するだけ**）

## 9. 完了条件と、次へ渡すもの

**完了条件**: 「発熱の主因は ASR か、録音の常時稼働側か」について、**どちらかに寄せて話せる材料が記録に残っていること**。決着しなくてもよいが、「分からなかった」で終わらせず、何が分からなかったかを書く。

**次へ渡すもの**: `spike/power-triage.md` のみ。**コードはマージしない。**

この結果は後続の判断に使う。

- ASR の寄与が小さい → 重い候補（S7 `qwen3`）を残したまま進める
- ASR も無視できない → **S7 を後回しにし、軽い候補（S6 `sensevoice`）を先に見る**
